title: 一次完整的 DNS 解析过程是怎样的？Go 的纯 Go 解析器（netgo）和 cgo 解析器有什么区别？
--- answer
**1. 一次完整的 DNS 解析过程**

当客户端访问 `api.example.com` 时：
1. **本地检查**：先查浏览器/应用缓存 → 操作系统 `/etc/hosts` 静态映射 → 本机 DNS 缓存（如 `systemd-resolved`、`nscd` 或 NodeLocal DNSCache）；
2. **递归查询（客户端 → 本地递归解析器）**：读取 `/etc/resolv.conf` 中的 `nameserver`（如 `8.8.8.8` 或 K8s 的 `kube-dns/CoreDNS`），以及 `search` 域后缀和 `ndots` 配置，发送 UDP（53 端口，超 512B 字节或开启 EDNS0 超限时回退 TCP）请求；
3. **迭代查询（递归解析器 → 根域 `.` → 顶级域 `.com` → 权威域名服务器 `example.com`）**：递归解析器若无缓存，依次向根、TLD、权威 NS 查询，拿到 `A`（IPv4）或 `AAAA`（IPv6）记录及 `TTL` 缓存时间后返回给客户端。

**2. Go 的两种 DNS 解析器：纯 Go 解析器（`netgo`） vs `cgo` 系统解析器**

Go 的 `net` 包内置了两套 DNS 解析实现（可通过 `GODEBUG=netdns=go` 或 `netdns=cgo`，或编译标签 `-tags netgo` 控制）：

| 维度 | 纯 Go 解析器（`netgo`，Linux 默认优先） | `cgo` 解析器（调用 libc `getaddrinfo`） |
| --- | --- | --- |
| **底层机制** | Go 直接读取 `/etc/hosts` 和 `/etc/resolv.conf`，用非阻塞 UDP/TCP Socket 通过 **netpoller（epoll）** 发包解析 | 通过 cgo 调用操作系统 C 库 `getaddrinfo()` |
| **协程与线程开销** | **不占用 OS 线程**！DNS 等待期间仅挂起 goroutine（`_Gwaiting`），高并发下极轻量 | **阻塞整个 OS 线程（M）**！如果 DNS 服务器抖动，1000 个并发 DNS 查询会瞬间创建 1000 个系统线程导致进程崩溃 |
| **系统兼容性** | 不支持 `/etc/nsswitch.conf` 自定义插件、mDNS 或 systemd 特殊模块 | 完全遵循操作系统级 NSS / VPN / macOS 系统解析链 |

**注意**：Go 标准库的 `net.Resolver` **默认不做进程内 DNS 结果缓存**！如果既没用连接池复用连接，宿主机也没装本地 DNS 缓存，每次新建连接都会触发一次真实的网络 DNS 查询。
--- deep
**原理展开**

深挖 Go 在容器环境（Alpine / Kubernetes）中最常遇到的两个 DNS 线上大坑：

1. **为什么在 Linux 上有时候没有设置 `GODEBUG=netdns=cgo`，Go 也会偷偷退回到阻塞线程的 `cgo` 解析器？**
   在 Linux 上（当未开启 `CGO_ENABLED=0` 静态编译时），Go 运行时会检查 `/etc/resolv.conf` 和 `/etc/nsswitch.conf`：如果发现系统配置了 Go 无法原生理解的模块（如 `mdns`、`nis` 或特殊的 `hosts:` 顺序），Go 为了保证解析结果与系统一致，会**自动回退使用 `cgo` 解析器**（可以通过启动时设置 `GODEBUG=netdns=go+1` 打印每次解析到底走了 `go` 还是 `cgo`）！
2. **Alpine 容器（musl libc）与 Kubernetes `ndots:5` 的组合灾难**：
   - Kubernetes 默认在 Pod 的 `/etc/resolv.conf` 中配置了 **`options ndots:5`** 和 3～4 个 `search` 域（`default.svc.cluster.local`、`svc.cluster.local` 等）；
   - 这意味着当你请求外部域名 `api.stripe.com`（里面只有 **2 个点 `< 5`**）时，解析器**不会直接查 `api.stripe.com.`**，而是先依次拼接所有 search 域查一遍 `api.stripe.com.default.svc.cluster.local`（每次还要并发查 A 和 AAAA 两条记录），**整整发出 8 次无效的 DNS 查询收到 NXDOMAIN 后，第 9 次才去查真正的 `api.stripe.com.`**！

**代码示例**

```go
// 1. 显式定制纯 Go 解析器 + 自定义 DNS 服务器超时与连接控制
func NewCustomResolver(dnsServerAddr string) *net.Resolver {
	return &net.Resolver{
		PreferGo: true, // 强制使用非阻塞的纯 Go 解析器，绝不阻塞 OS 线程
		Dial: func(ctx context.Context, network, address string) (net.Conn, error) {
			d := net.Dialer{Timeout: 1500 * time.Millisecond}
			return d.DialContext(ctx, "udp", dnsServerAddr)
		},
	}
}

// 2. 带单飞合并（Singleflight）与 TTL 缓存的应用层 DNS 预解析拨号器，
// 防止高并发短连接或连接池重连瞬间打爆 CoreDNS！
type CachedDialer struct {
	resolver *net.Resolver
	mu       sync.RWMutex
	cache    map[string]cachedIP
	ttl      time.Duration
}

type cachedIP struct {
	ip       string
	expireAt time.Time
}
```

**常见追问**

- 如果我在请求外部固定域名时，把域名末尾加上一个点，写成 `"api.stripe.com."`（FQDN 完全限定域名），有什么奇效？→ 只要域名以 `.` 结尾，无论 K8s 的 `ndots` 设成多少，DNS 解析器都会识别出这是绝对根域名，**跳过所有 `search` 域拼接，直接 1 次查询命中**！（注意：如果在 HTTPS 请求 URL 里直接写末尾点，需确认服务端 TLS 证书 SNI / Host 路由支持，更通用的做法是在 K8s Pod yaml 中配置 `dnsConfig: options: [{name: ndots, value: "2"}]`）。
- 为什么 Go 标准库坚持不在 `net` 包里内置默认 DNS 缓存？→ 因为在操作系统层面无法统一感知网络切换、DHCP 变更或 `/etc/hosts` 修改，早期 Java 默认永久缓存 DNS 曾引发过无数云上切流不生效的故障；Go 把连接复用交给 `http.Transport` 长连接池，把 DNS 缓存交给节点侧的 `NodeLocal DNSCache`。
- `CGO_ENABLED=0 go build` 编译出来的静态二进制文件一定使用纯 Go 解析器吗？→ **是的**，禁用 cgo 后二进制里根本没有链接 libc，100% 走 `netgo` 纯 Go 解析器。

**实战建议**

- 容器化构建 Go 服务时，若无必须的 C 依赖，统一使用 **`CGO_ENABLED=0`** 编译，或显式设置 `GODEBUG=netdns=go`，彻底杜绝 DNS 抖动引发的操作系统线程暴涨。
- 在 Kubernetes 集群中部署 **NodeLocal DNSCache**，并将高频访问外网域名的 Pod `ndots` 从默认的 `5` 调低为 `2`。

title: HTTP 强缓存（Cache-Control）和协商缓存（ETag / Last-Modified）是怎么工作的？
--- answer
HTTP 缓存机制分为**强缓存**和**协商缓存**两级，核心目标是减少网络带宽传输、降低源站负载并把响应延迟降到 0ms：

```text
浏览器发起请求
  |-- 1. 检查本地缓存的【强缓存】是否未过期（Cache-Control: max-age=3600）
  |      |-- 未过期 -> 直接使用本地缓存（200 from memory/disk cache，完全不发网络请求！）
  |      +-- 已过期或配置了 no-cache -> 进入第 2 步
  v
  |-- 2. 发送请求到服务端进行【协商缓存】校验
         （请求头携带 If-None-Match: "<ETag>" 或 If-Modified-Since: <Date>）
         |-- 资源未变化 -> 服务端返回【304 Not Modified】（无响应体，极省带宽！）
         +-- 资源已变化 -> 服务端返回【200 OK】+ 最新完整资源体 + 新的 ETag/Cache-Control
```

**1. `Cache-Control` 常见指令辨析（最易考误区）**

- `max-age=3600`：在 3600 秒内直接使用强缓存；
- `s-maxage=86400`：专门给 **CDN / 共享代理缓存**看的过期时间（优先级高于 `max-age`）；
- **`no-cache` vs `no-store`**：
  - **`no-cache` 不是“不缓存”**！它的真实含义是“可以保存在本地缓存中，但**每次使用前必须先向服务端发起协商缓存校验（ETag 比对）**”；
  - **`no-store` 才是真正的“绝对禁止任何缓存”**（本地和 CDN 均不得落盘保存，用于银行账单等敏感响应）；
- `private` vs `public`：`private` 表示仅允许终端用户的浏览器缓存，禁止中间 CDN 缓存（防止把用户 A 的个人信息缓存给用户 B！）。

**2. 协商缓存两套标识的对比：`ETag` vs `Last-Modified`**

- `Last-Modified` / `If-Modified-Since`：基于秒级修改时间。缺陷是：**粒度只到秒**（1 秒内修改多次无法感知），且如果文件只是重新生成但内容完全没变，也会导致缓存失效；
- `ETag` / `If-None-Match`：**优先级高于 `Last-Modified`**。由服务端根据内容哈希或版本号生成（如 `"v1-a8f9c2"` 或弱校验 `W/"1024-173000"`），精确到字节级变化。
--- deep
**原理展开**

深挖现代 CDN 与网关缓存设计中的高阶指令（RFC 5861 / RFC 9111）：

1. **`stale-while-revalidate` 与 `stale-if-error`（消除缓存过期毛刺与源站容灾）**：
   - `Cache-Control: max-age=60, stale-while-revalidate=30`：前 60 秒直接命中强缓存；在 60～90 秒之间来了请求，CDN/浏览器**立即先把旧缓存返回给用户（0ms 等待）**，同时在后台异步向源站拉取新数据更新缓存！
   - `stale-if-error=86400`：当源站 Go 服务挂了返回 5xx 时，允许 CDN 在 24 小时内继续拿旧缓存兜底响应用户，实现网关级自动降级！
2. **`Vary` 响应头的作用与缓存雪崩隐患**：
   如果同一个 URL `/api/articles` 会根据请求头的 `Accept-Encoding`（`gzip` vs `br`）或 `Accept-Language` 返回不同的内容，服务端必须在响应头加上 **`Vary: Accept-Encoding, Accept-Language`**，告诉 CDN 把这些请求头的值作为二级缓存 Key，否则不支持 `br` 的老客户端会拿到乱码！但**切忌写 `Vary: User-Agent`**（因为全球客户端的 `User-Agent` 字符串有成千上万种细微差异，会导致 CDN 缓存命中率瞬间暴跌到接近 0）。

**代码示例**

```go
// Go 中实现支持 ETag / If-None-Match 协商缓存与 Cache-Control 的 API 响应辅助函数
func WriteJSONWithETag(w http.ResponseWriter, r *http.Request, data any, maxAgeSec int) error {
	body, err := json.Marshal(data)
	if err != nil {
		return err
	}
	// 计算内容的 SHA-256 前 16 字节作为强 ETag（必须带双引号！）
	sum := sha256.Sum256(body)
	etag := fmt.Sprintf(`"%x"`, sum[:8])

	w.Header().Set("ETag", etag)
	w.Header().Set("Cache-Control", fmt.Sprintf("private, max-age=%d, must-revalidate", maxAgeSec))

	// 检查客户端发来的 If-None-Match（可能包含逗号分隔的多个 ETag 或 "*"）
	if (r.Method == http.MethodGet || r.Method == http.MethodHead) && matchETag(r.Header.Get("If-None-Match"), etag) {
		w.WriteHeader(http.StatusNotModified) // 304 响应不能写响应体！
		return nil
	}

	w.Header().Set("Content-Type", "application/json; charset=utf-8")
	w.WriteHeader(http.StatusOK)
	_, err = w.Write(body)
	return err
}

func matchETag(inmHeader, currentETag string) bool {
	if inmHeader == "" {
		return false
	}
	if strings.TrimSpace(inmHeader) == "*" {
		return true
	}
	for _, part := range strings.Split(inmHeader, ",") {
		cand := strings.TrimSpace(part)
		// 弱比较（Weak Comparison）：忽略开头的 W/ 前缀比对引号内标识
		if strings.TrimPrefix(cand, "W/") == strings.TrimPrefix(currentETag, "W/") {
			return true
		}
	}
	return false
}
```

**常见追问**

- 前端单页应用（React/Vue/Vite）构建出来的 `index.html` 和带哈希后缀的静态资源 `app.8f92a1.js`，它们的 `Cache-Control` 应该怎么配？→ 带内容哈希的 `app.8f92a1.js` 配置**永久强缓存**：`Cache-Control: public, max-age=31536000, immutable`（因为内容一变文件名就会变）；而入口文件 **`index.html` 必须配置为协商缓存 `Cache-Control: no-cache`**，确保每次发版后用户刷新页面能立即拿到引用了新 JS 文件名的 `index.html`！
- 强 ETag（`"abc"`）和弱 ETag（`W/"abc"`）有什么区别？→ 强 ETag 要求每个字节（包括空白符和压缩结果）完全一模一样，可用于 `If-Range` 字节级断点续传；弱 ETag（以 `W/` 开头）只要求业务语义等价（例如基于数据库记录的 `updated_at` 和 `version` 字段拼成 `W/"v3"`，无需先序列化整个大 JSON 算哈希就能直接判断 304！），非常适合动态 API 接口。
- `If-Match` 头是干什么用的（和 `If-None-Match` 有什么不同）？→ `If-None-Match` 用于 `GET` 缓存校验（匹配则返回 `304`）；而 **`If-Match: "v3"` 用于 `PUT / PATCH` 更新操作实现分布式乐观锁（CAS）**——只有当服务端当前资源的版本仍然是 `"v3"` 时才允许修改，如果已被别人改成了 `"v4"`，服务端直接返回 **`412 Precondition Failed`**，防止并发编辑互相覆盖（Lost Update）！

**实战建议**

- 对读多写少的配置或详情查询接口，用数据库里的版本号 `version` 或 `updated_at` 直接构造弱 ETag `W/"<id>-<version>"`——在查询完整关联数据前先比对 `If-None-Match`，命中时直接回 `304 Not Modified`，同时省掉数据库关联查询和网络传输。
- 包含用户个人数据的接口，如果设置了 `max-age`，前面**必须加上 `private`**，严防被公共 CDN 或企业网关误缓存给其他用户。

title: 什么是 mTLS（双向 TLS）？在 Go 中如何配置服务端与客户端双向证书校验及证书热加载？
--- answer
普通的 HTTPS 是**单向 TLS**：只有客户端校验服务端的证书（确认服务端不是假冒的钓鱼网站），而服务端不认识客户端证书。
**mTLS（Mutual TLS，双向 TLS）** 要求在 TLS 握手阶段**服务端和客户端双方互相出示并校验对方的 X.509 数字证书**，廣泛用于微服务网格（Service Mesh 如 Istio）、零信任内网 RPC、金融支付接口和 Kubernetes 组件间通信。

**1. mTLS 握手相比普通 TLS 多了哪几步？**

1. 服务端发送自己的 `Certificate` 后，额外发送一条 **`CertificateRequest`** 消息（附带服务端信任的客户端根 CA 列表）；
2. 客户端校验通过服务端证书后，发送**客户端自己的 `Certificate`**；
3. 客户端使用**自己的私钥**对握手历史消息摘要进行数字签名，发送 **`CertificateVerify`** 消息证明自己确实拥有该客户端证书对应的私钥；
4. 服务端用自己配置的 `ClientCAs` 根证书池验证客户端证书链合法、未过期，并验证 `CertificateVerify` 签名通过后，握手成功。

**2. Go 中配置 mTLS 与不停机证书热轮换（Hot Reload）**

- **服务端配置**：在 `tls.Config` 中设置 **`ClientAuth: tls.RequireAndVerifyClientCert`**，并将内部 CA 根证书放入 **`ClientCAs: caCertPool`**；
- **不停机证书热加载**：内部 mTLS 证书有效期通常很短（如 24 小时或 7 天），如果把证书写死在 `tls.Config.Certificates` 切片里，每次续期都要重启服务。在 Go 中只需实现 **`tls.Config.GetCertificate`**（服务端）和 **`tls.Config.GetClientCertificate`**（客户端）回调函数，从原子指针 `atomic.Pointer[tls.Certificate]` 中动态返回最新加载的证书即可！
--- deep
**原理展开**

深挖 Go `crypto/tls` 在生产落地 mTLS 时的身份提取与安全校验细节：

1. **握手通过只是第一步（Authentication），如何基于客户端证书做细粒度授权（Authorization）？**
   客户端只要持有同一家私有 CA 签发的任何一张合法证书，就能通过 `RequireAndVerifyClientCert` 握手。如果订单服务只允许“支付服务（`spiffe://cluster.local/ns/prod/sa/payment`）”调用，不允许“评论服务”调用，就必须在 `tls.Config.VerifyConnection` 钩子或 HTTP/gRPC 中间件里检查 `r.TLS.PeerCertificates[0]`（叶子证书）的 **SAN（Subject Alternative Name，如 `DNSNames`、`URIs`）** 或 `Subject.CommonName`！
2. **为什么现代证书校验（Go 1.15+）已经废弃了 `CommonName (CN)`，强制要求校验 `SAN`？**
   RFC 6125 废弃了用 `Subject.CommonName` 匹配域名的方式。在用 `openssl` 或 Go 的 `x509.CreateCertificate` 自签发内网 mTLS 证书时，**必须在 `x509.Certificate` 的 `DNSNames`、`IPAddresses` 或 `URIs`（SPIFFE 标准）字段中填入标识**，否则 Go 客户端握手时会直接报错：`x509: certificate relies on legacy Common Name field, use SANs instead`。

**代码示例**

```go
// 支持零停机证书热轮换（Hot Reload）与客户端身份提取的 mTLS 配置组件
type CertReloader struct {
	cert atomic.Pointer[tls.Certificate]
}

func (cr *CertReloader) Reload(certPEM, keyPEM []byte) error {
	c, err := tls.X509KeyPair(certPEM, keyPEM)
	if err != nil {
		return err
	}
	// Go 1.23+ tls.X509KeyPair 已自动填充 c.Leaf；旧版本可手动 x509.ParseCertificate(c.Certificate[0])
	cr.cert.Store(&c)
	return nil
}

func (cr *CertReloader) ServerTLSConfig(clientCAPEM []byte, allowedClientDNS map[string]bool) (*tls.Config, error) {
	pool := x509.NewCertPool()
	if !pool.AppendCertsFromPEM(clientCAPEM) {
		return nil, errors.New("invalid client CA PEM")
	}
	return &tls.Config{
		MinVersion: tls.VersionTLS13, // 内网 mTLS 推荐强制要求 TLS 1.3，握手少一个 RTT 且算法更安全
		ClientAuth: tls.RequireAndVerifyClientCert,
		ClientCAs:  pool,
		// 每次新连接握手时动态获取最新加载的服务端证书，无需重启 Server！
		GetCertificate: func(*tls.ClientHelloInfo) (*tls.Certificate, error) {
			return cr.cert.Load(), nil
		},
		// 握手完成前校验客户端叶子证书的 SAN DNSName 是否在允许调用的白名单内
		VerifyConnection: func(cs tls.ConnectionState) error {
			if len(cs.PeerCertificates) == 0 {
				return errors.New("no peer certificate")
			}
			leaf := cs.PeerCertificates[0]
			for _, dns := range leaf.DNSNames {
				if allowedClientDNS[dns] {
					return nil
				}
			}
			return fmt.Errorf("unauthorized client cert SANs: %v", leaf.DNSNames)
		},
	}, nil
}
```

**常见追问**

- 在 `tls.Config` 中，如果我已经通过 `GetCertificate` 回调返回最新证书了，那 `Certificates` 切片字段应该设为什么？→ 保持为 `nil`（空）即可！因为当 `Certificates` 非空且没有匹配异常时，某些路径下可能优先读取静态切片；只设 `GetCertificate`（客户端对应 `GetClientCertificate`）最清晰确定。
- 服务端的 `RootCAs` 和 `ClientCAs` 两个字段千万别配反了，它们分别是什么？→ **`RootCAs` 是客户端字段**（用来验证远端服务端证书的根 CA）；**`ClientCAs` 是服务端字段**（用来在 mTLS 中验证连过来的客户端证书的根 CA）！如果在服务端配了 `RootCAs` 却没配 `ClientCAs`，客户端证书校验会全部失败。
- 如果某台客户端机器的私钥泄露了，在证书还没到期前怎么紧急吊销它？→ ① 现代云原生最佳实践是**极短有效期证书（Short-lived Certificates，如 Istio / SPIRE 默认每 24 小时甚至每 1 小时自动轮换一次）**，省去沉重的吊销列表查询；② 若使用长周期证书，可在服务端 `VerifyConnection` 钩子中检查本地热更新的证书序列号黑名单（`leaf.SerialNumber`）或 OCSP Stapling。

**实战建议**

- 内网服务间开启 mTLS 时，直接在 `tls.Config` 中设置 `MinVersion: tls.VersionTLS13`，TLS 1.3 彻底移除了所有不安全的静态 RSA 密钥交换套件，赋予所有连接前向安全性（Forward Secrecy）。
- 切勿在自签发测试证书时只写 `-subj "/CN=localhost"`，必须加上 `-addext "subjectAltName=DNS:localhost,IP:127.0.0.1"`。

title: gRPC 的流控（Flow Control）是怎么实现的？传输超大消息时会有什么问题？
--- answer
gRPC 底层基于 **HTTP/2** 协议，因此它的多路复用和流控机制建立在 HTTP/2 的 **`WINDOW_UPDATE` 帧与两级信用窗口（Credit-based Flow Control）**之上：

**1. HTTP/2 与 gRPC 的两级流控窗口**

为了防止在单条 TCP 连接上多路复用的某一个快流（Stream）把整个连接的接收缓冲区塞满、饿死其他并发请求，gRPC 实施两级流控：
- **流级别窗口（Stream-level Window）**：限制单个 RPC 请求/流最多还能发送多少未确认的 `DATA` 帧字节（HTTP/2 默认初始窗口为 **64KB - 1**）；
- **连接级别窗口（Connection-level Window）**：限制整条 TCP 连接上所有并发 Stream 加起来最多能发送的未确认字节数。
- **动态窗口调节（BDP 带宽时延积估算）**：`grpc-go` 默认开启了基于 **BDP（Bandwidth-Delay Product）** 的自动窗口调整——通过定期发送 HTTP/2 `PING` 帧测量当前网络的真实带宽和 RTT，在吞吐量大且接收方消费及时时，自动把流窗口和连接窗口动态放大（最大可达数 MB），而在接收方处理不过来时停止回复 `WINDOW_UPDATE`，自然给发送方施加**背压（Backpressure）**。

**2. 用 gRPC 直接传输超大消息（如 50MB 的文件或大列表）会有什么问题？**

1. **默认 4MB 大小拦截**：gRPC 客户端默认限制最大接收消息 `MaxCallRecvMsgSize` 为 **4MB**（`4 * 1024 * 1024`），超出直接报错 `ResourceExhausted: grpc: received message larger than max`；
2. **全量内存缓冲与 OOM 风险**：Protobuf 对单条 Message 的序列化/反序列化不是流式的，发送和接收一条 50MB 的消息时，调用栈、压缩缓冲、Protobuf 解码对象会同时在堆上产生 **100MB～150MB 的瞬时内存分配**，高并发下极易触发 GC 毛刺甚至 OOM；
3. **队头阻塞（Head-of-Line Blocking）**：gRPC 多路复用同一条连接时，50MB 的大消息切成的几千个 `DATA` 帧会长时间占满连接级流控窗口和网卡发送队列，把同连接上的其他小 RPC 请求延迟全部拖慢！

**解决方案**：超过 1MB～4MB 的大数据，应改用 **gRPC 流式分块传输（Streaming RPC，每次 `Send` 64KB 分块）**，或者将数据存入对象存储（S3/OSS），在 gRPC 消息里只传对象的 URL 凭证。
--- deep
**原理展开**

深挖 `grpc-go` 双向流（Bidirectional Streaming）中的背压机制与大消息拆包实战：

1. **为什么在 `grpc-go` 中连续调用 `stream.Send(msg)` 似乎不会立刻阻塞，要到什么时候才会阻塞？**
   `stream.Send(msg)` 会把序列化后的消息放进本地发送缓冲并扣减当前可用的 HTTP/2 流控窗口配额（`outFlow`）。只要当前 Stream 窗口和 Connection 窗口都还有剩余额度，`Send` 就会立即返回；一旦接收方消费太慢（没有从它的 `Recv()` 读走数据，导致接收方不发送 `WINDOW_UPDATE` 帧回来补充额度），发送方的可用窗口降为 `0`，下一次 `stream.Send(msg)` 就会**自动阻塞挂起**，直到收到对端的 `WINDOW_UPDATE` 或 `ctx` 超时取消！
2. **为什么不建议简单粗暴地把 `grpc.MaxRecvMsgSize(100 << 20)` 调成 100MB 了事？**
   调大阈值只是关掉了安全保险丝。由于 Protobuf 编码没有消息头预知子结构总大小的设计，解码器必须先把整块 100MB 的字节流完整读入一个连续的 `[]byte` 切片中才能开始 `proto.Unmarshal`，这会在 Go 的 `mheap` 中直接申请超过 32KB 的巨型大对象 span，对内存分配器和 GC 辅助标记造成剧烈冲击。

**代码示例**

```go
// 将大载荷按固定 64KB 切片为流式分块（Chunking），使单次 RPC 内存占用恒定为 O(64KB) 并实现平滑流控！
const DefaultChunkSize = 64 << 10 // 64KB：契合 HTTP/2 默认流控窗口与 Go 内存页大小

func SplitIntoChunks(data []byte, chunkSize int) [][]byte {
	if chunkSize <= 0 {
		chunkSize = DefaultChunkSize
	}
	if len(data) == 0 {
		return nil
	}
	n := (len(data) + chunkSize - 1) / chunkSize
	chunks := make([][]byte, 0, n)
	for i := 0; i < len(data); i += chunkSize {
		end := min(i+chunkSize, len(data))
		chunks = append(chunks, data[i:end])
	}
	return chunks
}

// 模拟基于信用窗口（Credit Window）的发送端流控器：体验 HTTP/2 WINDOW_UPDATE 背压控制逻辑
type FlowWindow struct {
	mu     sync.Mutex
	cond   *sync.Cond
	window int64
}
```

**常见追问**

- HTTP/2 既然号称解决了 HTTP/1.1 的队头阻塞，为什么在大消息或丢包场景下仍然有队头阻塞？→ HTTP/2 解决的是**应用层（HTTP 层）**的队头阻塞；但由于多个 Stream 复用了底层的**同一条 TCP 连接**，在 **TCP 传输层**：一旦发生 1 个 TCP 包丢失，内核 TCP 协议栈为了保证字节流严格有序，必须把后续已经收到的其他所有 Stream 的数据包全部卡在内核接收缓冲区里等待那个丢包重传成功（即 **TCP 层队头阻塞**）！同时在应用层如果单个大消息把 Connection-level 的流控窗口耗尽，也会阻塞同连接的其他 Stream。
- 在 `grpc-go` 中，哪些配置参数用来手动调大初始流控窗口（比如在跨国高延迟专线、BDP 极大的场景下）？→ 使用 `grpc.WithInitialWindowSize(size)`（设置单个 Stream 的初始窗口）和 `grpc.WithInitialConnWindowSize(size)`（设置整条连接的初始窗口）。
- gRPC 开启 Gzip 压缩后，怎么防范“压缩炸弹（Zip Bomb）”攻击？→ 攻击者可能发送一个压缩后只有 1MB（绕过了网络传输大小检查）、但解压后膨胀到 2GB 的恶意 Protobuf 包！`grpc-go` 的 `MaxRecvMsgSize(4MB)` 检查的是**解压后的字节大小**：在 `io.LimitReader` 解压过程中一旦超过 4MB 就会立即中断报错，不会把 2GB 全部解压到内存里。

**实战建议**

- 保持 gRPC 默认的 4MB（或最多放宽到 8MB～16MB）单消息上限作为安全护栏，强制促使团队将大批量导出和文件传输设计为分页查询、Streaming 流或对象存储外链。
- 跨机房高吞吐 gRPC 调用如果发现带宽跑不满，检查是否因 RTT 较高导致默认 64KB 初始流控窗口受限，可适当调大 `InitialWindowSize` 和 `InitialConnWindowSize` 到 1MB～4MB。

title: 什么是事务消息？如何利用事务消息或本地消息表实现可靠事件投递？
--- answer
在微服务中，最常见的需求是**“更新本地数据库”与“发送 MQ 消息通知下游”必须同时成功或同时失败**（例如：订单表插入成功，必须保证发出 `OrderCreated` 消息）。

先看**两种错误的直觉写法**：
- **先写库，在事务内（或提交后）直接发 MQ**：如果在事务提交前发 MQ，发完 MQ 后数据库提交失败（或发 MQ 卡住拉长了数据库事务锁），下游会收到幽灵消息；如果在事务提交后发 MQ，刚提交完进程崩溃或网络闪断，消息就永远丢了！

**两大工业级标准解决方案：**

**1. 本地消息表（Transactional Outbox Pattern，适用于任意 MQ 如 Kafka / RabbitMQ）**

```text
1. 在同一个本地数据库事务中：
   BEGIN;
   INSERT INTO orders (...);
   INSERT INTO outbox_messages (id, topic, payload, status='PENDING'); -- 同库同事务，100% 原子性！
   COMMIT;

2. 后台投递协程（Relay Worker）或监听 binlog（CDC 如 Debezium/Canal）：
   扫描 status='PENDING' 的记录 -> 发送给 Kafka -> 收到 Broker ACK 后更新为 status='SENT'
```

**2. RocketMQ 事务消息（两阶段提交 + 事务状态回查）**

当 MQ 本身原生支持事务消息时，无需自己建 `outbox` 表：
1. **第一阶段（发送半消息 Half Message）**：生产者先向 Broker 发送一条对消费者**暂时不可见**的“半消息”；
2. **执行本地事务**：半消息写入成功后，生产者开始执行本地数据库事务 `INSERT INTO orders`；
3. **第二阶段（Commit / Rollback）**：本地事务成功则向 Broker 发送 `Commit`（消息对消费者变为可见）；本地事务失败则发送 `Rollback`（Broker 直接删除半消息）；
4. **兜底回查（Transaction Check）**：如果生产者在第 3 步崩溃了，Broker 迟迟没收到确认，会定时主动回调生产者的 `CheckLocalTransaction(msg)` 接口，生产者去查本地数据库里这笔订单到底存不存在，据实返回 `Commit` 或 `Rollback`。
--- deep
**原理展开**

深入对比 **本地消息表（Outbox）** 与 **RocketMQ 事务消息** 的本质联系与边界条件：

1. **为什么无论用本地消息表还是 RocketMQ 事务消息，都只能做到 At-Least-Once（至少投递一次），消费者依然必须做幂等？**
   - 在本地消息表中：后台协程把消息发给 Kafka 已经成功了，但在准备执行 `UPDATE outbox_messages SET status='SENT'` 的瞬间进程崩溃了；重启后协程看到状态还是 `PENDING`，就会**再发第二次**；
   - 在 RocketMQ 事务消息中：半消息回查或网络超时重试同样可能触发重复投递。
   因此，**“发送端可靠投递（Outbox / 事务消息） + 消费端幂等去重（Idempotent Consumer）”** 合起来才是完整的最终一致性闭环！
2. **本地消息表的分库分表注意点**：
   `outbox_messages` 表必须和业务表 `orders` 位于**同一个物理数据库实例（分库分表时必须在同一个分片库）**中，这样它们才能共享同一个本地 ACID 事务，无需走昂贵的 XA 两阶段提交。

**代码示例**

```go
// Go 中实现本地消息表（Transactional Outbox）的核心写入与带退避的异步轮询投递器
type OutboxMessage struct {
	ID        int64
	BizKey    string
	Topic     string
	Payload   []byte
	Status    string // "PENDING", "SENT", "FAILED"
	RetryCnt  int
	NextRetry time.Time
}

// 第一步：业务写操作与写入 Outbox 消息表必须在同一个 *sql.Tx 本地事务中完成！
func CreateOrderWithOutbox(ctx context.Context, db *sql.DB, order Order, eventPayload []byte) error {
	tx, err := db.BeginTx(ctx, nil)
	if err != nil {
		return err
	}
	defer tx.Rollback()

	if _, err := tx.ExecContext(ctx,
		"INSERT INTO orders (order_no, user_id, amount) VALUES (?, ?, ?)",
		order.OrderNo, order.UserID, order.Amount); err != nil {
		return err
	}
	if _, err := tx.ExecContext(ctx,
		"INSERT INTO outbox_messages (biz_key, topic, payload, status) VALUES (?, ?, ?, 'PENDING')",
		order.OrderNo, "topic.order.created", eventPayload); err != nil {
		return err
	}
	return tx.Commit() // 原子提交：要么订单和待发消息都在库里，要么都不在！
}

// 第二步：即使进程在 Commit 后立刻断电，重启后 Relay 投递器也会把 PENDING 消息补发出去
```

**常见追问**

- 在本地消息表方案中，如果等后台定时任务每隔 1 秒去轮询数据库，消息投递岂不是有最多 1 秒的延迟？怎么做到毫秒级实时投递？→ **“内存即时触发 + 定时轮询兜底”双结合**！在 `tx.Commit()` 成功返回后的下一行，立即非阻塞地把这条消息扔进内存 channel 让投递协程**当场立即发送并标记 `SENT`**（99.99% 的情况下延迟 `< 2ms`）；后台定时轮询任务只扫“创建时间超过 5 秒仍处于 `PENDING`”的漏网之鱼，平时几乎不产生慢轮询压力！
- 在 RocketMQ 事务消息的回查接口 `CheckLocalTransaction` 中，如果此时本地数据库事务还在执行中（还没 Commit 也还没 Rollback），回查就已经到了怎么办？→ 返回 **`UNKNOW`（未知状态）**！Broker 收到 `UNKNOW` 后会等待一段时间（如 60 秒后）再次发起回查，直到本地事务尘埃落定（最多回查 15 次）。
- `outbox_messages` 表每天写入几千万条，表越来越大怎么清理？→ 已变成 `SENT` 状态且超过保留期（如 3 天）的历史记录，由后台归档任务按主键分批 `DELETE ... LIMIT 1000` 清理，或者按天建立分区表直接 `DROP PARTITION`。

**实战建议**

- 如果公司基础设施统一用 Kafka（原生不支持跨业务 DB 的回查式半消息），**“同库本地消息表 + 提交后异步即时触发 + 定时补偿扫描”** 是最稳健、最易维护的标准架构。
- Outbox 表中务必记录 `retry_count` 和 `next_retry_at`，超过最大重试次数（如 10 次）仍发不出去时状态改为 `FAILED` 并触发告警，避免把正常消息阻塞在后面。

title: 消息消费失败时如何设计重试队列与死信队列（DLQ）？
--- answer
在消费消息队列（Kafka / RocketMQ / RabbitMQ）时，如果因为下游暂时超时或某条消息本身格式有 bug（**“毒丸消息 / Poison Pill”**）导致消费失败，处理不当会产生两种极端事故：
- **原地死循环重试**：当前分区/队列被这一条毒丸消息死死卡住（Head-of-Line Blocking），后面几百万条正常消息全部积压；
- **直接忽略跳过**：本来只是下游闪断 1 秒钟就能恢复的正常业务消息被直接丢弃，造成资金或订单数据不一致。

**标准架构：分级延迟重试队列（Retry Topic） + 死信队列（Dead-Letter Queue，DLQ）**

```text
[主业务 Topic] ---> 消费者处理
                      |-- 成功 -> 提交 Offset / ACK
                      +-- 失败 -> 判断错误类型：
                            |-- 不可重试错误（如 JSON 格式损坏、业务校验明确拒绝） -> 直接投递【死信队列 DLQ】并 ACK
                            +-- 可重试错误（如 DB 锁冲突、下游网络超时）：
                                  |-- 第 1~N 次失败 -> 投递到【延迟重试 Topic】（按 1s, 5s, 30s, 5m 阶梯退避），
                                  |                   并立即 ACK 原主队列消息，不阻塞后续正常消息！
                                  +-- 超过最大重试次数（如 5 次） -> 投递【死信队列 DLQ】+ 落库告警
```

**死信队列（DLQ）的运维闭环：**
进入 DLQ 的消息必须携带**原始 Topic、原始分区/Offset、已重试次数、最后一次报错堆栈和业务 TraceID**，落盘到后台管理表中，支持值班研发修复 bug 或下游恢复后**一键重放（Replay）**。
--- deep
**原理展开**

深挖不同消息中间件在重试与死信实现机制上的差异，以及**顺序消息（Ordered Messages）遇到失败时的特殊矛盾**：

1. **RocketMQ / RabbitMQ vs Kafka 的原生能力差异**：
   - **RocketMQ** 原生为每个 Consumer Group 自动创建了 `%RETRY%<group>` 重试队列（内置 16 个延迟级别：10s, 30s, 1m, 2m ... 2h）和 `%DLQ%<group>` 死信队列，消费者只需返回 `ConsumeRetryLater` 即可自动进入阶梯延迟重试；
   - **Kafka** 是基于分区连续 Offset 日志的模型，它**不能跳过 Offset 100 先去确认 Offset 101**（只要提交了 101 就意味着 $\le 101$ 全部消费成功）。因此在 Kafka 中实现非阻塞重试，必须在应用层封装：**消费者把失败的消息附加 `x-retry-count` Header 主动 Produce 发送到专门的 `order.retry`（或 `order.dlq`）Topic，确认写入重试 Topic 成功后，立即 Commit 主 Topic 的 Offset 继续往前走**！
2. **顺序消息（同一订单 ID 的创建 -> 支付 -> 发货）的死锁矛盾**：
   如果业务严格要求同一个 `order_id` 的消息必须按顺序消费，那么当“订单创建”消息消费失败时，**绝对不能把它扔到异步重试队列然后继续消费后面的“订单支付”消息**（否则会先消费支付、后消费创建，顺序彻底乱套）！对于严格顺序消息，只能**在当前消费者本地做有限次数的带退避阻塞重试**，若仍失败则将整个相同的路由键（Sharding Key）关联的后续消息一并拦截转入挂起表。

**代码示例**

```go
// Go 中通用的 MQ 消费者重试与死信（DLQ）路由调度器
type Message struct {
	ID         string
	Key        string
	Payload    []byte
	RetryCount int
	LastError  string
}

type RetryPolicy struct {
	MaxRetries int
	Backoffs   []time.Duration // 例如 [1s, 5s, 30s, 2m]
}

// 返回动作：0=ACK成功，1=发往延迟重试队列，2=发往死信队列(DLQ)
func DispatchFailedMessage(msg Message, err error, isRetryable func(error) bool, policy RetryPolicy) (action int, delay time.Duration, updated Message) {
	updated = msg
	updated.LastError = err.Error()

	// 1. 不可重试的确定性错误（如数据格式损坏）或已达最大重试上限 -> 直接进死信队列 DLQ
	if !isRetryable(err) || msg.RetryCount >= policy.MaxRetries {
		return 2, 0, updated
	}

	// 2. 可重试错误：递增重试计数并计算当前阶梯的退避延迟时长
	updated.RetryCount++
	idx := min(updated.RetryCount-1, len(policy.Backoffs)-1)
	if idx >= 0 {
		delay = policy.Backoffs[idx]
	}
	return 1, delay, updated
}
```

**常见追问**

- 在 Kafka 中把失败消息转发到 `retry` Topic 再 Commit 原 Offset 时，如果转发 `retry` Topic 失败了怎么办？→ 必须等 `retry`（或 `dlq`）Topic 的同步 `Produce` 收到 Broker 确认（ACK）之后，才允许提交原主 Topic 的 Offset；如果连发往 Kafka 集群都失败了（说明 Kafka 本身不可用），则停止提交原 Offset 原地退避等待。
- 怎么在 Kafka 这种原生不支持任意延迟消息的 MQ 里实现“等待 30 秒后再消费 `retry` Topic”？→ 常见做法是按固定退避档位建几个重试 Topic（如 `retry-5s`、`retry-30s`、`retry-5m`）。消费 `retry-30s` 的协程每次读到一条消息时，检查消息头里的 `next_consume_time` 时间戳：如果还没到点，就调用 `Pause` 暂停该分区并 `time.Sleep(until)` 到点后再 `Resume` 消费（因为同一个 `retry-30s` 队列里的消息都是 +30s，天然按到期时间单调递增排好序了！Uber 开源的 Kafka 延迟重试架构正是基于此原理）。
- 死信队列（DLQ）里的消息重放（Replay）时需要注意什么？→ 重放前要先确认下游是否已经收到过更新版本的事件（避免旧状态覆盖新状态），因此消费者不仅要按 `message_id` 做幂等，最好还要校验业务数据的版本号 `version` 或事件时间戳。

**实战建议**

- 消费者代码里第一件事就是把错误分为 **`PermanentError`（永久错误，立即进 DLQ）** 和 **`TransientError`（临时错误，走退避重试）**：反序列化 JSON 失败重试 100 次也还是失败，一秒都不要浪费在重试队列上。
- 死信队列一旦有消息进入，必须立即触发告警通知（钉钉/飞书/PagerDuty），不能建了 DLQ 却没人看，变成“静默丢数垃圾桶”。

title: QUIC 协议是如何实现 0-RTT 建连和连接迁移（Connection Migration）的？
--- answer
**QUIC（RFC 9000，HTTP/3 的底层传输协议）** 是运行在 **UDP** 之上的新一代可靠安全传输协议，它在用户态重新实现了可靠传输、拥塞控制、多路复用和 TLS 1.3 加密，彻底解决了传统 TCP + TLS 的三大历史包袱：

**1. 极速建连：1-RTT 首次握手与 0-RTT 重连**

```text
传统 TCP + TLS 1.2 (3-RTT):          TCP + TLS 1.3 (2-RTT):          QUIC (首次 1-RTT / 重连 0-RTT):
Client              Server          Client              Server      Client                      Server
  |---- TCP SYN ----->|               |---- TCP SYN ----->|           |-- Initial (TLS ClientHello)->|
  |<--- SYN + ACK ----|               |<--- SYN + ACK ----|           |<- Initial + Handshake -------|
  |---- TCP ACK ----->| (1 RTT)       |-- ACK+ClientHello>| (1 RTT)   |-- 1-RTT 应用数据请求 ------->|
  |-- TLS ClientHello>|               |<- ServerHello+Fin-|
  |<- ServerHello ...-| (2 RTT)       |-- HTTP 请求数据 -->| (2 RTT)  (重连时携带上次会话 PSK 票据，
  |-- ChangeCipher -->|                                               第 1 个包就直接同时带上加密的 HTTP 请求，
  |<-- Finished ------| (3 RTT)                                       实现真正的 0-RTT 建连！)
```

- **原理**：传统协议中 TCP 三次握手（传输层）和 TLS 握手（安全层）是分先后串行进行的；而 QUIC **将传输层握手与 TLS 1.3 密码学握手合二为一**，首次建连只需 **1-RTT**；如果客户端之前连过该服务器并缓存了会话票据（Session Ticket / PSK），再次连接时第一个 UDP 包就能直接携带加密的业务请求数据（**0-RTT**）。

**2. 无感连接迁移（Connection Migration，如手机从 Wi-Fi 切换到 5G 蜂窝网络）**

- **TCP 的痛点**：TCP 连接由**四元组 `(源IP, 源端口, 目的IP, 目的端口)`** 唯一标识。当手机走出电梯从 Wi-Fi 切换到 5G 时，客户端的源 IP 和端口变了，原有的 TCP 连接瞬间失效断开，必须重新三次握手 + TLS 握手并重传请求；
- **QUIC 的解法**：QUIC 引入了与网络四元组解耦的 **64 位连接标识符 `Connection ID (CID)`**。当手机切换网络导致源 IP/端口改变时，客户端发出的 QUIC 包里依然带着相同的目标 `Connection ID` 并通过路径验证（`PATH_CHALLENGE` / `PATH_RESPONSE`），服务端一看 CID 没变，直接无缝继续收发数据，**连接不断开、音频视频通话零卡顿**！
--- deep
**原理展开**

深挖 QUIC 在安全性与传输机制上的三个核心设计考量：

1. **0-RTT 数据的致命安全隐患：重放攻击（Replay Attack）！**
   为什么 0-RTT 虽然快，但不能随便用于所有的请求？
   因为 0-RTT 数据包是在没有经过服务端最新随机挑战（ServerHello Random）的情况下直接用上次缓存的密钥加密发出的。如果中间人攻击者截获了这个 0-RTT UDP 数据包，并原封不动地向服务端**重放发送 10 次**，服务端在密码学上无法仅凭握手区分这是不是客户端新发的！
   因此 RFC 8446 / 9000 规定：**0-RTT（Early Data）只允许用于幂等的安全请求（如 `GET` 静态资源）**，严禁用于非幂等的转账、下单请求；且若服务端检测到重放风险，可返回 **HTTP `425 Too Early`** 状态码让客户端等待 1-RTT 握手完成后再重发。
2. **连接迁移时如何防止“连接标识符关联追踪（Linkability）”暴露用户隐私？**
   如果客户端在 Wi-Fi 和 5G 下一直使用完全相同的明文 `Connection ID`，路上的网络运营商就能轻易追踪到“原来这个 5G IP 就是刚才那个 Wi-Fi 用户”。为此 QUIC 在握手完成后，双方会通过加密帧预先协商备好**一组（多个）备用 `Connection ID` 和对应的重置令牌（Stateless Reset Token）**——当客户端切换到 5G 新网络时，立即换用池子里的下一个新 CID，只有服务端知道它们属于同一条连接，外部观察者完全无法关联！
3. **彻底消除队头阻塞**：QUIC 每个独立的 Stream 在丢包重传时，只阻塞当前这 1 个 Stream，其他 Stream 收到的数据包可以立即交付给上层应用，彻底解决了 HTTP/2 的 TCP 层队头阻塞。

**代码示例**

```go
// Go 中模拟 QUIC Connection ID 路由表与网络切换（Connection Migration）加上防追踪 CID 轮换机制
type QUICSession struct {
	SessionID   string
	ClientAddr  string   // 当前活跃的客户端 UDP IP:Port
	ActiveCIDs  []string // 预先协商分配给该连接的可用 CID 池
	MigratedCnt int
}

type QUICRouter struct {
	mu      sync.RWMutex
	cidMap  map[string]*QUICSession // CID -> Session（与客户端 IP:Port 四元组彻底解耦！）
}

func (r *QUICRouter) HandlePacket(cid string, srcAddr string, pathVerified bool) (*QUICSession, bool) {
	r.mu.Lock()
	defer r.mu.Unlock()
	sess, ok := r.cidMap[cid]
	if !ok {
		return nil, false
	}
	// 检测到客户端源 IP:Port 发生变化（例如 Wi-Fi 切换到 5G），且通过了 PATH_CHALLENGE 验证：
	// 直接将底层的发送目标地址切换为新的 srcAddr，上层连接状态毫发无损！
	if sess.ClientAddr != srcAddr && pathVerified {
		sess.ClientAddr = srcAddr
		sess.MigratedCnt++
	}
	return sess, true
}
```

**常见追问**

- 既然 QUIC 这么好，为什么很多企业内网或跨国机房里开启 QUIC（HTTP/3）后有时候反而连不上或比 TCP 慢？→ ① 很多老旧的企业防火墙、运营商 QoS 策略会对大流量的 **UDP 443 端口**进行限速甚至直接封禁（因此浏览器访问 HTTP/3 时都采用 `Alt-Svc` 升级 + **Happy Eyeballs 自动回退 TCP HTTP/2** 机制）；② 早期 Linux 内核对 UDP 的硬件网卡分流（GSO/GRO）优化不如 TCP 成熟，导致用户态收发 UDP 包的 CPU 开销高于内核态 TCP（新版 Linux 内核引入 `UDP_SEGMENT` / `UDP_GRO` 后已大幅追平）。
- Go 生态中用什么库实现 QUIC 和 HTTP/3？→ 最成熟的标准事实库是 **`github.com/quic-go/quic-go`**（包含 `http3.Server` 和 `http3.Transport`，Caddy 和 Cloudflare 均重度使用），直接实现了标准库的 `http.RoundTripper` 接口。
- 什么是 `PATH_CHALLENGE` 和 `PATH_RESPONSE` 帧，为什么连接迁移时必须要发它？→ 为了**防止源 IP 欺骗与反射放大攻击（IP Spoofing Amplification）**！如果攻击者伪造受害者的 IP 地址向服务端发一个带合法 CID 的小包，服务端如果不验证新地址的真实性就立刻往这个假 IP 狂发几 MB 的视频流，就会变成 DDoS 反射器。因此服务端发现源地址变化后，会向新地址发一个带 8 字节随机数的 `PATH_CHALLENGE`，只有客户端能从新地址原样回传 `PATH_RESPONSE`，才证明客户端真的拥有该新 IP。

**实战建议**

- 在移动端 App 弱网优化（地铁、电梯、Wi-Fi/蜂窝切换频繁场景）中，接入 HTTP/3（QUIC）通常能将网络报错率和重连耗时降低 30%～50%。
- 若服务端开启了 TLS 1.3 0-RTT Early Data，网关或中间件必须拦截非安全方法（如 `POST / PUT / DELETE`）的 0-RTT 请求并返回 `425 Too Early`，严防重放攻击。
