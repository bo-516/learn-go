title: 如何设计一个高可用的配置中心？长轮询（Long Polling）实时推送是怎么实现的？
tags: 配置中心, 长轮询, 高可用, Apollo, Nacos
tasks: arch-21-1
--- answer
高可用配置中心的核心矛盾是：**变更推送要秒级生效（实时性）**，同时**配置中心全挂时业务进程仍能正常启动和运行（高可用容灾）**。

**1. 推拉结合：HTTP 长轮询（Long Polling）机制**
- **为什么不用短轮询？** 每秒轮询一次会有大量无效空请求，压垮服务端；每分钟轮询一次又会导致变更延迟高达 60 秒。
- **为什么不直接用 TCP/WebSocket 长连接？** 容易穿透内网防火墙/七层代理超时断开，且重连状态管理重。
- **HTTP 长轮询（Apollo / Nacos 核心方案）**：
  1. 客户端发起 HTTP GET 请求，携带本地配置版本号 `version`。
  2. 服务端比对当前最新版本号：
     - 如果服务端版本号 **大于** 客户端 `version`，**立即返回**最新配置；
     - 如果版本号一致（未发生变更），服务端**不立即响应，而是将该请求挂起（Hold）在内存的等待队列（如 Go 的 `chan struct{}` 广播通道）中**，最长等待 30 秒。
  3. 在这 30 秒挂起窗口内，一旦管理员发布了新配置，服务端立刻唤醒所有等待队列中的请求，实时返回新版本（毫秒级送达）；若 30 秒内无变更，返回 `304 Not Modified`，客户端立刻发起下一轮长轮询。

**2. 客户端四级容灾（保证配置中心挂了业务不挂）**
1. **内存缓存（`atomic.Pointer`）**：业务代码读取配置是纯内存无锁操作，绝不发起网络请求。
2. **長轮询实时更新 + 定时全量兜底拉取（如每 5 分钟一次）**：防止极端网络闪断漏掉某次通知。
3. **本地磁盘快照（Local File Snapshot）**：每次拉取成功都原子写入本地磁盘（Write Temp + Rename）。当配置中心集群全挂且业务容器重启时，直接读取本地磁盘快照启动！
4. **代码默认值兜底**。
--- deep
### 为什么配置中心是线上事故的高发区？

一次错误的配置变更（比如把超时时间从 `500ms` 改成 `500s`，或者写出非法 JSON）通过长轮询在 100 毫秒内推送到全集群 5000 台机器，破坏力比发版代码大得多（发版通常有 10% 灰度，而配置很多时候是全量广播）。

```
┌──────────────┐   1. Watch(ver=5, timeout=30s)   ┌──────────────────────┐
│              │ ───────────────────────────────► │  Config Server       │
│  App Client  │                                  │  (ver==5: 挂起 chan) │
│  (内存+落盘) │ ◄─────────────────────────────── │                      │
└──────────────┘   2. 一旦发布 ver=6 立即唤醒返回 └──────────────────────┘
                                                             ▲
                                                             │ 2. Publish(ver=6)
                                                       ┌─────┴─────┐
                                                       │ 灰度/管理 │
                                                       └───────────┘
```

### 生产级配置中心的三大工程铁律

1. **用 `close(notifyCh)` 实现零锁百万级广播**：
   在 Go 中实现长轮询挂起队列时，最优雅的做法是在当前版本维护一个 `notifyCh chan struct{}`。所有来 `Watch` 的协程拿到当前的 `notifyCh` 后直接 `select { case <-notifyCh: ... case <-ctx.Done(): ... }`。当管理员 `Publish` 新版本时，加锁更新数据并直接 `close(oldNotifyCh)`，再新建一个 `notifyCh`。利用 Go **关闭 channel 会瞬间唤醒所有等待在它上面的接收协程**的语言特性，无需遍历连接列表逐个发送！
2. **客户端惊群打散（Jitter）**：
   如果某热门配置（被 5000 个实例监听）发布了新版本，`close(notifyCh)` 瞬间唤醒 5000 个长轮询请求。如果长轮询只返回通知信号（如 Apollo 只推 notificationId，客户端再调拉取接口），客户端必须在发起拉取前加上 `0~500ms` 的随机抖动，防止瞬间打爆服务端带宽。
3. **灰度发布与一键回滚**：
   所有配置变更必须保留完整的版本历史表（审计日志 + Diff），支持先推送给 1~2 台金丝雀机器验证无误后再全量发布。

title: 如何设计一个分布式定时任务调度系统？如何避免任务重复执行和单点故障？
tags: 分布式调度, 定时任务, 时间轮, 分片广播, 幂等
tasks: arch-22-1
--- answer
单机 `crontab` 或进程内 `time.Ticker` 在多副本集群下面临两个致命问题：**单点故障（机器挂了任务停了）**和**多副本重复执行（10 台机器在同一秒同时发了 10 份对账单）**。

**1. 整体架构（调度器与执行器分离，如 XXL-JOB / ElasticJob）**
- **调度中心（Scheduler Cluster）**：无状态多节点部署，负责解析 Cron 表达式、触发调度时机，并把任务派发给业务执行器。
- **业务执行器（Worker Cluster）**：集成在业务服务中的 SDK，接收调度请求、执行具体业务逻辑并回传执行结果。

**2. 调度中心如何避免重复触发与单点故障？**
- **数据库行锁抢占（中小规模，QPS < 1000）**：多台调度器扫描即将到期的任务前，先对数据库锁表执行 `SELECT ... FOR UPDATE`（或基于乐观锁更新 `trigger_next_time`：`UPDATE job SET next_time = ? WHERE id = ? AND next_time = ?`），抢到锁或 CAS 更新成功的节点才发起远程调用。
- **时间轮（Timing Wheel）+ 分片 Leader 选举（大规模）**：通过 Etcd/ZooKeeper 将任务按 `job_id % N` 分片给不同的调度节点，由时间轮在内存中高效推进，节点宕机时由租约过期自动漂移给其他节点接管。

**3. 阻塞与过期策略与分片广播**
- **单机串行 / 丢弃后续 / 覆盖之前**：如果定时任务每分钟触发一次，但上一次执行耗时 3 分钟还没跑完，执行器必须根据策略拒绝并发重入或排队。
- **分片广播（Sharding Broadcast）**：扫表处理 1000 万条到期订单时，一台 Worker 跑太慢。调度中心向全部 $N$ 台存活 Worker 广播触发，同时下发各自的 `(shardIndex, shardTotal)`（如 `0/3, 1/3, 2/3`），每台 Worker 执行 `WHERE id % shardTotal = shardIndex`，实现无锁水平扩容！
--- deep
### 为什么有了调度锁，业务任务依然必须做幂等？

很多工程师以为：“既然调度中心已经用了分布式锁保证同一周期只触发一次，我的业务代码就不需要考虑幂等了。”——这是大错特错的！

考虑以下两类必然发生的异常：
1. **网络超时重试（Ack 丢失）**：调度中心调 Worker A 触发任务，Worker A 已经在跑了，但由于网络抖动响应超时，调度中心以为 Worker A 挂了，立刻故障转移（Failover）調用 Worker B，此时 A 和 B 并发执行同一个周期的任务。
2. **进程级时钟偏移或锁过期**：调度节点 GC 停顿或数据库慢查询导致锁超时释放。

```
调度中心触发时携带唯一幂等号：fireKey = "job_42:2026-05-01T10:00:00Z"
Worker 落库/执行前校验：INSERT INTO job_execution_log (fire_key, status) VALUES (...) ON CONFLICT DO NOTHING
```

### 大任务分片广播（MapReduce 思想）

当一个定时任务需要处理百万级数据（如凌晨 2 点全量结算昨日收益）时：
1. **严禁单线程大事务全表扫描**。
2. 利用分片参数 `shardIndex`（当前机器序号 `0..N-1`）和 `shardTotal`（总存活机器数 `N`）：
   - Worker `i` 只捞取 `mod(user_id, shardTotal) == shardIndex` 的数据；
   - 如果某台 Worker 执行中途宕机，调度中心感知心跳断开后，针对失败的分片单独触发重跑，结合业务侧的按天/按周期唯一状态位，既跑得快又能安全断点续传。

title: MySQL 数据如何实时同步到 Elasticsearch？如果出现乱序或延迟怎么保证最终一致？
tags: MySQL, Elasticsearch, Binlog, CDC, 最终一致性
tasks: arch-23-1
--- answer
将 MySQL 数据实时同步到 Elasticsearch（用于全文检索或多维复杂筛选）的核心要求是：**业务无侵入、准实时（秒级延迟）、乱序免疫（最终强一致）**。

**1. 四种同步方案对比**
1. **业务代码同步双写**：写完 MySQL 直接写 ES。强耦合、写耗时翻倍、部分失败导致数据永久不一致，**严禁在核心链路使用**。
2. **业务发 MQ 异步消费**：解耦了性能，但业务代码仍需散落发消息逻辑，且容易漏发。
3. **定时任务扫 `updated_at` 字段**：有分钟级延迟，无法感知物理删除（`DELETE`），且扫表对主库有压力。
4. **Binlog CDC 订阅（Canal / Debezium + Kafka，业界标准方案）**：
   - Canal 伪装成 MySQL 从库拉取 `ROW` 格式的 Binlog，解析出变更前后的完整行数据投递到 Kafka；
   - 同步 Worker 消费 Kafka 并批量写入（`Bulk API`）Elasticsearch，与业务代码完全解耦。

**2. 如何解决并发与重试导致的乱序覆盖问题？（核心考点）**
哪怕 Kafka 按主键 Hash 到了同一个分区，在遇到**全量初始化与增量同步交叉**、或者 **Bulk 部分失败重试**时，旧版本的变更仍可能晚于新版本到达 ES！
- **解法：使用外部版本号（`version` + `version_type=external`）**
  - 在 MySQL 表中维护单调递增的业务字段（如 `version` 乐观锁版本号，或毫秒级时间戳+自增位 / Binlog GTID 位点转换值）。
  - 写入 ES 时携带 `?version=<mysql_version>&version_type=external`。
  - ES 内部会原子比对：只有当传入的 `version` **严格大于** ES 当前文档已存储的 `_version` 时才允许写入；如果是迟到的旧版本数据，ES 直接返回 `409 Version Conflict`，消费端捕获并忽略该冲突即可，天然免疫一切乱序！
--- deep
### 存量全量迁移与增量同步如何无缝衔接（零停机）？

新建一个 ES 索引同步一张已有 5000 万行的 MySQL 表时，如果先跑全量脚本再开增量消费，中间脱节的数据会丢失；如果同时跑，全量读出的旧数据又可能覆盖掉增量刚写入的新数据！

```
时间轴 ──►
1. 记录当前 Binlog 位点 P0，启动 Canal 将 P0 之后的增量写入 Kafka（先积压不消费，或直接开启带 external version 的消费）
2. 开启全量扫表脚本（按主键 id 游标分页读取 MySQL），携带 version_type=external 写入 ES
3. 全量跑完后，增量消费持续追平 Kafka 积压
```

只要全量写入和增量写入**统一使用 `version_type=external`**（以数据行的 `version` 字段为准）：
- 假如增量先把 `id=100, version=5` 写进了 ES；
- 随后全量游标扫到了旧快照 `id=100, version=4` 并尝试写入 ES；
- ES 发现 `4 <= 5`，直接拒绝全量的旧覆盖（返回 409 Conflict），数据毫发无损！

### 生产调优与巡检对账

1. **ES Bulk 攒批写入**：绝对不能一条 Binlog 发一次 ES HTTP 请求（ES 单次 Refresh 开销极大）。消费端必须用 `Batcher`（例如每凑够 500 条或每 200ms 触发一次 ` Bulk` 批量请求）。
2. **离线/准实时对账补偿（Reconciliation）**：没有任何流式管道能保证 100% 不丢消息。生产上必须配一个定时巡检任务，对比近 10 分钟 MySQL `updated_at` 变更的主键列表与 ES 中的 `_version`，发现不一致自动回源 MySQL 重刷修复。

title: 如何设计一个支撑亿级并发读写的计数系统（如点赞数、播放量、未读数）？
tags: 系统设计, 计数系统, 写聚合, Redis, 高并发
tasks: arch-24-1
--- answer
微博/短视频场景下的计数系统（播放量、点赞数、评论数、转评赞汇总）具有极端的读写特征：**读写比都极高（大 V 发博瞬间每秒数十万次点赞写 + 数百万次刷屏读）**。

**1. 为什么直接 `UPDATE mysql` 或单 Key `INCR redis` 不行？**
- 直接 `UPDATE post SET like_cnt = like_cnt + 1 WHERE id = 100`：行锁竞争会导致数据库在几百 QPS 下就彻底卡死。
- 直接对单个 Redis Key 执行 `HINCRBY`：当单 Key QPS 超过 10 万时，该 Key 所在的单个 Redis 分片 CPU 会被打到 100%（热点 Key 问题）。

**2. 写路径：内存缓冲聚合（Write-Behind Batching）**
- **进程内微批聚合（Local Aggregator）**：业务网关或计数服务收到点赞/播放事件后，不立即写 Redis/DB，而是写入进程内的分片哈希表，每隔 `100ms ~ 500ms`（或攒满阈值）将同一个 `target_id` 的增量合并为一次 `delta`（例如 100ms 内 5000 次播放合并为一次 `+5000`），将后端写压力直接削减 **2~3 个数量级**！
- **Kafka 削峰 + 流式聚合**：对于需要持久化的精确计数，先发 Kafka，由消费 Worker 在内存中按窗口聚合后批量 `INSERT ... ON DUPLICATE KEY UPDATE cnt = cnt + VALUES(cnt)` 落库，同时更新 Redis。

**3. 读路径与存储压缩优化**
- **多级缓存**：热点大 V 的计数通过本地缓存（1~2 秒短 TTL）挡住 99% 的读流量，绝不穿透到 Redis。
- **紧凑编码合并存储**：一篇文章往往有多个维度计数（阅读、点赞、评论、收藏、转发）。不要拆成 5 个独立的 Redis String Key（Key 元数据开销比 8 字节整数大 10 倍），而是打包成固定字节数组或小型 Hash（配合 `hash-max-listpack-entries` 压缩）紧凑存储。
--- deep
### 区分“模糊计数”与“精确带去重计数”

面试回答计数系统设计题时，第一步一定要先向面试官确认业务类型：

| 计数类型 | 典型场景 | 核心诉求 | 架构设计要点 |
| :--- | :--- | :--- | :--- |
| **模糊累加计数** | 视频播放量、帖子浏览量（PV） | 吞吐量极大、允许秒级延迟和极少量丢失、不需要去重 | 网关层内存 Buffer 聚合（每 500ms 批量 `INCRBY`），异步落库 |
| **精确去重计数** | 点赞数、收藏数 | 严禁重复点赞（幂等）、需要判断当前用户是否已赞（`is_liked`） | 先经过点赞关系存储（Redis Set/ZSet/Bitmap 或分库分表唯一索引）校验去重成功，再触发计数器 `+1/-1` |
| **强一致配额计数** | 秒杀库存、优惠券余量 | 严禁超卖、不能为负数 | Redis Lua 原子预扣减 + 异步事务落库 |

```
[每秒 50万次播放请求]
       │
       ▼
┌────────────────────────────┐
│ 计数节点内存 Buffer        │  map[itemID]int64
│ ("video:888" += 1)         │  100ms 窗口内合并 5000 次请求
└──────────────┬─────────────┘
               │ 每 100ms Flush 一次 (+5000)
               ▼
┌────────────────────────────┐
│ Redis Cluster & MySQL DB   │  写 QPS 从 500,000 降至 200！
└────────────────────────────┘
```

### 优雅停机（Graceful Shutdown）防丢数据

使用进程内内存聚合缓冲（Write-Behind）时，最关键的工程细节是：**当容器收到 `SIGTERM` 准备滚动重启时，必须先停止接收新请求，并调用 `Flush()` 将内存 Buffer 中尚未到期的余量全部刷入下游存储后才能退出**，否则每次发版都会丢掉最后几百毫秒的计数。

title: 如何设计一个全平台消息通知与推送系统（站内信、邮件、短信、App Push）？
tags: 系统设计, 消息推送, 读扩散, 写扩散, 渠道网关

--- answer
全平台通知系统需要解决两个层面的核心问题：**多渠道外部推送的可靠性与限流（短信/邮件/Push）**，以及**站内信（Inbox）个人点对点与全员公告的存储模型**。

**1. 统一通知网关（多渠道编排、去重、频控、降级）**
1. **模板与业务解耦**：业务方只传 `template_id`、`user_id`、`params` 和幂等 `request_id`，不知道底层用的是阿里云短信还是腾讯云短信。
2. **多级优先级队列（Kafka Topic 物理隔离）**：
   - **高优实时队列（P0）**：验证码、支付扣款提醒，独占消费集群，保障 1 秒内触达；
   - **普通通知队列（P1）**：物流状态变更、评论回复；
   - **营销群发队列（P2）**：促销活动推送，严格限速且避开夜间免打扰时段（22:00~08:00）。
3. **防疲劳频控（Fatigue Control）与供应商主备自动切换**：
   - 限制同一用户每天最多收 N 条营销通知；
   - 当主通道（如供应商 A）超时率或失败率超标时，滑动窗口断路器自动将流量切往备用供应商 B。

**2. 站内信存储：写扩散（Push）与读扩散（Pull）结合**
- **点对点私信/个人通知（写扩散）**：直接写入接收者的收件箱表 `user_inbox (user_id, msg_id, is_read)`。
- **全员系统公告/千万粉丝大 V 通知（读扩散）**：如果给 5000 万用户每人插入一条收件箱记录，数据库会被瞬间写爆！正确做法是：只往公共广播表 `broadcast_msg (msg_id, content, created_at)` 写 **1 条**记录；当活跃用户打开站内信列表时，根据用户上次拉取游标 `last_broadcast_id`，将 `broadcast_msg` 中新增的公告实时合并（或懒加载同步）到个人收件箱中。
--- deep
### 站内信“未读数红点”与全员公告的工程实现

在读扩散 + 写扩散混合模型下，用户登录 App 首页时需要极速展示“未读消息总数（红点）”：

```
用户个人维度维护两个游标/计数器（存储在 Redis Hash `unread:{uid}`）：
1. personal_unread: 个人私信/通知未读数（每次写扩散插入时 HINCRBY +1，已读时扣减）
2. last_ack_broadcast_id: 用户上次拉取/已读到的最大全员公告 ID

全站维护一个全局有序列表（缓存于各节点内存）：
global_broadcasts: [ {id: 101, time: ...}, {id: 105, time: ...}, {id: 108, time: ...} ]
```

当用户请求首页未读红点时：
- 总未读数 = `personal_unread` + `count(global_broadcasts where id > last_ack_broadcast_id and id > user_register_time_id)`。
- 既不需要在发全员公告时写 5000 万次 Redis，又能让在线用户在毫秒级算出准确的个人总未读数！
- 当用户真正点击进入“消息列表”时，再把 `id > last_ack_broadcast_id` 的公告懒写入（Lazy Materialize）用户的个人收件箱并推进 `last_ack_broadcast_id`。

=== arch-26
cat: arch
group: 治理
level: 3
title: 如何设计一个集群级的分布式全局限流系统？如何兼顾性能与精确度？
tags: 分布式限流, 令牌桶, 本地预取, Redis, 微服务治理
tasks: arch-26-1
--- answer
在网关或微服务集群（比如 200 个 Pod）中保护下游核心依赖或限制租户 API 配额时，面临一个两难困境：
- **纯单机限流**：每台机器配额 `total / N`。一旦扩缩容或机器间负载不均，配额极不准确。
- **纯集中式 Redis Lua 限流**：每次请求都调一次 Redis Lua 脚本。如果全局限流阈值是 50 万 QPS，意味着每次业务请求都要增加 1ms RTT，且单个限流 Key 会把 Redis 单个分片彻底打爆！

**业界标准解法：本地批量预取令牌 + 远端中心配额池（Token Batch Lease，如 Sentinel 集群限流 / Envoy Global Rate Limit 进阶方案）**

**1. 核心工作流程**
1. **中心配额池**：Redis（或独立限流 Server）维护全局每秒总配额（如 `10000 QPS`）。
2. **客户端本地预取（Batch Acquire）**：每个业务节点内部维护一个本地令牌桶。当本地令牌耗尽时，不再每次只向 Redis 申请 `1` 个令牌，而是**一次性批量申请一批令牌（如 `batch = 50` 个）**，缓存在本地内存中。
3. **本地零网络开销扣减**：后续的 49 次业务请求直接在进程内原子扣减本地缓存的令牌，耗时仅 **几十纳秒**，将对中心 Redis 的请求量直接降低了 **50 倍**！

**2. 边界处理与高可用降级**
- **令牌过期作废**：本地预取的令牌批次带有窗口过期时间（如当前秒结束即作废），防止空闲节点囤积大量旧令牌在下一秒瞬间释放造成毛刺。
- **动态批次大小**：剩余配额充足时按 `batch` 预取；当中心池余量不足 `batch` 时，返回实际剩余量（甚至降级为逐个申请）。
- **故障自动降级（Fallback）**：一旦中心 Redis 超时或宕机，节点立刻无缝切换为按 `全局总配额 / 预估节点数` 的**本地单机限流模式**，绝不因为限流组件故障导致业务中断。
--- deep
### 集中式限流 vs 本地批量预取的性能账本

假设某大型 API 网关集群有 100 个节点，要对某个大客户做全局 `100,000 QPS` 的限流控制：

| 维度 | 每次请求调 Redis Lua | 本地批量预取（Batch = 100）+ 远端中心池 |
| :--- | :--- | :--- |
| **Redis 承受 QPS** | `100,000 QPS`（单分片接近极限） | **`1,000 QPS`**（降低 99%） |
| **业务请求 P99 延迟开销** | 每次增加 `0.5ms ~ 2ms` 网络 RTT | 99% 请求纯内存操作（`< 50ns`） |
| **最高理论误差（超发/少发）** | 0（绝对精确） | 窗口边界最多浪费 `节点数 × Batch`（可通过自适应调小尾批消除） |

```
[业务请求] ──► 检查本地缓存令牌 (localTokens > 0 且未跨时间窗口?)
                 ├── 是 ──► localTokens-- 立即放行 (0 网络 RTT)
                 └── 否 ──► 向中心配额池申请 min(batchSize, 远端剩余配额)
                              ├── 申请到 K 个 (K > 0) ──► 消耗 1 个，剩余 K-1 个存入本地
                              ├── 远端返回 0 ──────────► 触发 429 限流拒绝
                              └── 远端网络报错 ────────► 降级为本地单机限流兜底
```

这种**“把分布式高频同步转化为分批租借（Lease / Batch Allocation）”**的思想，不仅用于分布式限流，在**分布式发号器（美团 Leaf 号段模式）**和**高并发库存预分配**中也是完全相通的核心架构范式。

=== arch-27
cat: arch
group: 设计题
level: 3
title: 历史订单表数据量达到百亿级，如何设计冷热数据分离与归档方案？
tags: 冷热分离, 数据归档, 分库分表, TiDB, 对象存储
tasks: arch-27-1
--- answer
电商或支付系统的订单表随着时间推移会无限膨胀。当数据量达到百亿级时，如果冷热数据混存在昂贵的在线 OLTP 数据库（SSD 高配 MySQL）中，不仅存储成本高昂、B+ 树层级加深拖慢在线交易，还会导致 DDL 变更和备份恢复无法进行。

**1. 区分冷热边界**
- **热数据（Hot Data）**：近 3 个月内创建、或者状态仍未终结（如“待支付”、“配送中”、“售后中”）的订单，占总访问量的 **95% 以上**，留在在线 MySQL 主库。
- **温/冷数据（Cold Data）**：创建时间超过 3 个月且已进入终态（“已完成”、“已关闭”）的历史订单，仅用于用户偶尔翻看年度账单或客服核查，迁移至低成本大容量存储（如 TiDB、ClickHouse、HBase 或带二级索引的归档库 / Parquet 对象存储）。

**2. 平滑归档流水线（严禁大事务 `DELETE`）**
1. **游标小批次扫描**：按主键或时间索引每批扫描 500 条满足冷数据条件的终态订单。
2. **幂等写入冷库 + 校验**：先将这 500 条订单 `UPSERT` 写入冷存储，并校验写入行数与关键字段摘要一致。
3. **小批次限速删除热库**：从热库按主键删除这 500 条记录（`DELETE FROM orders WHERE id IN (...)`），每批之间 `sleep` 或动态监控主从复制延迟（`Seconds_Behind_Master`），一旦从库延迟升高立刻暂停降速。
4. **表空间碎片整理**：大量 `DELETE` 只会将 InnoDB 页标记为可复用而不会归还磁盘空间，需按月/按季用分区表直接 `DROP PARTITION`（最推荐！）或在低峰期用 `gh-ost` 重建表回收空间。

**3. 透明查询路由（Federation Query）**
查询层封装统一的 `OrderRepository`：
- 按单号查询（单号内嵌时间戳）：直接解析单号中的时间位，精准路由到热库或冷库；
- 按用户分页查列表：优先查热库（前几页 99% 在热库），当热库返回条数不足 `pageSize` 或游标时间跨越了 3 个月分界线时，自动拼接冷库查询结果。
--- deep
### 为什么按时间范围分区（Range Partition）是冷热归档的神器？

如果单表或分库分表内部配合了按月分区（或按月分表 `orders_202601`）：
- **用 `DELETE` 删 1 亿条旧数据**：会产生海量的 Undo Log 和 Binlog，打满磁盘 IOPS，引发严重的主从延迟，且文件大小不变（产生大量表空间洞）。
- **先把未完结的极少数非终态老订单捞出迁移，然后直接 `DROP PARTITION`**：属于文件系统级的元数据删除操作，秒级释放数十 GB 磁盘空间，零页碎片，零主从复制风暴！

### 冷热联邦分页游标（Cursor Pagination across Hot & Cold）

当用户在 App 里一直往下滑动“我的订单”跨越 3 个月分界线时，如何做到无缝衔接、不重不漏？

```
请求：ListOrders(userID, cursorTime, limit=10)
  ├── 1. 若 cursorTime > cutoffTime (还在热数据时间段内):
  │      先查 HotStore(time < cursorTime, limit=10) -> 得到 K 条
  │      ├── 若 K == 10: 直接返回这 10 条
  │      └── 若 K < 10 : 说明热库已见底，用 (limit = 10 - K) 继续查 ColdStore 补齐！
  └── 2. 若 cursorTime <= cutoffTime (已经滑到了冷数据时间段):
         直接只查 ColdStore(time < cursorTime, limit=10)，无需再碰热库！
```

同时，为了应对极少数“6 个月前下单但至今仍未完结/刚发起售后”的特例，若按单号查热库未命中，读路径只需多做一次 Fallback 回源冷库（配合布隆过滤器防穿透），即可对业务上层完全透明。
