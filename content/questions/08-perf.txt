title: 线上报警磁盘空间满（No space left on device），但 du 统计文件总和却很小，怎么排查？
tags: Linux, 磁盘满, Inode, 已删除未释放文件, lsof
tasks: perf-29-1
--- answer
这是 Linux 线上运维中最经典的两大磁盘陷阱，按以下两步可在 30 秒内定位根因：

**情况一：`df -h` 显示磁盘容量 100%，但 `du -sh /*` 加起来只有几个 GB（相差几十 GB）**
- **根因**：**大文件（如几十 GB 的日志）被直接 `rm` 删除了，但仍被某个运行中的进程（如业务进程或日志采集 Agent）持有打开的文件描述符（fd）**！
  - 在 Linux VFS 中，`rm` 只是调用 `unlink()` 移除了目录项并将 Inode 的硬链接计数（`i_nlink`）减为 0，所以 `du` 遍历目录树时看不到它；
  - 但只要内核中还有进程持有该文件的打开句柄（引用计数 `i_count > 0`），操作系统就**绝对不会回收该文件占用的磁盘块**，所以直接读取文件系统超级块统计的 `df -h` 依然显示 100% 满！
- **定位命令**：`lsof +L1`（或 `lsof | grep deleted`），找出持有 `(deleted)` 大文件的进程 PID 和 fd。
- **正确恢复**：
  - 以后清理正在写入的大日志时，**严禁直接 `rm`**，而应该用 `truncate -s 0 app.log` 或 `: > app.log` 原地截断清空；
  - 若文件已被 `rm`，而又不能立刻重启业务进程，可执行 `: > /proc/<PID>/fd/<FD>` 直接通过 procfs 截断该匿名 Inode 瞬间释放磁盘空间！

**情况二：`df -h` 显示磁盘容量才用了 20%，却依然报 `No space left on device`**
- **根因**：**Inode 耗尽（`df -i` 显示 `IUse% = 100%`）**！例如定时任务、缓存目录或未清理的临时会话生成了数百万个几字节的零碎小文件，把文件系统的 Inode 号分配光了，导致无法创建任何新文件。
- **定位命令**：`df -i` 确认 Inode 满，再用 `find / -xdev -printf '%h\n' | sort | uniq -c | sort -k 1 -nr | head -20` 找出包含小文件最多的目录并分批清理（用 `find dir -type f -delete`，避免 `rm *` 报 `Argument list too long`）。
--- deep
### 为什么 `rm` 不会立刻释放磁盘空间？（Linux VFS 引用计数双条件）

Linux 内核决定是否真正释放一个文件占用的磁盘数据块（Data Blocks）和 Inode，必须**同时满足两个计数归零**：

```
                  ┌──────────────────────────────────────────┐
                  │             Linux VFS Inode              │
                  │  1. i_nlink (目录硬链接数): rm 将其减 1  │
                  │  2. i_count (内存打开句柄数): close 减 1 │
                  └────────────────────┬─────────────────────┘
                                       │
            只有当 i_nlink == 0 且 i_count == 0 时，才真正释放磁盘块！
```

当运维同学看到 `/var/log/app.log` 有 80GB，随手敲了 `rm -f /var/log/app.log`：
1. `i_nlink` 从 1 变成 0，文件名从目录树中消失，`ls` 和 `du` 再也看不见它；
2. 但 Go 业务进程的 `os.File` 依然打开着它（`i_count == 1`），并且还在源源不断地往这个“幽灵文件”里 `write()` 追加日志；
3. 磁盘空间一字节都没释放，甚至还在继续涨！

### 在不重启进程且已 `rm` 的绝境下如何瞬间救火？

假设线上核心交易进程不能重启，而 80GB 的日志文件已经被误 `rm` 了：
1. 执行 `lsof +L1` 找到该进程 PID（如 `12345`）和对应的文件描述符 FD（如 `4w`）；
2. 执行截断指令：
   ```bash
   truncate -s 0 /proc/12345/fd/4
   ```
   内核会直接将 `/proc/<pid>/fd/<fd>` 指向的底层 Inode 长度截断为 0，80GB 磁盘空间在 100 毫秒内原地满血释放，且业务进程毫发无损！

title: 线上偶发请求超时，排查发现是 DNS 解析慢（5 秒毛刺），是什么原因？如何解决？
tags: DNS, Kubernetes, CoreDNS, ndots, Conntrack, Go
tasks: perf-30-1
--- answer
在 Kubernetes 容器环境或高并发 Linux 服务器上，“DNS 解析偶发 5 秒毛刺（5000ms）”是一个极其高频的经典线上疑难杂症。为什么刚好是 **5 秒**？因为 Linux `/etc/resolv.conf` 默认的 DNS 超时重试时间（`timeout:5`）正好是 5 秒！

**三大常见根因与排查**

**1. K8s 默认 `ndots:5` 引发的 4~5 倍冗余 DNS 查询放大**
- K8s Pod 默认的 `/etc/resolv.conf` 包含：
  `search default.svc.cluster.local svc.cluster.local cluster.local`
  `options ndots:5`
- **原理**：当请求域名中的点号 `.` 少于 5 个（例如调外部接口 `api.weixin.qq.com`，只有 3 个点）时，解析器会认为它是集群内部短域名，**依次拼接所有的 `search` 后缀去查一遍（每次还并发查 A 记录 IPv4 和 AAAA 记录 IPv6）**！前 6 次全返回 `NXDOMAIN`，最后才查真正的 `api.weixin.qq.com.`，把 CoreDNS 的 QPS 放大了近 10 倍。

**2. Linux 内核 UDP `nf_conntrack` 并发竞态丢包（正好卡 5 秒！）**
- DNS 默认使用 UDP 协议。当同一个客户端并发发起 A（IPv4）和 AAAA（IPv6）两个 UDP DNS 请求时，在开启了 `netfilter`（如 kube-proxy iptables 模式）的节点上，两个 UDP 包可能同时到达内核并尝试插入同一条 `conntrack` 表项；
- 后者在 CAS 冲突中直接被内核静默丢弃（可通过 `conntrack -S` 看到 `insert_failed` 计数增长）！被丢包的那个请求只能傻等 **5 秒超时** 后才触发重试。

**3. Go 语言 DNS 解析器（Pure Go vs cgo）线程耗尽**
- Go 默认使用纯 Go 实现的 DNS 解析器（`GODEBUG=netdns=go`，在协程中非阻塞收发 UDP）；但如果启用了 cgo 且存在特殊 NSS 配置，走到系统调用 `getaddrinfo`（`netdns=cgo`），每个阻塞的 DNS 查询都会独占一个 OS 线程（M），瞬间创建上千个系统线程拖垮进程。

**彻底根治方案**
1. **部署 NodeLocal DNSCache**，并开启 `options single-request-reopen` 或强制走 TCP；
2. **调小 Pod 的 `ndots: 2`**，或在代码中访问外部固定域名时末尾加上根点（FQDN：`api.weixin.qq.com.`）；
3. **在 Go 进程内对 `net.Dialer` 增加带 Singleflight 与 Stale-While-Revalidate 的进程内 DNS 缓存**（避免每次新建连接都查 DNS）。
--- deep
### 为什么 `api.weixin.qq.com` 会在 K8s 里触发 8 次 DNS 查询？

看一眼 K8s Pod 里的 `/etc/resolv.conf`：
```
nameserver 10.96.0.10
search prod.svc.cluster.local svc.cluster.local cluster.local ec2.internal
options ndots:5
```

当你请求 `api.weixin.qq.com`（包含 **3** 个 `.`，小于 `ndots:5`）时，解析器执行的查询序列是：
1. `api.weixin.qq.com.prod.svc.cluster.local.` (A + AAAA) -> NXDOMAIN
2. `api.weixin.qq.com.svc.cluster.local.` (A + AAAA) -> NXDOMAIN
3. `api.weixin.qq.com.cluster.local.` (A + AAAA) -> NXDOMAIN
4. `api.weixin.qq.com.ec2.internal.` (A + AAAA) -> NXDOMAIN
5. `api.weixin.qq.com.` (A + AAAA) -> **终于拿到 IP！**

```
解决办法对比：
1. Pod YAML 配置 dnsConfig: options: [{name: ndots, value: "2"}, {name: timeout, value: "1"}, {name: attempts, value: "2"}]
2. 进程内缓存：重写 http.Transport 的 DialContext，将域名解析结果在内存中缓存 30~60s，后台异步刷新！
```

### Go 服务为什么强烈建议做进程内 DNS 缓存？

与 Java（JVM 默认缓存 DNS）不同，**Go 标准库的 `net.Resolver` 没有任何内置 DNS 缓存**！只要连接池因为波动新建 TCP 连接（或者短连接未复用），每次 `DialContext` 都会实打实地向 CoreDNS 发 UDP 包。在 `http.Transport.DialContext` 层包一层带 `Singleflight` 和过期兜底（Serve Stale on Error）的内存 DNS 缓存，即便 CoreDNS 整个集群短暂重启，你的 Go 服务也能靠本地缓存的旧 IP 零报错平稳度过！

title: 容器频繁发生 OOMKilled（退出码 137），但监控显示 Go Heap 只有容器限制的一半，怎么排查？
tags: OOMKilled, 容器内存, GOMEMLIMIT, PageCache, Mmap, Cgo
tasks: perf-31-1
--- answer
当 Kubernetes Pod 因退出码 `137`（`SIGKILL`，`Reason: OOMKilled`）重启，但 Grafana 上 `go_memstats_heap_inuse_bytes` 才 1GB（容器 Limit 是 2GB）时，说明**另外那 1GB 内存并不在 Go 的存活堆（Heap Inuse）里**。

**四大隐形内存刺客与排查路径**

**1. Go 运行时非 `HeapInuse` 内存（GC 峰值翻倍 + 协程栈 + 空闲 Span）**
- 默认 `GOGC=100` 下，如果当前存活堆是 900MB，下次触发 GC 的阈值是 1.8GB，加上海量 Goroutine 栈（`StackInuse`）、运行时元数据（`MSpanInuse`）以及尚未归还给 OS 的空闲页（`HeapIdle - HeapReleased`），进程的真实物理内存（RSS）轻松突破 2GB。
- **解法**：设置 **`GOMEMLIMIT=1700MiB`**（预留 15% 给容器基础开销），让 Go GC 在逼近容器水位前主动高频回收并立即归还物理内存（`scavenge`）。

**2. 容器 cgroup 的文件系统 Page Cache 被计入内存 Limit！**
- **极具迷惑性的坑**：Linux cgroup 的 `memory.usage_in_bytes`（v1）或 `memory.current`（v2）= **进程匿名物理内存（RSS）+ 文件读写页缓存（Page Cache）**！
- 如果你的 Go 程序在容器内频繁读写本地大文件、解压临时包或写大量本地日志，内核会把这些文件缓存在 Page Cache 中；当触发重度分配来不及回收 Page Cache 时，也会误触 OOM。可通过查看 `/sys/fs/cgroup/memory/memory.stat` 中的 `rss` 与 `cache` 占比来确认。

**3. `mmap` 映射内存或 Cgo（C/C++ 库）堆外内存泄漏**
- 使用 `syscall.Mmap`（如 BoltDB、Badger、本地向量索引）或通过 Cgo 调用 `malloc`（如图像处理 `libvips`、音频编解码、`rocksdb`）分配的内存，**完全不在 Go `runtime.MemStats` 的统计范围内**！
- **排查**：对比操作系统视角的进程 `VmRSS`（`/proc/self/status`）与 Go 运行时的 `Sys - HeapReleased`，若差值巨大，必有 Cgo 或 `mmap` 内存占用，需用 `jemalloc` profiler 或 `ebpf` 追踪。

**4. 容器内存在多个进程（如日志采集脚本、子进程 `exec.Command`）**
- cgroup Limit 限制的是整个 Pod 容器内所有进程的 RSS 总和。若 Go 进程通过 `os/exec` 并发拉起了多个 `ffmpeg` / `git` / `python` 子进程，子进程的内存同样算在同一个 cgroup 账上！
--- deep

### 为什么 `go tool pprof inuse_space` 经常比监控上的容器内存小得多？

线上排查内存告警时，新手最常犯的错误是直接看 `pprof/heap`（默认展示 `inuse_space`）：
1. `pprof/heap` **只包含上一次 GC 结束时存活的堆对象**（甚至不包含当前 GC 周期内新分配还没来得及回收的临时对象，也不包含 Goroutine 栈 `StackInuse`！）；
2. 要看真实的 Go 运行时账本，应该查 **`/metrics` 或 `/debug/pprof/heap?debug=1`** 中的：
   - `HeapInuse`：正在使用的堆 Span（包含页内碎片，往往比 `HeapAlloc` 大 10%~30%）；
   - `HeapIdle - HeapReleased`：已空闲但 Go runtime 留在手里没调 `madvise` 归还给 OS 的物理内存；
   - `StackInuse`：所有协程栈占用的物理内存（例如 10 万个曾扩容到 8KB 的协程栈就是 800MB，全部不在 heap profile 里！）。

title: 怎么正确阅读 CPU 火焰图、内存火焰图和差分火焰图（Diff Flame Graph）？
tags: 火焰图, pprof, 性能分析, CPU, 内存调优
tasks: perf-32-1
--- answer
火焰图（Flame Graph，由 Brendan Gregg 发明）是定位性能瓶颈最直观的可视化利器，但很多工程师会误读它的坐标轴含义。

**1. 火焰图的三大核心阅读法则**
- **Y 轴（纵向）表示调用栈深度**：每一层是一个函数调用帧（Stack Frame），越往上（或倒置火焰图越往下）是越底层的被调用子函数（父函数调用子函数）。
- **X 轴（横向）表示采样命中占比，绝不代表时间先后顺序！** 同一层级的函数块只是按**字母表顺序（Alphabetical Order）**从左到右排列并合并相同调用路径的。
- **看哪儿？找“大平顶（Plateau）”！**
  - 如果一个函数块很宽，但上面还完整顶着一个同样宽的子函数（俗称“细高塔”），说明它只是中间透传调用者（**Cumulative 累计耗时高，但 Flat 自身耗时为 0**）；
  - **只有顶部直接暴露在空气中且横向很宽的“平顶山（Plateau）”**，才是真正消耗大量 CPU 指令或直接分配内存的罪魁祸首（**Flat / Self 值高**）！

**2. 四种核心火焰图场景**
1. **CPU 火焰图（`profile`）**：定位哪些函数的循环、正则、序列化或锁自旋吃掉了 CPU 时间片。
2. **内存分配火焰图（`heap`）**：
   - `inuse_space`：查**内存泄漏**（哪些对象分配后一直没被释放）；
   - `alloc_space` / `alloc_objects`：查 **GC 压力过高**（哪些短命对象每秒在疯狂分配又立即被回收，虽然 `inuse` 很低但把 CPU 花在了 GC 上）。
3. **差分火焰图（Diff Flame Graph，`go tool pprof -diff_base=before.pb.gz after.pb.gz`）**：
   - 发版后 CPU 涨了 20% 或内存慢泄漏时，对比两个时间点（或发版前后）的 profile：
   - **红色块**代表耗时/内存增长的热点（越红增长越多），**蓝色块**代表减少的部分，1 秒揪出劣化代码！
--- deep
### 理解 `Flat (Self)` 与 `Cum (Cumulative)` 的本质区别

假设调用链是 `Handler() -> Service() -> MarshalJSON()`，其中：
- `Handler()` 自身逻辑耗时 `1ms`，调用了 `Service()`；
- `Service()` 自身逻辑耗时 `2ms`，调用了 `MarshalJSON()`；
- `MarshalJSON()` 自身耗时 `97ms`。

```
火焰图形状（顶部为被调用者）：
      ┌───────────────────────────────┐
      │         MarshalJSON (97ms)    │  <-- 暴露在顶部的“大平顶”！(Flat=97ms, Cum=97ms)
     ┌┴───────────────────────────────┴┐
     │           Service (99ms)        │  <-- 只有左右两侧露出 2ms (Flat=2ms, Cum=99ms)
    ┌┴─────────────────────────────────┴┐
    │            Handler (100ms)        │  <-- 底座 (Flat=1ms, Cum=100ms)
    └───────────────────────────────────┘
```

| 函数名 | Flat（自身耗时 = 块总宽 - 所有子块宽之和） | Cum（累计耗时 = 自身耗时 + 所有子调用耗时） | 优化启示 |
| :--- | :--- | :--- | :--- |
| `Handler` | `1ms` (1%) | `100ms` (100%) | 只是入口，看它没用 |
| `Service` | `2ms` (2%) | `99ms` (99%) | 只是中间商 |
| `MarshalJSON` | **`97ms` (97%)** | `97ms` (97%) | **真正的热点！优化它！** |

### 为什么颜色在普通火焰图里没有任何性能含义？

在普通火焰图（非差分火焰图）中，深红、橙色、黄色只是为了区分相邻方块的**随机暖色调**，**颜色深浅与耗时高低毫无关系**，只看**横向宽度（Width）**！只有在 `-diff_base` 生成的**红蓝差分火焰图**中，颜色才代表增长（红）与下降（蓝）。

=== perf-33
cat: perf
group: 综合
level: 3
title: 服务刚启动或滚动发布刚上线的前几秒大量报错超时（冷启动毛刺），可能是什么原因？怎么解决？
tags: 冷启动, 滚动发布, 连接池预热, 本地缓存, 优雅上下线, 慢启动
tasks: perf-33-1
--- answer
每次 K8s 滚动发布（Rolling Update）新 Pod 刚接流量的前 5~10 秒，监控上都会出现一波 P99 飙升甚至超时报错（Cold Start Latency Spike），是微服务稳定性的头号杀手。

**四大核心原因与工程解法**

**1. 下游连接池全空（TCP + TLS + MySQL/Redis 认证风暴）**
- **原因**：新 Pod 刚启动时，MySQL `sql.DB`、Redis 连接池、下游 gRPC/HTTP Keep-Alive 连接池里是 **0 个连接**。当负载均衡器瞬间把每秒 2000 QPS 的生产流量切进来时，前 2000 个请求被迫在热路径上同步进行 TCP 三次握手 + TLS 握手 + 数据库账号密码握手，耗时比平时高 10~50 倍！
- **解法**：**连接池预热（Connection Pool Warmup）**。在 Readiness 探针返回 `200 OK` 之前，主动并发执行 `Ping` 或预建最小核心连接数（MinIdleConns）。

**2. 进程内本地缓存（Local Cache）全空，瞬间穿透打爆下游**
- **原因**：老节点内存里缓存了全站热点商品/配置数据，命中率 99%；新节点刚启动时本地缓存命中率为 **0%**，所有请求全部回源 Redis/DB。
- **解法**：启动阶段在开放流量前，先执行 **Top-K 热点数据预加载（Cache Pre-population）**，把必查的字典、配置、热榜数据提前拉入内存。

**3. 首次调用的懒初始化锁竞争（Lazy Init）与 Go 堆/协程栈初始连续翻倍扩容**
- **原因**：正则表达式首次编译、大结构体反射元数据首次构建、以及新进程初始堆只有 4MB（前几秒连续触发 4MB->8MB->16MB->32MB->64MB... 的高频 GC 与栈拷贝）。
- **解法**：禁止在请求热路径做重型懒加载（一律提前到 `init` 或启动 `Bootstrap` 阶段完成），并通过设置初始内存压舱石或 `GOMEMLIMIT` 稳定 GC。

**4. 负载均衡器缺少慢启动（Slow Start / Warmup Window）**
- **解法**：在网关/Service Mesh（如 Envoy `slow_start_config`）或 RPC 客户端配置 **30~60 秒线性慢启动窗口**：新节点刚上线第 1 秒只分配 5% 权重，随着时间推移在 30 秒内平滑递增到 100% 正常权重！
--- deep
### 标准生产级服务启动与就绪（Readiness）生命周期编排

很多团队的 `/healthz` 和 `/readyz` 直接写死返回 `200 OK`，导致容器刚跑起 `main()` 第一行还没连上数据库，K8s 就把流量切过来了。

```
[进程启动 main()]
      │
      ▼
1. Bootstrap 预热阶段（此时 /readyz 返回 503 Service Unavailable）
   ├── 并发 Ping 并预建 MySQL / Redis / gRPC 连接池 (MinIdleConns)
   ├── 预加载本地字典缓存、路由规则与配置中心全量快照
   └── 预热关键序列化器与模板
      │
      ▼
2. 标记 atomic.Bool ready = true（/readyz 开始返回 200 OK）
      │
      ▼
3. 负载均衡器感知就绪，开启 30s Slow-Start 线性渐进加权放量 (5% -> 20% -> 50% -> 100%)
```

### 慢启动权重公式（Linear Slow-Start Weight）

在客户端负载均衡（如 gRPC Picker）中，针对上线时间不足 `warmupDuration`（如 30s）的新实例，计算其动态权重比例：
$$W(t) = \max\left(W_{\min}, \min\left(1.0, \frac{t - t_{\text{start}}}{T_{\text{warmup}}}\right)\right)$$
例如设定最小起步权重 $W_{\min} = 0.1$（10%），预热窗口 $T_{\text{warmup}} = 30\text{s}$：
- 刚上线时（$t=0\text{s}$）拿到 10% 的流量，温和填满本地缓存；
- 15 秒时拿到 50% 流量；
- 30 秒后恢复 100% 满额权重，彻底消灭滚动发布毛刺！

title: 线上日志打印过多打满磁盘 I/O，拖慢了业务接口响应，如何定位和治理？
tags: 日志治理, 磁盘IO, 异步日志, 日志采样, zap, slog
tasks: perf-34-1
--- answer
“一行 `log.Info` 把 P99 延迟从 5ms 拖慢到 500ms”是高并发系统中极易被忽视的性能杀手。

**1. 为什么打日志会卡死业务协程？**
1. **同步 `write(2)` 系统调用与文件锁竞争**：标准库 `log` 或默认同步刷盘的日志库内部有一把全局 `sync.Mutex`。当磁盘 I/O 被打满、内核 Page Cache 脏页比例超过 `vm.dirty_ratio`（默认 20%）时，内核会强制将调用 `write()` 的业务协程挂起，转为**同步等待物理磁盘刷盘**！由于该协程还握着日志库的 `Mutex`，其余成千上万个尝试打日志的业务协程瞬间全部锁死在等待队列中。
2. **容器 stdout 管道反压**：K8s 容器把日志打到 `stdout`，由容器运行时（containerd）读取并落盘。一旦落盘速度跟不上，`stdout` 管道缓冲区写满，业务进程的所有日志写入直接阻塞。
3. **JSON 反射序列化与字符串拼接的 CPU/GC 开销**：即便日志级别未开启，若写成 `log.Debugf("req: %+v", hugeStruct)`，参数里的 `hugeStruct` 依然会在每次请求时发生堆逃逸和格式化。

**2. 如何定位是日志 I/O 拖慢了服务？**
- **系统层**：`iostat -xz 1` 看到 `%util` 接近 100%，`w_await` 飙升；`iotop` 显示日志进程或 `containerd` 占满写带宽。
- **Go pprof 层**：抓取 `/debug/pprof/goroutine?debug=1` 或 `mutex`/`block` profile，看到成百上千个业务协程阻塞在 `os.(*File).Write` 或日志库的 `Mutex.Lock` 上。

**3. 体系化治理方案**
1. **结构化零反射日志库（`uber-go/zap` 或 Go 1.21+ `log/slog`）**；
2. **环形缓冲区异步批量刷盘（Buffered / Async Writer + Drop-on-Full）**：业务协程只写内存 RingBuffer，满时宁可丢弃非核心日志并累加 `dropped_logs_total` 指标，也**绝不阻塞业务主流程**；
3. **高频重复日志限流采样（Log Sampling，如 `zapcore.NewSamplerWithOptions`）**：当下游故障每秒报 5 万次相同的连接拒绝错误时，每秒前 100 条正常打印，之后每 100 条只采样打印 1 条！
--- deep
### 为什么故障雪崩时“报错日志”往往是压死骆驼的最后一根稻草？

平时正常运行时，只有 0.01% 的请求会走入 `if err != nil { log.Error(...) }` 分支，每秒只有几条错误日志；
一旦下游 Redis 或 DB 发生网络闪断：
1. 瞬间 **100% 的请求（每秒 50,000 次）** 全部进入 `log.Error("redis timeout", zap.Stack("stack"))` 分支；
2. 每次获取调用栈 `runtime.Callers` + 写入数 KB 的堆栈文本，瞬间产生 **200MB/s** 的磁盘写流量；
3. 磁盘 I/O 被打满 -> `write()` 阻塞 -> 日志锁阻塞 -> 原本已经恢复的下游请求也因为业务协程卡在打日志上而全部超时！

```
日志采样器（Tick Window Log Sampler）原理：
在每个时间窗口（如 1 秒）内，按日志消息模板（Key）计数：
  ├── count <= firstN (如前 10 条)：100% 原样输出（保留充足的现场第一手信息）
  └── count > firstN             ：仅当 (count - firstN) % thereafter == 0 时采样输出 1 条！
```

这样即使每秒爆发 10 万条完全相同的错误日志，经过 `first=10, thereafter=1000` 采样后，每秒最多只会写入 `10 + 100 = 110` 条，削减了 **99.9%** 的磁盘 I/O 风暴，同时一条关键报错类型都不会漏！

=== perf-35
cat: perf
group: 综合
level: 3
title: 跨可用区或跨机房调用偶发网络抖动，如何体系化地定位和容灾？
tags: 网络抖动, TCP重传, 跨可用区, 对冲请求, 区域亲和路由, eBPF
tasks: perf-35-1
--- answer
在多可用区（Multi-AZ）或混合云部署下，经常遇到“应用层监控报警偶发 P999 毛刺（200ms~1s），但上下游服务本身的 CPU、GC、DB 全都很空闲”的情况——这通常是**跨机房/跨 AZ 物理链路抖动或交换机微突发丢包（Micro-burst）**导致的 TCP 超时重传（RTO 最小 200ms）。

**1. 如何定位并实锤是底层网络抖动？（甩锅与定界铁证）**
1. **业务客户端分层埋点（`httptrace.ClientTrace`）**：区分耗时到底卡在 `DNS`、`Connect`（SYN 丢包重传，默认 1 秒！）、`TLSHandshake` 还是 `FirstResponseByte`。
2. **主机级 TCP 重传指标监控**：
   - 执行 `nstat -az | grep -E 'TcpExtTCPSynRetrans|TcpRetransSegs|TcpExtTCPTimeouts'` 或 `ss -ti` 查看具体连接的 `retrans` 和 `rtt`；
   - 如果发现在毛刺同一秒内，`TcpExtTCPSynRetrans`（建连丢包）或 `TcpRetransSegs` 同步突增，即可 100% 实锤是底层网络丢包重传，而非业务代码卡顿！
3. **双向持续拨测网格（Pingmesh）**：每个节点后台定时对其他 AZ 的节点做轻量级 TCP/ICMP 探测并绘制热力矩阵，一眼看出是“单机网卡故障”还是“AZ-A 到 AZ-B 的专线抖动”。

**2. 架构层四大容灾手段**
1. **同可用区优先路由（Zone-Aware / Topology-Aware Routing）**：
   - RPC 客户端优先将流量路由给**同机房/同可用区（Same AZ）**的下游实例（延迟 `< 0.5ms` 且免跨 AZ 带宽费）；只有当本 AZ 实例健康度不足或负载过高时，才溢出到其他 AZ。
2. **连接池长连接保活 + 调小建连超时（Connect Timeout）**：
   - 消灭每次请求新建连接遭遇 SYN 丢包（1s 惩罚）的概率；并将 `DialTimeout` 从默认的数秒收紧到 `200ms ~ 500ms`，快速失败切换节点。
3. **只读/幂等接口开启对冲请求（Hedged Requests）**：当请求超过 P95 延迟（如 15ms）仍未返回时，立刻向另一个可用区的副本并发发出备份请求，谁先回用谁。
4. **主动连接驱逐（Outlier Detection + SubConn Eviction）**：当某条长连接连续发生超时，强制关闭该连接并重新建连，让四元组重新哈希走健康的 ECMP 交换机链路。
--- deep
### 为什么一次 TCP SYN 丢包会让接口至少卡顿 1000ms？

在 Linux 内核中：
- **已建立连接的数据包重传（RTO）**：基于动态测量的 RTT 计算，内网最小 RTO（`TCP_RTO_MIN`）通常是 **200ms**（如果开启了早期重传 ER / RACK-TLP 可能更快）。
- **新建连接的第一次握手包（SYN）丢包**：因为此时还没有测量过该连接的 RTT，内核只能使用静态初始重传超时 `TCP_TIMEOUT_INIT`，在 Linux 内核中固定为 **1 秒（1000ms）**！

```
短连接遇上 0.1% 的跨机房 SYN 丢包：
Client ─── SYN (丢包!) ───► X
  ... 傻等整整 1000ms ...
Client ─── SYN (第1次重传) ──► Server (1ms 建连成功)
结果：P999 延迟直接出现 1001ms 的断崖式毛刺！
```

### 同可用区亲和路由（Zone-Aware Routing）算法

在多可用区部署（如 `az-east-1a`, `az-east-1b`, `az-east-1c`）下，客户端负载均衡器选择下游节点时遵循以下三级水位线：

```
客户端位于 az-east-1a，待选下游健康节点池 endpoints:
  ├── 1. 筛选出同可用区 (Zone == "az-east-1a") 且未超载的健康节点列表 localPool
  ├── 2. 检查同可用区健康占比：len(localPool) / totalLocal >= minHealthyRatio (如 50%)
  │      ├── 满足：100% 流量在 localPool 内部轮询（零跨 AZ 流量，最低延迟）
  │      └── 不满足（本 AZ 大面积故障）：自动降级退化为全集群跨 AZ 全局负载均衡！
```

这样既在平时消除了 100% 的跨机房网络抖动与云厂商跨 AZ 流量账单，又能在单可用区发生局部故障时无缝自动溢出到兄弟可用区。
