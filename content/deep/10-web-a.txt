=== web-01
--- deep
**原理展开**

`conn.serve` 的循环里，每个请求的处理步骤：

1. `readRequest`：用 `bufio.Reader` 读取请求行和请求头（受 `ReadHeaderTimeout` 限制），构造 `*http.Request`，请求体被包装成一个按需读取的 `body`；
2. 创建 `response`（实现了 `ResponseWriter`），它内部有一个 `bufio.Writer`（默认 4KB），响应头在第一次写入或者 handler 返回时才真正发出；
3. 调用 handler；
4. handler 返回后：没写过响应头就补发 200；**把请求体剩余的部分读掉**（最多 256KB，读不完就关闭连接），这样连接才能用于下一个请求；flush 响应。

HTTP/2 的处理方式不同：一个连接有一个读循环 goroutine 负责读取帧，每个 stream 的 handler 在独立的 goroutine 中运行，写操作通过一个写调度器合并发送。

**代码示例**

```go
// 观察连接复用：ConnState 回调
srv := &http.Server{
	Addr:    ":8080",
	Handler: mux,
	ConnState: func(c net.Conn, s http.ConnState) {
		slog.Debug("conn", "remote", c.RemoteAddr(), "state", s) // New → Active → Idle → Active … → Closed
	},
}

// 客户端断开时及时停止
func handler(w http.ResponseWriter, r *http.Request) {
	select {
	case res := <-doWork(r.Context()):
		json.NewEncoder(w).Encode(res)
	case <-r.Context().Done():
		return // 客户端已断开，不用再写响应
	}
}
```

**常见追问**

- handler 里可以在 goroutine 中继续使用 `w` 吗？→ 不可以，handler 返回后 ResponseWriter 就不能再使用，后台任务需要的数据要提前复制出来。
- 请求体可以读两次吗？→ 不能直接读两次；需要时先读到内存（注意大小限制），再用 `io.NopCloser(bytes.NewReader(b))` 替换 `r.Body`。
- 为什么 handler 返回后连接可能被关闭？→ 请求体没读完且剩余太多、handler panic、请求或响应带有 `Connection: close`。

**实战建议**

- 限制请求体大小：`r.Body = http.MaxBytesReader(w, r.Body, 1<<20)`。
- 理解“一个连接一个 goroutine”，有助于分析连接数、goroutine 数和内存之间的关系。

=== web-02
--- deep
**原理展开**

两种中间件模型的本质：

- **标准库（装饰器）**：每个中间件返回一个新的 Handler，调用链在“组装时”就确定了，形成一层层嵌套的闭包；调用下一层就是调用被包装的 `next.ServeHTTP`；
- **Gin（切片 + 下标）**：所有处理函数放在一个切片里，`Next()` 推进下标并循环调用，调用链在“运行时”由下标驱动。好处是不需要为每个请求创建闭包，`Abort` 实现起来也很简单（直接修改下标）。

两种模型都形成“洋葱”结构：中间件可以在调用下一层之前做预处理（鉴权、限流），之后做后处理（记录耗时、修改响应）。

**代码示例**

```go
// Gin 中间件：记录耗时和状态码
func Logger() gin.HandlerFunc {
	return func(c *gin.Context) {
		start := time.Now()
		c.Next() // 执行后续的所有处理函数
		slog.Info("request",
			"path", c.FullPath(), "status", c.Writer.Status(),
			"latency", time.Since(start), "errors", c.Errors.String())
	}
}

// 鉴权失败时中止
func Auth() gin.HandlerFunc {
	return func(c *gin.Context) {
		if !valid(c.GetHeader("Authorization")) {
			c.AbortWithStatusJSON(http.StatusUnauthorized, gin.H{"code": 40100})
			return // Abort 之后当前函数仍会继续，所以要 return
		}
		c.Next()
	}
}

// 在 goroutine 中使用 Context 前复制
func Async(c *gin.Context) {
	cc := c.Copy()
	go func() { audit(cc.Request.URL.Path) }()
}
```

**常见追问**

- 中间件的顺序有什么讲究？→ 通常是：恢复 panic → 请求 ID / trace → 日志 → 限流 → CORS → 鉴权 → 业务。恢复放在最外层才能捕获所有 panic；CORS 在鉴权之前，否则预检请求会被拒绝。
- 中间件之间怎么传递数据？→ 标准库用 `r.WithContext(context.WithValue(...))`；Gin 用 `c.Set` / `c.Get`。
- 中间件里修改响应体怎么做？→ 包装 ResponseWriter，把写入缓冲下来，处理后再写出（会增加内存开销，不适合流式响应）。

**实战建议**

- 中间件只做横切关注点（日志、鉴权、限流、追踪），不要放业务逻辑。
- 新项目如果只用到路由和中间件，标准库 + 少量辅助函数就足够了。

=== web-03
--- deep
**原理展开**

ServeMux 的匹配规则：当多个模式都能匹配一个请求时，选择**最具体**的那个。“更具体”的定义是：如果模式 A 匹配的请求是模式 B 匹配的请求的严格子集，A 更具体。例如 `/users/{id}` 和 `/users/me` 都匹配 `/users/me`，后者更具体，所以选后者。如果两个模式匹配的请求有交集、但谁也不是谁的子集（比如 `/users/{id}/posts` 和 `/{x}/me/posts`），注册时就会 panic，避免在运行时出现歧义。

其他规则：带方法的模式比不带方法的更具体；`GET` 同时匹配 `HEAD`；以 `/` 结尾的模式匹配所有以它为前缀的路径；`{$}` 只匹配末尾斜杠本身（`/{$}` 只匹配根路径）。

**代码示例**

```go
mux := http.NewServeMux()
mux.HandleFunc("GET /users/{id}", getUser)
mux.HandleFunc("GET /users/me", getMe)            // 更具体，优先
mux.HandleFunc("GET /{$}", home)                   // 只匹配 "/"
mux.HandleFunc("/", notFound)                      // 兜底

// 子路由：用 StripPrefix 挂载另一个 mux
api := http.NewServeMux()
api.HandleFunc("GET /orders/{id}", getOrder)
mux.Handle("/api/v1/", http.StripPrefix("/api/v1", api))

// 中间件分组：给一组路由统一加中间件
admin := http.NewServeMux()
admin.HandleFunc("POST /users/{id}/ban", banUser)
mux.Handle("/admin/", http.StripPrefix("/admin", requireAdmin(admin)))
```

**常见追问**

- 路径参数可以有正则约束吗？→ 不支持，需要在 handler 里自己校验。
- 405 响应会带 Allow 头吗？→ 会，ServeMux 自动列出该路径支持的方法。
- 旧版本的模式（不带方法）还能用吗？→ 能，向后兼容；可以用 `GODEBUG=httpmuxgo121=1` 恢复旧的匹配行为。

**实战建议**

- 路由少、需求简单的服务直接用标准库，减少依赖。
- 需要参数绑定、校验、文档生成等完整功能时再引入框架。

=== web-04
--- deep
**原理展开**

`Shutdown` 的执行过程：

1. 关闭所有 Listener，不再接受新连接；
2. 关闭所有**空闲**的连接；
3. 循环检查（间隔从 1ms 逐渐增加到 500ms）：所有连接都变为空闲并关闭后返回；ctx 到期则返回 ctx.Err()。

正在处理请求的连接会在请求结束后变为空闲，然后被关闭（keep-alive 的连接不会再接受新的请求）。HTTP/2 连接会发送 GOAWAY 帧，通知客户端不要再发起新的 stream。

在 Kubernetes 中的时序问题：kubelet 发送 SIGTERM 和 endpoints controller 摘除 Pod 是并行的，kube-proxy / ingress 更新转发规则还需要时间。如果收到信号立刻 Shutdown，这段时间内新来的连接会被拒绝。

**代码示例**

```go
func run(ctx context.Context) error {
	health := &Health{}
	srv := &http.Server{Addr: ":8080", Handler: routes(health)}
	errCh := make(chan error, 1)
	go func() { errCh <- srv.ListenAndServe() }()

	select {
	case err := <-errCh:
		return err
	case <-ctx.Done():
	}

	health.MarkShuttingDown()      // 1. 就绪探针返回 503
	time.Sleep(5 * time.Second)    // 2. 等待负载均衡摘除流量

	sctx, cancel := context.WithTimeout(context.Background(), 20*time.Second)
	defer cancel()
	if err := srv.Shutdown(sctx); err != nil { // 3. 等待处理中的请求
		return err
	}
	consumer.Stop()                // 4. 停止后台任务
	return db.Close()              // 5. 释放资源
}
```

**常见追问**

- `Close` 和 `Shutdown` 有什么区别？→ `Close` 立即关闭所有连接，不等待请求完成。
- 长连接（WebSocket、SSE）怎么优雅关闭？→ 用 `RegisterOnShutdown` 注册回调，通知这些连接发送关闭消息，并设置较短的等待时间。
- 消息队列的消费者怎么优雅关闭？→ 停止拉取新消息，等待正在处理的消息完成并提交位点，然后关闭连接。

**实战建议**

- 关闭流程的每一步都打日志，带上耗时，便于排查“为什么关闭很慢”。
- 用 `preStop` 的 sleep 或者应用内的延迟，二选一即可，总时长要小于 terminationGracePeriodSeconds。

=== web-05
--- deep
**原理展开**

`http.Client` 只是一个轻量的配置（超时、重定向策略、Cookie），真正干活的是 **Transport**：它维护连接池（按 host 分组的空闲连接）、负责建立连接（DNS、TCP、TLS 握手）、HTTP/2 的多路复用。

几个超时的层次：

- `Client.Timeout`：从发起请求到读完响应体的总时间；
- `Transport.DialContext` 中的 `net.Dialer.Timeout`：建立 TCP 连接；
- `Transport.TLSHandshakeTimeout`：TLS 握手；
- `Transport.ResponseHeaderTimeout`：发送完请求到收到响应头；
- 请求的 ctx：可以继承上游的截止时间，最灵活。

**代码示例**

```go
var transport = &http.Transport{
	Proxy: http.ProxyFromEnvironment,
	DialContext: (&net.Dialer{
		Timeout:   2 * time.Second,
		KeepAlive: 30 * time.Second,
	}).DialContext,
	TLSHandshakeTimeout:   3 * time.Second,
	ResponseHeaderTimeout: 5 * time.Second,
	MaxIdleConns:          200,
	MaxIdleConnsPerHost:   50, // 默认只有 2
	IdleConnTimeout:       90 * time.Second,
	ForceAttemptHTTP2:     true,
}

var client = &http.Client{Transport: transport, Timeout: 10 * time.Second}

// 观察连接是否被复用
trace := &httptrace.ClientTrace{
	GotConn: func(info httptrace.GotConnInfo) {
		slog.Debug("got conn", "reused", info.Reused, "idle_time", info.IdleTime)
	},
}
req = req.WithContext(httptrace.WithClientTrace(req.Context(), trace))
```

**常见追问**

- 重定向会自动跟随吗？→ 默认最多跟随 10 次；可以通过 `CheckRedirect` 自定义，返回 `http.ErrUseLastResponse` 表示不跟随。
- 为什么要读完 Body 才能复用连接？→ HTTP/1.1 的响应在同一个连接上依次传输，没读完的数据会混进下一个响应里，所以 Transport 只回收读完的连接。
- 怎么设置每个请求不同的超时？→ 用 `http.NewRequestWithContext` + `context.WithTimeout`。

**实战建议**

- 每个下游服务一个专门配置的 Client（超时、连接池大小按下游的特点设置），全局复用。
- 在客户端埋点记录每个下游的耗时、状态码和错误类型。

=== web-06
--- deep
**原理展开**

**JWT 的结构和验证**：`header.payload.signature`。签名算法常用 HS256（HMAC，对称密钥，签发方和验证方共享密钥）或 RS256 / ES256（非对称，私钥签发、公钥验证，适合多个服务独立验证而不需要持有签发的密钥）。验证时**必须固定期望的算法**，否则攻击者可以把 alg 改成 `none`，或者把 RS256 改成 HS256 并用公钥作为 HMAC 的密钥伪造签名。

**refresh token 轮换**：每次用 refresh token 换取新的 access token 时，同时签发一个新的 refresh token，旧的立即作废。如果旧的 refresh token 再次被使用，说明它可能被窃取了（合法的客户端已经拿到了新的），这时吊销这个用户的整条 token 链。

**代码示例**

```go
// golang-jwt：验证时限定算法
token, err := jwt.ParseWithClaims(raw, &Claims{}, func(t *jwt.Token) (any, error) {
	return secretFor(t.Header["kid"]), nil
}, jwt.WithValidMethods([]string{"HS256"}), jwt.WithExpirationRequired(), jwt.WithLeeway(30*time.Second))

// Cookie 的安全属性
http.SetCookie(w, &http.Cookie{
	Name:     "session",
	Value:    sid,
	Path:     "/",
	HttpOnly: true,                 // JS 无法读取，防 XSS 窃取
	Secure:   true,                 // 只通过 HTTPS 发送
	SameSite: http.SameSiteLaxMode, // 跨站请求默认不携带，防 CSRF
	MaxAge:   7 * 24 * 3600,
})
```

**常见追问**

- token 放在 localStorage 还是 Cookie？→ localStorage 容易被 XSS 读取；HttpOnly Cookie 不能被脚本读取，但需要防 CSRF（SameSite + CSRF token）。
- JWT 适合做 Session 吗？→ 需要随时踢人下线、频繁修改权限的场景，有状态的 Session 更简单；JWT 适合服务之间传递身份、或者短期的访问令牌。
- `exp`、`nbf`、`iat` 是什么？→ 过期时间、生效时间、签发时间，都是 Unix 秒；验证时允许少量的时钟偏差（leeway）。

**实战建议**

- access token 短期有效（分钟级），refresh token 存储在服务端并可撤销。
- 密钥通过 `kid` 支持轮换，旧密钥在所有旧令牌过期之前保留用于验证。

=== web-07
--- deep
**原理展开**

同源策略限制的是**读取响应**，而不是发送请求：跨域的简单请求实际上已经发到了服务端并被执行，只是浏览器不让页面脚本读取结果。所以 CORS 不能防止跨站请求造成的副作用（那是 CSRF 防护要做的事）。预检请求的意义是：对于“非简单”的请求，先问一下服务端是否允许，服务端不允许就根本不发送真正的请求，保护那些不知道 CORS 的老服务。

几个响应头：

- `Access-Control-Allow-Origin`：允许的源；
- `Access-Control-Allow-Credentials`：是否允许携带 Cookie；
- `Access-Control-Allow-Methods` / `Allow-Headers`：预检响应中允许的方法和请求头；
- `Access-Control-Expose-Headers`：允许脚本读取的响应头（默认只能读几个基本的头）；
- `Access-Control-Max-Age`：预检结果的缓存时间（浏览器有上限，Chrome 是 2 小时）。

**代码示例**

```go
// 使用成熟的库：github.com/rs/cors
c := cors.New(cors.Options{
	AllowedOrigins:   []string{"https://app.example.com"},
	AllowedMethods:   []string{http.MethodGet, http.MethodPost, http.MethodPut, http.MethodDelete},
	AllowedHeaders:   []string{"Authorization", "Content-Type", "X-Request-ID"},
	ExposedHeaders:   []string{"X-Request-ID"},
	AllowCredentials: true,
	MaxAge:           600,
})
handler := c.Handler(mux)
```

**常见追问**

- 开发环境怎么处理跨域？→ 前端开发服务器配置代理（把 `/api` 转发到后端），浏览器看到的就是同源请求。
- 为什么设置了 CORS 头还是失败？→ 常见原因：预检请求被鉴权中间件拦截返回 401、响应头被重复设置（网关和应用都加了）、带凭证时使用了 `*`。
- `Vary: Origin` 有什么用？→ 告诉缓存（CDN、浏览器）响应内容随 Origin 变化，否则一个源的响应可能被缓存后返回给另一个源。

**实战建议**

- 白名单精确匹配，不要用“以 example.com 结尾”这种字符串匹配（`evil-example.com` 也能匹配）。
- CORS 统一在网关或者一个中间件里处理，不要在多处重复设置。

=== web-08
--- deep
**原理展开**

幂等性要在**整条链路**上考虑：客户端重试、网关重试、服务间调用重试、消息队列重复投递，任何一处都可能产生重复请求。核心思路是给每个“业务操作”一个唯一的标识，服务端根据这个标识识别重复：

- 标识由谁生成：客户端生成（幂等键）能覆盖网络超时后的重试；服务端生成（订单号）适合在业务开始时就分配；
- 标识存在哪里：数据库唯一索引最可靠（和业务数据在同一个事务里）；Redis 适合短期的去重，需要处理 Redis 和数据库之间的不一致。

“处理中”状态的处理：第一个请求还没完成时第二个请求到达，可以返回 409 让客户端稍后查询，或者等待第一个请求完成后返回相同的结果。

**代码示例**

```go
// 幂等键中间件（Redis 版）：只对写操作生效
func Idempotent(rdb *redis.Client) func(http.Handler) http.Handler {
	return func(next http.Handler) http.Handler {
		return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
			key := r.Header.Get("Idempotency-Key")
			if key == "" || r.Method == http.MethodGet {
				next.ServeHTTP(w, r)
				return
			}
			rk := "idem:" + userID(r) + ":" + key
			ok, err := rdb.SetNX(r.Context(), rk, "processing", 24*time.Hour).Result()
			if err != nil {
				http.Error(w, "internal error", http.StatusInternalServerError)
				return
			}
			if !ok {
				if saved, _ := rdb.Get(r.Context(), rk).Result(); saved != "processing" {
					w.Header().Set("Idempotent-Replayed", "true")
					w.Write([]byte(saved)) // 返回首次的结果
					return
				}
				http.Error(w, "request in progress", http.StatusConflict)
				return
			}
			rec := httptest.NewRecorder()
			next.ServeHTTP(rec, r)
			if rec.Code < 500 {
				rdb.Set(r.Context(), rk, rec.Body.String(), 24*time.Hour)
			} else {
				rdb.Del(r.Context(), rk) // 服务端错误允许重试
			}
			for k, v := range rec.Header() {
				w.Header()[k] = v
			}
			w.WriteHeader(rec.Code)
			w.Write(rec.Body.Bytes())
		})
	}
}
```

**常见追问**

- 幂等键要不要和用户绑定？→ 要，否则不同用户恰好生成了相同的键会互相干扰，甚至泄露数据。
- 第二次请求的参数和第一次不同怎么办？→ 应该报错（比如 422），保存时可以记录请求参数的哈希用于比对。
- 消息队列的消费怎么做幂等？→ 用消息的业务 ID 做唯一约束，或者记录已处理的消息 ID（见「幂等消费」任务）。

**实战建议**

- 所有涉及资金、库存、状态变更的接口都要设计幂等方案，并写进接口文档。
- 数据库唯一约束是最后一道防线，无论上层用了什么方案都要加。

=== web-09
--- deep
**原理展开**

令牌桶的两个参数：**速率**决定长期的平均吞吐，**桶容量**决定允许多大的突发。`rate.Limiter` 的实现不需要定时器：记录上次更新的时间和令牌数，每次请求时根据经过的时间计算新增的令牌。它还支持“预约”（`Reserve`）：令牌不够时告诉你需要等多久，适合需要平滑发送速率的场景（比如调用有频率限制的第三方 API）。

分布式限流的难点：多个实例共享一个配额，计数必须在一个中心化的地方（Redis）原子地完成，每次请求都要访问 Redis，增加了延迟和对 Redis 的依赖。折中方案：每个实例从 Redis 批量“预取”一部分配额在本地使用。

**代码示例**

```lua
-- Redis 令牌桶（KEYS[1] 桶，ARGV: 速率/秒, 容量, 当前毫秒, 需要的令牌数）
local rate, cap, now, need = tonumber(ARGV[1]), tonumber(ARGV[2]), tonumber(ARGV[3]), tonumber(ARGV[4])
local b = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
local tokens = tonumber(b[1]) or cap
local ts = tonumber(b[2]) or now
tokens = math.min(cap, tokens + (now - ts) / 1000 * rate)
local ok = 0
if tokens >= need then
  tokens = tokens - need
  ok = 1
end
redis.call('HSET', KEYS[1], 'tokens', tokens, 'ts', now)
redis.call('PEXPIRE', KEYS[1], math.ceil(cap / rate * 1000) * 2)
return ok
```

**常见追问**

- 限流的维度有哪些？→ 全局、接口、用户、IP、租户，通常组合使用（比如每个用户每秒 10 次，同时接口总共每秒 1 万次）。
- 被限流的请求应该排队还是拒绝？→ 在线请求一般直接拒绝（快速失败），后台任务可以排队等待。
- 限流和熔断的区别？→ 限流保护自己不被过多的请求压垮；熔断保护下游，在下游故障时停止调用。

**实战建议**

- 限流阈值通过压测确定，并可以动态调整（配置中心）。
- 被限流的请求要计入监控，阈值设置不合理时能及时发现。

**原理展开**

几个服务端超时覆盖的阶段：

```text
|-- 建立连接 --|-- 读请求头 --|-- 读请求体 --|-- 处理 + 写响应 --|-- 空闲 --|
               |← ReadHeaderTimeout →|
               |←──── ReadTimeout ────→|
                              |←──────── WriteTimeout ────────→|
                                                                |← IdleTimeout →|
```

注意 `WriteTimeout` 是从**读完请求头**开始计时的，包含了 handler 的执行时间；超时后连接被关闭，但 handler 本身并不会被中断（它只会在写的时候发现错误）。所以 handler 的执行时间要通过 ctx 来控制。

**超时预算**：一个请求的总超时是 1 秒，它要依次调用服务 A（预算 300ms）和服务 B（预算 300ms），重试一次的话就需要 1.2 秒，已经超过总预算。所以超时要自上而下规划，下游的超时（含重试）之和要小于上游。

**代码示例**

```go
// 针对单个请求调整写超时（比如导出文件）
func export(w http.ResponseWriter, r *http.Request) {
	rc := http.NewResponseController(w)
	_ = rc.SetWriteDeadline(time.Now().Add(5 * time.Minute))
	for chunk := range generate(r.Context()) {
		w.Write(chunk)
		_ = rc.Flush()
	}
}

// 根据剩余时间决定是否调用下游
func callIfTime(ctx context.Context, need time.Duration, fn func(context.Context) error) error {
	if dl, ok := ctx.Deadline(); ok && time.Until(dl) < need {
		return context.DeadlineExceeded // 时间不够，不必再浪费下游的资源
	}
	return fn(ctx)
}
```

**常见追问**

- `http.TimeoutHandler` 有什么缺点？→ 它会缓冲整个响应（不能流式输出），超时后 handler 仍在后台运行。
- 客户端超时和服务端超时哪个应该更长？→ 客户端的超时应该略长于服务端的处理超时，这样服务端有机会返回一个明确的超时错误，而不是连接被直接断开。
- 网关有自己的超时吗？→ 有（Nginx 的 `proxy_read_timeout` 等），要和服务的超时协调好。

**实战建议**

- 每个服务都在启动配置里显式设置 Server 的四个超时。
- 把超时配置集中管理，画出调用链上每一跳的超时，检查是否合理。

=== web-11
--- deep
**原理展开**

错误码设计的几个原则：

- **对调用方有用**：客户端需要根据错误码做不同的处理（提示用户、重试、跳转登录），只需要区分这些情况，不需要把内部的每种错误都编码；
- **稳定**：错误码一旦发布就是 API 的一部分，不能随意修改含义；
- **分层**：HTTP 状态码给网关、监控、通用客户端看；业务码给业务逻辑看；message 给用户看（可以国际化）；详细原因只进日志。

常见的业务码编排：前两位或三位表示模块（10 用户、20 订单），后面表示具体错误；或者直接使用 HTTP 状态码 × 100 + 序号（40001、40401）。

**代码示例**

```go
// 用 validator 做结构体校验，并转换成统一的字段错误
type CreateUserReq struct {
	Name  string `json:"name"  validate:"required,min=2,max=20"`
	Email string `json:"email" validate:"required,email"`
	Age   int    `json:"age"   validate:"gte=0,lte=150"`
}

var validate = validator.New(validator.WithRequiredStructEnabled())

func bind(r *http.Request, v any) error {
	dec := json.NewDecoder(http.MaxBytesReader(nil, r.Body, 1<<20))
	dec.DisallowUnknownFields()
	if err := dec.Decode(v); err != nil {
		return &BizError{Code: 40000, Message: "请求格式错误", cause: err}
	}
	if err := validate.Struct(v); err != nil {
		var ve validator.ValidationErrors
		if errors.As(err, &ve) {
			return &BizError{Code: 40001, Message: ve[0].Field() + " 不合法", cause: err}
		}
		return err
	}
	return nil
}
```

**常见追问**

- 业务错误要不要返回 HTTP 200？→ 两种风格都有：统一返回 200 + 业务码（对某些客户端更简单）；或者使用合适的 HTTP 状态码（对网关、监控、缓存更友好）。后者更符合 HTTP 语义，推荐使用。
- 错误信息要国际化怎么做？→ 根据错误码和 `Accept-Language` 在出口处查表翻译，内部只传错误码和参数。
- 参数校验放在哪一层？→ 格式校验（必填、长度、格式）在 handler 层；业务规则校验（用户名是否已存在）在 service 层。

**实战建议**

- 维护一份错误码清单文档（或者代码生成），客户端和服务端共享。
- 统一的响应格式和错误出口从项目一开始就建立，后期再改代价很大。
