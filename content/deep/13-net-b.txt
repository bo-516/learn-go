=== net-12
--- deep
**原理展开**

wire type 是兼容性的关键：解码器读到一个不认识的字段编号时，根据 wire type 就知道它的值有多长，从而跳过它（或者原样保留，重新序列化时写回去）。五种 wire type：0 varint、1 64 位定长、2 长度前缀、5 32 位定长（3、4 是废弃的 group）。

几个容易出错的变更：

- `int32` 改成 `int64`：wire type 都是 varint，兼容，但超出范围的值会被截断；
- `int32` 改成 `sint32`：都是 varint，但 zigzag 编码的含义不同，**不兼容**；
- `string` 和 `bytes` 互换：wire type 相同，UTF-8 有效时兼容；
- 单个字段改成 `repeated`：对标量类型，proto3 的 packed 编码和单个值的编码不同，可能不兼容；
- 修改字段名：二进制兼容（编码里没有名字），但 JSON 映射使用字段名，会不兼容。

**代码示例**

```protobuf
syntax = "proto3";
package order.v1;

message Order {
  reserved 3, 5;                 // 已删除字段的编号，禁止重用
  reserved "coupon", "remark";   // 已删除字段的名字

  int64 id = 1;
  string user_id = 2;
  optional int64 discount = 4;   // optional：能区分“没设置”和 0
  OrderStatus status = 6;
  map<string, string> attrs = 7;
}

enum OrderStatus {
  ORDER_STATUS_UNSPECIFIED = 0;  // 第一个必须是 0，表示未设置
  ORDER_STATUS_PAID = 1;
}
```

**常见追问**

- 为什么 1～15 号字段更“珍贵”？→ tag 也是 varint，编号 1～15 的 tag 只占 1 个字节，常用字段应该用小编号。
- proto3 的默认值会被序列化吗？→ 不会，零值字段不写入，所以无法区分；`optional` 字段会生成“是否设置”的标记。
- protobuf 和 JSON 的性能差多少？→ 编码体积通常小几倍，编解码速度快一个数量级，具体取决于数据。

**实战建议**

- 在 CI 中用 `buf breaking` 自动检查 proto 的兼容性。
- proto 文件按版本组织包名（`order.v1`），真正不兼容的修改通过新的包版本发布。

**原理展开**

**元数据（metadata）**：gRPC 的 metadata 就是 HTTP/2 的头部，key 必须是小写；以 `-bin` 结尾的 key 的值是二进制（自动 base64 编码）。客户端用 outgoing context 发送，服务端从 incoming context 读取；服务端还可以通过 `grpc.SetHeader` / `grpc.SetTrailer` 返回元数据。

**错误码的选择**：gRPC 定义了 17 个标准状态码，选择正确的码很重要，因为客户端、网关、重试策略都依赖它：

- `InvalidArgument`（参数错误，不重试）vs `FailedPrecondition`（状态不允许，比如订单已取消，不重试）vs `Aborted`（并发冲突，可以在更高层重试）；
- `Unavailable`（暂时不可用，可以重试）vs `Internal`（内部错误，一般不重试）；
- `DeadlineExceeded`（超时）、`ResourceExhausted`（限流）、`Unauthenticated`、`PermissionDenied`、`NotFound`、`AlreadyExists`。

**代码示例**

```go
// 服务端读取元数据
func AuthInterceptor(ctx context.Context, req any, info *grpc.UnaryServerInfo, handler grpc.UnaryHandler) (any, error) {
	md, _ := metadata.FromIncomingContext(ctx)
	tokens := md.Get("authorization")
	if len(tokens) == 0 {
		return nil, status.Error(codes.Unauthenticated, "missing token")
	}
	user, err := verify(tokens[0])
	if err != nil {
		return nil, status.Error(codes.Unauthenticated, "invalid token")
	}
	return handler(WithUser(ctx, user), req)
}

// 返回结构化的错误详情

st, _ = st.WithDetails(&errdetails.BadRequest{
	FieldViolations: []*errdetails.BadRequest_FieldViolation{{Field: "email", Description: "格式不正确"}},
})
return nil, st.Err()
```

- 服务端怎么知道客户端设置的超时？→ `ctx.Deadline()`，gRPC 已经根据 `grpc-timeout` 头设置好了。
- 业务错误码怎么和 gRPC 状态码结合？→ 用 gRPC 状态码表达大类，用 `errdetails.ErrorInfo`（Reason + Domain + Metadata）携带业务错误码。
- 流式调用的拦截器有什么不同？→ 流拦截器包装的是 `ServerStream`，要拦截每条消息需要包装它的 `SendMsg` / `RecvMsg`。

- 制定团队的错误码映射规范：哪些业务错误对应哪个 gRPC 状态码。

**原理展开**

gRPC 客户端的内部结构：`grpc.ClientConn` 不是一个连接，而是一个连接管理器：

- **resolver**（解析器）把目标地址（`dns:///svc:9090`）解析成一组后端地址，并在地址变化时通知；
- **balancer**（负载均衡器）为每个地址维护一个 **SubConn**（真正的连接），并决定每个 RPC 使用哪个 SubConn；
- 默认的 `pick_first` 策略只连接第一个可用的地址，所有请求都走这一个连接——这就是不均衡的根源；`round_robin` 会连接所有地址并轮询。

DNS 解析器默认只在启动时和连接失败时重新解析，所以扩容后新实例的地址需要一段时间才会被发现。服务端设置 `MaxConnectionAge` 定期关闭连接，客户端重连时就会重新解析。

=== net-15
--- deep
**原理展开**

**重试放大**的数学：每层重试 3 次（共 4 次尝试），调用链有 3 层时，最底层服务在故障时会收到 4³ = 64 倍的请求。这些额外的流量恰好发生在下游已经出问题的时候，会让故障更难恢复。

**重试预算**（retry budget）：统计一个时间窗口内的请求数和重试数，重试数超过请求数的一定比例（如 10%）就不再重试。正常时偶发的失败可以被重试掩盖，下游大面积故障时重试会被自动限制，流量最多只放大 1.1 倍。

**对冲请求**（hedging）：针对尾延迟。发出请求后，如果超过一定时间（比如 p95 延迟）还没有响应，就向另一个副本再发一份，使用先返回的结果并取消另一个。只能用于幂等请求，会增加少量的负载，但能显著降低 p99。

**代码示例**

```json
// gRPC 的服务配置：声明式的重试策略
{
  "methodConfig": [{
    "name": [{"service": "order.v1.OrderService", "method": "GetOrder"}],
    "retryPolicy": {
      "maxAttempts": 3,
      "initialBackoff": "0.1s",
      "maxBackoff": "1s",
      "backoffMultiplier": 2,
      "retryableStatusCodes": ["UNAVAILABLE", "DEADLINE_EXCEEDED"]
    }
  }],
  "retryThrottling": {"maxTokens": 10, "tokenRatio": 0.1}
}
```

`retryThrottling` 就是 gRPC 内置的重试预算：每次失败消耗 1 个令牌、每次成功恢复 0.1 个，令牌低于一半时停止重试。

**常见追问**

- 超时的请求可以重试吗？→ 要小心，超时不代表对方没有执行（可能执行了但响应慢），只有幂等的操作才能重试。
- 重试时应该换一个实例吗？→ 应该，同一个实例可能正处于故障中；gRPC 的重试会重新经过负载均衡器选择。
- 客户端怎么知道服务端过载了？→ 服务端返回 `ResourceExhausted` 或者 HTTP 429 / 503 并带上 `Retry-After`，客户端据此退避。

**实战建议**

- 明确规定在哪一层重试（通常是最靠近用户的那一层，或者最靠近故障的那一层），其他层不重试。
- 重试次数和退避参数写进服务的配置，并监控重试率。

=== net-16
--- deep
**原理展开**

RPC 框架的核心难点：

- **多路复用**：一个连接上同时有多个请求在途，每个请求带一个唯一的请求 ID，响应也带上这个 ID，客户端用一个 `map[reqID]chan *Response` 把响应分发给对应的调用者；
- **连接管理**：连接池、健康检查、断线重连、优雅关闭（停止发送新请求，等待在途请求完成）；
- **服务治理**：这些功能和具体的业务无关，通常以拦截器 / 中间件的形式实现，可以插拔；
- **性能**：序列化、内存分配、系统调用次数（批量写）、goroutine 数量。

**代码示例**

```go
// 客户端多路复用的核心结构
type Client struct {
	conn    net.Conn
	mu      sync.Mutex
	seq     uint64
	pending map[uint64]chan *Response
}

func (c *Client) Call(ctx context.Context, method string, req []byte) (*Response, error) {
	ch := make(chan *Response, 1)
	c.mu.Lock()
	c.seq++
	id := c.seq
	c.pending[id] = ch
	c.mu.Unlock()
	defer func() { c.mu.Lock(); delete(c.pending, id); c.mu.Unlock() }()

	if err := c.writeFrame(id, method, req); err != nil {
		return nil, err
	}
	select {
	case resp := <-ch:
		return resp, nil
	case <-ctx.Done():
		return nil, ctx.Err() // 超时：响应之后到达时会因为找不到 pending 而被丢弃
	}
}

func (c *Client) readLoop() {
	for {
		resp, err := c.readFrame()
		if err != nil {
			c.failAll(err) // 连接断开：通知所有等待者
			return
		}
		c.mu.Lock()
		ch := c.pending[resp.ID]
		c.mu.Unlock()
		if ch != nil {
			ch <- resp
		}
	}
}
```

**常见追问**

- 怎么支持多种序列化方式？→ 定义 `Codec` 接口（Marshal / Unmarshal），在协议头里标记使用的编码类型。
- 写操作需要加锁吗？→ 需要，多个 goroutine 同时写同一个连接会让帧交错；常见做法是一个专门的写 goroutine 从 channel 中取帧批量写出。
- 标准库的 `net/rpc` 为什么不推荐使用？→ 它已经冻结，不支持 context、只支持 gob 编码，生态和功能都很有限。

**实战建议**

- 除非有特殊需求，直接使用 gRPC 或者成熟的框架（Kitex、go-zero），把精力放在业务和治理策略上。
- 理解这些模块的原理，有助于排查使用框架时遇到的问题（连接数、超时、负载不均）。

**原理展开**

WebSocket 帧的格式：FIN 位（是否是消息的最后一帧）、opcode（文本、二进制、关闭、ping、pong）、掩码位和掩码（**客户端发往服务端的帧必须掩码**，防止缓存投毒攻击）、负载长度（7 位，或者扩展为 16 / 64 位）、负载数据。控制帧（ping / pong / close）可以穿插在分片的消息中间。

每个连接一读一写两个 goroutine 的原因：WebSocket 库通常不允许并发写（多个 goroutine 同时写会让帧交错），所以所有写操作都通过一个发送 channel 交给唯一的写 goroutine；读也只能有一个 goroutine。心跳由写 goroutine 定期发送 ping，读 goroutine 收到 pong 时延长读超时。

**代码示例**

```go
// 广播时不阻塞：发送 channel 满了就断开这个慢客户端
func (h *Hub) broadcast(msg []byte) {
	h.mu.RLock()
	var slow []*Client
	for c := range h.clients {
		select {
		case c.send <- msg:
		default:
			slow = append(slow, c)
		}
	}
	h.mu.RUnlock()
	for _, c := range slow {
		h.unregister(c) // 关闭 send channel，写 goroutine 退出并关闭连接
	}
}

// 升级时校验 Origin，防止跨站 WebSocket 劫持
var upgrader = websocket.Upgrader{
	ReadBufferSize:  1024,
	WriteBufferSize: 1024,
	CheckOrigin: func(r *http.Request) bool {
		return r.Header.Get("Origin") == "https://app.example.com"
	},
}
```

**常见追问**

- WebSocket 连接需要鉴权吗？→ 需要，在升级握手时校验 token（浏览器的 WebSocket API 不能自定义请求头，通常通过 Cookie 或查询参数传递，注意查询参数可能被记录在日志里）。
- 多个网关节点之间怎么推送？→ 维护“用户 → 节点”的路由表，或者所有节点订阅同一个消息总线（Redis Pub/Sub、NATS），各自推送给本地的连接。
- 消息压缩有必要吗？→ permessage-deflate 扩展可以压缩消息，但每个连接都要维护压缩上下文，内存开销大，大量连接时要谨慎。

**实战建议**

- 设置单条消息的最大大小（`SetReadLimit`），防止恶意的超大消息。
- 客户端断线重连要有指数退避和随机抖动，服务端发布时分批重启，避免重连风暴。

=== net-18
--- deep
**原理展开**

百万连接网关的核心矛盾是**连接数和每个连接的资源**。估算内存：每个连接（goroutine 栈 2～8KB × 2 + 读写缓冲 + TLS 状态 + 会话对象）约 20～50KB，百万连接就是 20～50GB，超出单机的合理范围。

几个关键的优化方向：

- **减少每个连接的常驻资源**：缓冲区只在有数据时从池里借用；写 goroutine 按需启动；会话对象精简字段；
- **减少 goroutine**：基于 epoll 的事件驱动网络库，少量 goroutine 处理所有连接的 IO 事件；
- **批量处理**：时间轮管理心跳；下行消息合并发送；
- **TLS 卸载**：在负载均衡层终止 TLS，网关只处理明文，节省 CPU 和内存（代价是内网明文）。

**代码示例**

```go
// 路由表：用户在哪个网关节点、哪个连接
func (g *Gateway) onConnect(ctx context.Context, uid string, connID string) error {
	return g.rdb.HSet(ctx, "route:"+uid, connID, g.nodeID).Err()
}

// 下行推送：业务服务查路由表，发到对应节点的 MQ 主题
func push(ctx context.Context, uid string, msg []byte) error {
	conns, err := rdb.HGetAll(ctx, "route:"+uid).Result() // 一个用户可能多端在线
	if err != nil {
		return err
	}
	for connID, node := range conns {
		if err := mq.Publish(ctx, "gateway."+node, encode(connID, msg)); err != nil {
			return err
		}
	}
	return nil
}
```

**常见追问**

- 网关宕机时怎么办？→ 客户端检测到断线后重连到其他节点，路由表随之更新；离线期间的消息通过序号补拉。
- 怎么做消息的可靠投递？→ 每条消息带递增序号，客户端 ACK；服务端保存未确认的消息，超时重发；客户端根据序号去重和发现缺失。
- 单机能承载多少连接？→ 取决于消息频率和每个连接的资源，空闲的长连接在优化后单机可以达到百万级；活跃度高时瓶颈在 CPU 和带宽。

**实战建议**

- 网关保持“薄”：只做连接和协议转换，业务逻辑放在后端服务里。
- 压测时同时关注连接数、内存、GC、重连风暴下的恢复时间。

=== net-19

**原理展开**

几种 MQ 的存储模型决定了它们的特点：

- **Kafka**：每个分区是一个**只追加的日志文件**，消息按偏移量存储，消费者自己记录读到哪里。顺序写磁盘 + 页缓存 + 零拷贝（sendfile）让它的吞吐非常高；消息在保留期内一直存在，可以回溯重新消费；
- **RabbitMQ**：消息被路由到**队列**，消费者确认后从队列中删除；交换机（direct、topic、fanout、headers）提供灵活的路由；单条消息的确认、拒绝、重新入队都很方便；
- **RocketMQ**：所有消息写入一个 CommitLog，再为每个队列建立索引（ConsumeQueue），支持事务消息（半消息 + 回查）、延迟消息、消息过滤；
- **NATS**：核心是一个非常轻量的发布订阅（至多一次），JetStream 在其上增加了持久化和至少一次投递。

**代码示例**

```go

w := &kafka.Writer{
	Addr:         kafka.TCP("kafka-1:9092", "kafka-2:9092"),
	Topic:        "orders",
	Balancer:     &kafka.Hash{},           // 按 key 哈希选择分区
	RequiredAcks: kafka.RequireAll,        // acks=all
	BatchTimeout: 10 * time.Millisecond,   // 攒批，提高吞吐
}
err := w.WriteMessages(ctx, kafka.Message{Key: []byte(orderID), Value: payload})

// 消费者组：手动提交偏移量
r := kafka.NewReader(kafka.ReaderConfig{
	Brokers: []string{"kafka-1:9092"},
	GroupID: "order-service",
	Topic:   "orders",
})
for {
	m, err := r.FetchMessage(ctx)
	if err != nil {
		break
	}
	if err := handle(ctx, m); err == nil {
		r.CommitMessages(ctx, m) // 处理成功后才提交
	}
}
```

**常见追问**

- Kafka 为什么快？→ 顺序写、页缓存、零拷贝、批量发送和压缩、分区并行。
- 需要延迟消息但用的是 Kafka 怎么办？→ 用多个延迟级别的主题 + 消费者检查时间后转发，或者借助外部的延迟队列（Redis ZSet）。
- 消息队列能代替数据库吗？→ 不能把它当作主存储；Kafka 可以作为事件溯源的事件日志，但查询还是需要其他存储。

**实战建议**

- 选型时先列出硬需求（吞吐、顺序、延迟消息、事务消息、回溯、运维能力），再对比。
- 团队已经熟悉并在运维某个 MQ 时，除非有明确的需求缺口，否则沿用它。

**原理展开**

**ISR**（同步副本集合）：和 leader 保持同步的副本集合。`acks=all` 表示消息写入 ISR 中的所有副本才算成功；`min.insync.replicas=2` 要求 ISR 至少有 2 个副本，否则写入失败（宁可不可用，也不丢数据）。副本落后太多（超过 `replica.lag.time.max.ms`）会被移出 ISR。

**幂等生产者**：生产者有一个 PID，每条消息带序列号，broker 记录每个 PID 在每个分区上的最大序列号，重复的序列号会被丢弃。它只能避免**生产者重试**导致的重复，进程重启后 PID 会变化。

**消费端重复的来源**：消费者处理完消息、还没提交偏移量就崩溃或者被踢出消费者组（处理时间超过 `max.poll.interval.ms` 会触发重新平衡），接手的消费者从上次提交的偏移量开始，重复处理这段消息。

**代码示例**

```go
// 消费端幂等：业务数据和“已处理消息”记录在同一个事务里
func handle(ctx context.Context, db *sql.DB, m kafka.Message) error {
	return WithTx(ctx, db, func(tx *sql.Tx) error {
		res, err := tx.ExecContext(ctx,
			"INSERT IGNORE INTO processed_messages (msg_id) VALUES (?)", msgID(m))
		if err != nil {
			return err
		}
		if n, _ := res.RowsAffected(); n == 0 {
			return nil // 已经处理过
		}
		return applyBusinessChange(ctx, tx, m)
	})
}

// 分区内按 key 并发：同一个 key 由同一个 worker 串行处理
workers := make([]chan kafka.Message, 8)
for i := range workers {
	workers[i] = make(chan kafka.Message, 100)
	go func(ch <-chan kafka.Message) {
		for m := range ch {
			_ = handle(ctx, db, m)
		}
	}(workers[i])
}
dispatch := func(m kafka.Message) {
	h := fnv.New32a()
	h.Write(m.Key)
	workers[h.Sum32()%uint32(len(workers))] <- m
}
```

（并发处理时，偏移量的提交需要用“连续完成”的方式，见「并发处理时安全地提交位点」任务。）

**常见追问**

- Kafka 的 exactly-once 是什么？→ 事务 + 幂等生产者，保证“从 Kafka 读、处理、写回 Kafka”整个过程恰好一次（Kafka Streams 使用），写到外部系统时不适用。
- 重新平衡会造成什么问题？→ 期间所有消费者暂停消费；处理慢的消费者被踢出后又重新加入，可能反复触发。CooperativeSticky 策略可以减少影响。
- 顺序消息的失败怎么处理？→ 不能跳过也不能放到队尾，只能原地重试（会阻塞这个分区）或者把这个 key 后续的消息都暂存起来。

**实战建议**

- “生产端不丢 + Broker 不丢 + 消费端先处理后提交 + 消费端幂等”四件事缺一不可。
- 监控消费延迟（lag）和重新平衡的频率。

**原理展开**

积压时首先要区分是**消费能力下降**还是**生产量增加**：

- 消费速率突然下降（同样的消费者数量，处理速度变慢）：通常是下游变慢、出现了处理失败一直重试的消息、或者新版本的 bug；
- 生产速率增加（活动、补数据、上游 bug 产生了大量消息）：需要扩容或者限流上游。

**毒消息**（poison message）：某条消息每次处理都失败（格式错误、触发了 bug），消费者不断重试，整个分区被堵住。处理方式是有限次数重试后把它转移到**死信队列**（DLQ），记录原因并告警，然后继续消费后面的消息。

**代码示例**

```go
// 有限重试 + 死信队列
func consume(ctx context.Context, m kafka.Message) error {
	var err error
	for attempt := range 3 {
		if err = handle(ctx, m); err == nil {
			return nil
		}
		if !retryable(err) {
			break
		}
		time.Sleep(time.Duration(attempt+1) * 200 * time.Millisecond)
	}
	slog.ErrorContext(ctx, "message to DLQ", "offset", m.Offset, "err", err)
	return dlqWriter.WriteMessages(ctx, kafka.Message{
		Key:   m.Key,
		Value: m.Value,
		Headers: append(m.Headers,
			kafka.Header{Key: "x-error", Value: []byte(err.Error())},
			kafka.Header{Key: "x-origin-offset", Value: []byte(strconv.FormatInt(m.Offset, 10))}),
	})
}
```

**常见追问**

- 积压的消息会丢吗？→ Kafka 中超过保留期（`retention.ms`）的消息会被删除，长时间积压可能导致数据丢失，必要时临时延长保留期。
- 扩容分区有什么副作用？→ 按 key 哈希的分区映射会改变，同一个 key 的新旧消息可能在不同分区，短时间内顺序被打乱。
- 过期的消息可以丢弃吗？→ 对于时效性强的消息（比如推送通知、实时位置），过期后处理已经没有意义，可以直接跳过以快速追上。

**实战建议**

- 消费延迟告警要同时看绝对值（积压条数）和趋势（是否在持续增长）。
- 提前准备好积压处理的预案（扩容步骤、跳过策略、转发工具），而不是事发时临时编写。
