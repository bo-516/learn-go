=== go-21
--- deep
**原理展开**

对齐规则来自硬件：CPU 按“字”读取内存，一个 8 字节的整数如果跨越了两个对齐边界，需要两次读取，有的架构甚至直接报错。所以编译器保证：

- 每个字段的地址是它**对齐系数**（`unsafe.Alignof`，通常等于自身大小，最大 8）的整数倍；
- 结构体的对齐系数是所有字段对齐系数的最大值，结构体大小向上取整到这个值的倍数，这样数组里的每个元素也能对齐。

**代码示例**

```go
type Event struct {
	Active bool      // 1 + 7 填充
	TS     int64     // 8
	Kind   uint8     // 1 + 3 填充
	Code   int32     // 4
	Name   string    // 16
}                    // 共 40 字节

type EventPacked struct {
	Name   string
	TS     int64
	Code   int32
	Kind   uint8
	Active bool      // 2 字节填充
}                    // 共 32 字节

fmt.Println(unsafe.Sizeof(Event{}), unsafe.Sizeof(EventPacked{})) // 40 32
fmt.Println(unsafe.Offsetof(Event{}.TS))                           // 8
```

一百万个 Event 就差了 8MB。

**常见追问**

- 字段顺序会影响序列化吗？→ JSON 输出的字段顺序会变，二进制协议（如自定义的 binary 编码）会受影响，要注意兼容性。
- 32 位平台上 int64 的对齐是多少？→ 只有 4 字节，所以 `atomic.AddInt64(&s.n, 1)` 在 32 位平台上可能因为未对齐而崩溃；`atomic.Int64` 类型内部做了对齐保证。
- 空结构体字段会占空间吗？→ 放在中间不占，放在末尾会被填充（见 go-14）。

**实战建议**

- 只对**大量实例**的结构体做字段重排，普通结构体按业务含义组织字段更易读。
- `fieldalignment -fix ./...` 可以自动重排，但会打乱字段的逻辑分组，建议只用来检查。

=== go-22

**原理展开**

`reflect.TypeOf` 拿到的是运行时的类型描述符（`*rtype`），里面有类型的种类、大小、字段列表、方法列表、tag 等信息，这些都是编译器写进二进制里的。`reflect.ValueOf` 则是（类型, 数据指针, 标志位）的组合，标志位记录了这个值是否可寻址、是否来自未导出字段等，决定了能否 `Set`、能否 `Interface()`。

反射慢的原因：每个操作都要做运行时的类型检查；值经常需要装箱成 `any`；编译器无法内联和优化；`Call` 调用函数要构造参数切片。

**代码示例**

```go
// 按类型缓存反射结果：只在第一次遇到某个类型时做反射
type fieldInfo struct {
	index int
	name  string
}

var cache sync.Map // reflect.Type -> []fieldInfo

func fieldsOf(t reflect.Type) []fieldInfo {
	if v, ok := cache.Load(t); ok {
		return v.([]fieldInfo)
	}
	var fs []fieldInfo
	for i := range t.NumField() {
		f := t.Field(i)
		if f.IsExported() {
			fs = append(fs, fieldInfo{i, f.Tag.Get("db")})
		}
	}
	v, _ := cache.LoadOrStore(t, fs)
	return v.([]fieldInfo)
}
```

`encoding/json` 内部就是这样按类型缓存编码器的。

**常见追问**

- 反射能修改未导出字段吗？→ 正常途径不能（`CanSet` 为 false），只能借助 unsafe 绕过，不要这样做。
- `reflect.DeepEqual` 有什么坑？→ nil 切片和空切片不相等；函数值只有都是 nil 才相等；会比较未导出字段；性能差。
- 有没有替代反射的方法？→ 代码生成（`go generate` + 模板），在编译期生成针对具体类型的代码，比如 easyjson、sqlc、wire。

**实战建议**

- 反射代码集中在框架和库的边界，业务代码里避免。
- 一定要缓存按类型计算的结果，并且在每次操作前检查 `Kind`，给出清楚的错误而不是 panic。

=== go-23
--- deep
**原理展开**

为什么 uintptr 不能保存：

1. **GC 不追踪**：只有 uintptr 引用对象时，GC 认为对象已经不可达，可能把它回收；
2. **栈会移动**：goroutine 的栈增长时会整体复制到新的位置，并更新所有**指针**；uintptr 只是整数，不会被更新，保存下来的地址就指向了旧栈。

`unsafe` 包文档列出了六种合法的使用模式（如 `*T1` ↔ `unsafe.Pointer` ↔ `*T2` 的转换、在同一表达式中的指针运算、调用 `syscall.Syscall` 时的转换等），超出这些模式的代码不保证正确。

**代码示例**

```go
type Header struct {
	Magic uint32
	Len   uint32
}

// 把字节切片按结构体解读（零拷贝），需要保证长度和对齐
func parseHeader(b []byte) (*Header, error) {
	if len(b) < int(unsafe.Sizeof(Header{})) {
		return nil, errors.New("short buffer")
	}
	return (*Header)(unsafe.Pointer(unsafe.SliceData(b))), nil
}

// 更安全、可移植的写法：encoding/binary
func parseHeaderSafe(b []byte) Header {
	return Header{
		Magic: binary.LittleEndian.Uint32(b[0:4]),
		Len:   binary.LittleEndian.Uint32(b[4:8]),
	}
}
```

第一种写法依赖机器的字节序和对齐，第二种在任何平台上都正确，而且编译器会把它优化成一次读取。

**常见追问**

- `reflect.Value.Pointer()` 返回 uintptr，怎么用？→ 只能用来做比较或者打印，不要转回指针；需要指针时用 `UnsafePointer()`（Go 1.18+）。
- `go vet` 能检查什么？→ `unsafeptr` 检查器能发现把 uintptr 转回 unsafe.Pointer 的可疑用法。
- 什么时候真的需要 unsafe？→ 与 C 或系统调用交互、极致性能的零拷贝、实现底层数据结构；业务代码基本用不到。

**实战建议**

- 使用 unsafe 的代码集中在一个小包里，写清楚前提条件，并有充分的测试（包括 `-race` 和 `GOEXPERIMENT=cgocheck2` 之类的检查）。
- 优先用 Go 1.17～1.20 新增的辅助函数：`unsafe.Add`、`unsafe.Slice`、`unsafe.String`、`unsafe.SliceData`、`unsafe.StringData`。

=== go-24
--- deep
**原理展开**

- `a + b + c`：编译器把一次表达式里的多个 `+` 合并成一次 `runtime.concatstrings` 调用，先算总长度、一次分配，结果不逃逸且很小时还会用栈上的缓冲区；
- 循环中的 `s += x`：每次都分配一个新字符串并复制已有内容，总复制量是 O(n²)；
- `strings.Builder`：内部 `[]byte` 按 append 的规则扩容，`String()` 用 unsafe 直接返回，不复制；它禁止被复制（内部有一个指向自己的指针，复制后再写入会 panic）；
- `fmt.Sprintf`：参数装箱成 `[]any`，解析格式串，通过反射处理每个参数，最灵活也最慢。

**代码示例**

```go
func BenchmarkConcat(b *testing.B) {
	parts := strings.Fields(strings.Repeat("go ", 100))
	b.Run("plus", func(b *testing.B) {
		for range b.N {
			s := ""
			for _, p := range parts {
				s += p
			}
		}
	})
	b.Run("builder", func(b *testing.B) {
		for range b.N {
			var sb strings.Builder
			for _, p := range parts {
				sb.WriteString(p)
			}
			_ = sb.String()
		}
	})
	b.Run("join", func(b *testing.B) {
		for range b.N {
			_ = strings.Join(parts, "")
		}
	})
}
// 典型结果：plus 比 builder 慢一个数量级，分配次数约 100 次 vs 几次
```

**常见追问**

- `bytes.Buffer` 和 `strings.Builder` 怎么选？→ 需要读（作为 `io.Reader`）或者需要 `Bytes()` 时用 Buffer；只是拼字符串用 Builder（`String()` 不复制）。
- 拼接少量字符串用 `+` 会慢吗？→ 不会，固定的几个 `+` 是最快的写法之一。
- `fmt.Sprint(n)` 和 `strconv.Itoa(n)` 差多少？→ 后者快好几倍且分配更少。

**实战建议**

- 循环里拼接用 Builder 或者先收集到切片再 `strings.Join`。
- 日志、指标这类热点路径用结构化的字段，而不是先 Sprintf 拼好再传进去（日志级别被过滤时就白拼了）。

**原理展开**

`encoding/json` 的编码过程：第一次遇到某个类型时，通过反射分析它的字段和 tag，生成一个编码函数并缓存起来；之后对同类型的值直接调用缓存的函数。解码时对每个 JSON 键，用大小写不敏感的方式匹配字段名（这是另一个容易被忽略的坑：`{"NAME": "x"}` 也能匹配 `json:"name"` 的字段）。

自定义编解码：实现 `json.Marshaler`（`MarshalJSON() ([]byte, error)`）和 `json.Unmarshaler`；只需要文本形式时，实现 `encoding.TextMarshaler` 也会被 JSON 使用（还能用作 map 的 key）。

**代码示例**

```go
// 自定义时间格式
type Date time.Time

func (d Date) MarshalJSON() ([]byte, error) {
	return []byte(`"` + time.Time(d).Format("2006-01-02") + `"`), nil
}

func (d *Date) UnmarshalJSON(b []byte) error {
	t, err := time.Parse(`"2006-01-02"`, string(b))
	if err != nil {
		return err
	}
	*d = Date(t)
	return nil
}

// 结构不固定的字段延迟解析
type Event struct {
	Type    string          `json:"type"`
	Payload json.RawMessage `json:"payload"`
}

func handle(e Event) error {
	switch e.Type {
	case "order":
		var o Order
		return json.Unmarshal(e.Payload, &o)
	}
	return nil
}
```

**常见追问**

- 为什么 `MarshalJSON` 用值接收者、`UnmarshalJSON` 用指针接收者？→ 编码时值和指针都能用；解码要修改自身，必须是指针。
- `omitempty` 对结构体字段有效吗？→ 无效，结构体永远不是“空”的；Go 1.24 新增的 `omitzero` 会检查零值（或者调用 `IsZero()` 方法）。
- 有 JSON v2 吗？→ Go 1.25 以实验的形式提供了 `encoding/json/v2`（`GOEXPERIMENT=jsonv2`），默认行为更严格（大小写敏感、拒绝重复的键等），性能也更好。

**实战建议**

- 对外 API 的结构体专门定义（DTO），不要直接序列化数据库模型，避免字段意外泄露。
- int64 的 ID 给前端时用字符串；接收不可信输入时限制请求体大小（`http.MaxBytesReader`）。

=== go-26
--- deep
**原理展开**

context 是一棵树：每次 `WithCancel` / `WithTimeout` 都创建一个子节点，并把它注册到最近的可取消祖先的 `children` 集合里。父节点被取消时，遍历 children 依次取消，取消信号就这样向下传播。`cancel()` 除了关闭 Done channel，还会把自己从父节点的 children 中移除，这就是为什么不调用 cancel 会“泄漏”：子节点一直挂在父节点上，直到父节点结束。

`WithValue` 创建的节点只保存一个 key/value 和父节点指针，`Value(key)` 沿着父链向上逐个比较，所以是 O(深度)。

**代码示例**

```go
// 请求结束后还要继续执行的任务：脱离父 context 的取消，但保留其中的值
func handler(w http.ResponseWriter, r *http.Request) {
	// ... 处理请求 ...
	bg := context.WithoutCancel(r.Context()) // Go 1.21+，保留 trace ID 等值
	go func() {
		ctx, cancel := context.WithTimeout(bg, 5*time.Second)
		defer cancel()
		_ = audit.Record(ctx, "order.created")
	}()
}

// context 取消时执行回调（Go 1.21+）
stop := context.AfterFunc(ctx, func() {
	conn.SetDeadline(time.Now()) // 让阻塞中的读写立即返回
})
defer stop()

// 带原因的取消（Go 1.20+）
ctx, cancel := context.WithCancelCause(parent)
cancel(errors.New("upstream closed"))
fmt.Println(context.Cause(ctx)) // upstream closed
```

**常见追问**

- 子 context 的超时能比父 context 更长吗？→ 设置了也没用，截止时间取两者中较早的那个。
- context 是并发安全的吗？→ 是，可以传给多个 goroutine。
- 为什么不要把 context 存进结构体？→ context 的生命周期应该和一次请求或操作绑定，存进长期存在的结构体后，就分不清它代表哪次操作，也容易用到已经取消的 context。

**实战建议**

- 所有可能阻塞的函数（IO、RPC、数据库、等待锁）的第一个参数都是 ctx。
- 在循环、长任务中定期检查 `ctx.Err()`，让取消能及时生效。

=== go-27
--- deep
**原理展开**

逃逸分析是在编译期对每个函数做的**数据流分析**：构建一张“谁的地址被赋给了谁”的图，如果某个变量的地址能流到函数外部（返回值、全局变量、堆上的对象、其他 goroutine），或者编译器无法确定它的去向，它就必须分配在堆上。

几个不那么直观的点：

- 编译器是**保守**的：无法证明安全就放到堆上；
- 函数调用跨越了编译单元，或者通过接口、函数值调用时，编译器看不到被调用的函数会不会保存指针，只能假设会；
- **内联**能让逃逸分析看到被调用函数的内部，所以内联常常能消除逃逸；
- 栈上的变量最大也有限制（如超过 64KB 的 make 会放到堆上）。

**代码示例**

```go
// 逃逸：返回局部变量的地址
func newBuf() *bytes.Buffer { return &bytes.Buffer{} }

// 不逃逸：由调用方提供内存
func fill(buf *[64]byte, n int) []byte {
	for i := range n {
		buf[i] = byte(i)
	}
	return buf[:n]
}

func caller() {
	var b [64]byte
	data := fill(&b, 10) // b 在 caller 的栈上
	_ = data
}
```

```bash
go build -gcflags='-m=2' . 2>&1 | grep -E 'escapes|moved to heap'
```

**常见追问**

- 栈上分配为什么快？→ 只需要移动栈指针，函数返回时整体回收，不产生任何 GC 负担。
- 大量小对象逃逸有什么影响？→ 分配本身有开销，更大的影响是增加 GC 频率和标记工作量。
- `sync.Pool` 和逃逸分析的关系？→ 对象必然逃逸、又频繁创建时，用 Pool 复用，减少分配次数。

**实战建议**

- 先用 `-benchmem` 和 pprof 的 `alloc_space` 找到分配热点，再看 `-gcflags=-m` 的输出找原因。
- 常见的优化手法：返回值而不是指针、调用方传入缓冲区（像 `io.Reader.Read(p)` 那样）、避免在热路径上使用 `any`。

=== go-28
--- deep
**原理展开**

内联的代价模型：编译器为每个函数计算一个“开销”（大致是语法树节点数），低于预算（80）的函数可以被内联；包含某些结构（如 `select`、`defer`（早期版本）、`recover`、闭包调用）的函数可能不能内联。Go 1.12 起支持“中间栈内联”：被内联的函数自己也可以调用其他函数。

**PGO**（Profile-Guided Optimization）：编译器读取 CPU profile，知道哪些调用点是热点，对它们放宽内联预算；对热点的接口调用，如果 profile 显示大多数时候是某个具体类型，生成“类型判断 + 直接调用”的快速路径（去虚拟化）。

**代码示例**

```bash
# 查看内联决策
go build -gcflags='-m' ./... 2>&1 | grep -E 'can inline|inlining call'

# PGO：从生产环境抓 profile，放在 main 包目录
curl -o default.pgo 'http://host:6060/debug/pprof/profile?seconds=30'
go build ./cmd/server   # Go 1.21+ 默认会读取 main 包目录下的 default.pgo
```

```go
// 边界检查消除：提前访问最后一个元素，后面的访问编译器就知道不会越界
func sum4(s []int) int {
	_ = s[3] // 只检查一次
	return s[0] + s[1] + s[2] + s[3]
}
```

**常见追问**

- 内联会让二进制变大吗？→ 会，所以有预算限制；PGO 只对热点放宽，整体增长有限。
- `//go:noinline` 什么时候用？→ 写基准测试或者演示逃逸时，防止编译器把要测的东西优化掉；业务代码不要用。
- 编译器还有哪些常见优化？→ 常量折叠、死代码消除、边界检查消除、nil 检查消除、逃逸分析、开放编码的 defer。

**实战建议**

- 不要为了内联手工把函数拆小或者合并，先写清楚的代码，用 profile 找瓶颈。
- 生产服务可以考虑 PGO：用真实流量的 profile，收益通常在几个百分点，成本几乎为零。

=== go-29
--- deep
**原理展开**

一次 cgo 调用要做的事情：保存 Go 的上下文，切换到系统栈（C 代码不能在可增长的 goroutine 栈上运行），调用 `entersyscall` 通知调度器“这个 M 要去执行外部代码了”（之后 P 可能被别的 M 拿走），执行 C 函数，返回时再 `exitsyscall` 重新获取 P。这一套下来约几十纳秒，是普通 Go 函数调用的几十倍。

C 调用 Go（回调）更贵，需要把线程注册给 Go 运行时。

**代码示例**

```go
/*
#include <stdlib.h>
#include <string.h>
static size_t c_len(const char* s) { return strlen(s); }
*/
import "C"
import "unsafe"

func Len(s string) int {
	cs := C.CString(s)              // 在 C 堆上分配并复制，必须手动释放
	defer C.free(unsafe.Pointer(cs))
	return int(C.c_len(cs))
}
```

批量化：与其对一百万个元素各调用一次 C 函数，不如传一个数组进去，在 C 那边循环（见 GO-29 任务）。

**常见追问**

- C 代码里能保存 Go 的指针吗？→ 不能在调用返回后继续持有；需要长期关联 Go 对象时用 `runtime/cgo.Handle` 传一个整数句柄。
- 怎么检查指针传递是否合法？→ 运行时默认开启 `GODEBUG=cgocheck=1` 做基本检查，`GOEXPERIMENT=cgocheck2` 更严格（有性能开销）。
- `CGO_ENABLED=0` 有什么影响？→ 得到纯静态二进制，适合 scratch / distroless 镜像；`net` 包会使用纯 Go 的 DNS 解析器，`os/user` 等包使用纯 Go 的实现。

**实战建议**

- 在 Docker 多阶段构建里显式设置 `CGO_ENABLED=0`，避免因为基础镜像不同导致二进制在运行时找不到 libc。
- 必须用 cgo 时，限制并发调用数（见「限制阻塞调用的并发数」），并监控线程数和 RSS。
