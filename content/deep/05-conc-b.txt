=== conc-13
--- deep
**原理展开**

原子操作的两层含义：

1. **不可分割**：读-改-写在硬件层面一次完成（x86 上带 LOCK 前缀的指令会锁住对应的缓存行）；
2. **内存顺序**：Go 的原子操作是**顺序一致**的，原子写之前的所有内存操作，对后续读到这次写入的 goroutine 都可见。这让原子变量可以用来“发布”数据，比如写时复制的配置指针。

原子操作也有成本：一次原子加约几纳秒到几十纳秒，多个核心频繁写同一个原子变量时，缓存行在核心之间来回传递，性能会急剧下降。所以高并发计数通常要**分片**。

**代码示例**

```go
// 分片计数器：每个 P 大致写自己的槽位，读取时求和
type ShardedCounter struct {
	shards [64]struct {
		n atomic.Int64
		_ [56]byte // 避免伪共享
	}
}

func (c *ShardedCounter) Add(delta int64) {
	i := fastrand() % 64 // 或者按 goroutine / P 选择
	c.shards[i].n.Add(delta)
}

func (c *ShardedCounter) Load() (sum int64) {
	for i := range c.shards {
		sum += c.shards[i].n.Load()
	}
	return
}

func fastrand() uint32 { return uint32(rand.Uint64()) }

// CAS 循环实现“更新为最大值”
func storeMax(v *atomic.Int64, x int64) {
	for {
		old := v.Load()
		if x <= old || v.CompareAndSwap(old, x) {
			return
		}
	}
}
```

**常见追问**

- `atomic.Value` 和 `atomic.Pointer[T]` 怎么选？→ 新代码用 `atomic.Pointer[T]`，有类型检查；`atomic.Value` 要求每次 Store 的类型一致，否则 panic。
- 原子操作能保护多个字段吗？→ 不能，需要的话把多个字段放进一个结构体，用 `atomic.Pointer` 整体替换。
- 读多写少的计数器还需要原子读吗？→ 需要，普通读和原子写混用就是数据竞争。

**实战建议**

- 默认用 Mutex，只有简单的计数器、标志位、指针发布才用原子操作。
- 极高频的计数（每秒数百万次）用分片计数，或者每个 goroutine 本地累加后定期合并。

**原理展开**

errgroup 的实现非常短：一个 WaitGroup、一个 `sync.Once` 记录第一个错误、一个可选的 cancel 函数，以及 SetLimit 时用的信号量 channel。`Go` 方法在启动前先获取信号量（达到上限时**阻塞**），goroutine 结束时释放；`Wait` 等待所有任务后调用 cancel 并返回第一个错误。

需要注意的几点行为：

- 出错后**不会自动停止其他任务**，只是取消 ctx，其他任务必须自己检查 ctx 才能提前退出；
- `Wait` 之后 ctx 一定已经被取消，所以不能在 Wait 之后继续用这个 ctx 发起新请求；
- `SetLimit` 之后的 `Go` 会阻塞调用方，可以用 `TryGo` 非阻塞地尝试。

**代码示例**

```go
// 流水线：一个阶段产出，另一个阶段并发处理，任一出错整体取消
func process(ctx context.Context, ids []int64) error {
	g, ctx := errgroup.WithContext(ctx)
	items := make(chan Item)

	g.Go(func() error {
		defer close(items)
		for _, id := range ids {
			it, err := load(ctx, id)
			if err != nil {
				return err
			}
			select {
			case items <- it:
			case <-ctx.Done():
				return ctx.Err()
			}
		}
		return nil
	})

	for range 4 {
		g.Go(func() error {
			for it := range items {
				if err := save(ctx, it); err != nil {
					return err
				}
			}
			return nil
		})
	}
	return g.Wait()
}
```

**常见追问**

- 怎么拿到所有错误而不只是第一个？→ 自己用 WaitGroup，每个任务把错误写到切片的对应位置，最后 `errors.Join`。
- errgroup 里的 panic 会怎样？→ 不会被 recover，会让进程崩溃；需要时在任务函数里自己 recover 并转换成 error。
- 不需要取消时可以用零值的 `errgroup.Group` 吗？→ 可以，`var g errgroup.Group` 直接使用。

**实战建议**

- 并发调用多个下游组装页面数据，是 errgroup 最典型的场景。
- 记得把 `WithContext` 返回的 ctx 传给每个任务，而不是外层的 ctx。

**原理展开**

singleflight 的核心数据结构是 `map[string]*call`，每个 call 有一个 WaitGroup 和结果字段。第一个调用者创建 call、执行函数；后来者找到已有的 call 就 `Wait`。函数执行完后从 map 中删除这个 key，之后的调用会重新执行。

它解决的是“**同一时刻**的重复请求”，不是缓存：函数一结束，结果就不再保留。所以它通常和缓存配合使用：缓存命中直接返回，未命中时通过 singleflight 回源。

**代码示例**

```go
// 带超时的等待：第一个调用卡住时，后来者不会被一起拖住
func get(ctx context.Context, key string) (any, error) {
	ch := sf.DoChan(key, func() (any, error) {
		// 用独立的超时，避免第一个调用者的取消影响所有人
		ctx, cancel := context.WithTimeout(context.WithoutCancel(ctx), 2*time.Second)
		defer cancel()
		return loadFromDB(ctx, key)
	})
	select {
	case r := <-ch:
		return r.Val, r.Err
	case <-ctx.Done():
		return nil, ctx.Err()
	}
}
```

**常见追问**

- 返回值里的 `shared` 有什么用？→ 表示结果被多个调用者共享。如果结果是可变的对象（指针、切片），共享者之间修改会互相影响，需要复制。
- 多实例部署时还会击穿吗？→ 每个实例各回源一次，N 个实例就是 N 次，通常可以接受；要求更严格时用分布式锁或者缓存预热、逻辑过期（缓存不过期，后台异步刷新）。
- 函数 panic 时等待者会怎样？→ 官方实现会把 panic 传播给所有等待者（重新 panic），防止它们永远阻塞。

**实战建议**

- 热点数据的缓存访问统一封装成“缓存 + singleflight + 回源”的组合函数。
- key 要包含所有影响结果的参数，否则不同参数的请求会拿到同一个结果。

**原理展开**

几个值得注意的实现细节：

- **直接交接**：有接收者在等待时，发送方直接把数据复制到接收者的栈上（`sendDirect`），这是运行时少有的“写别的 goroutine 的栈”的地方，所以这里需要特殊的写屏障处理。

- **唤醒后的处理**：被唤醒的 goroutine 由 `goready` 放进唤醒者所在 P 的 `runnext`，优先运行，提高缓存局部性。
- **零大小元素**：`chan struct{}` 不需要缓冲区内存，只用计数。

**代码示例**

```go
// 用 channel 实现的互斥锁：容量为 1 的 channel
type ChanMutex chan struct{}

func NewChanMutex() ChanMutex     { return make(ChanMutex, 1) }
func (m ChanMutex) Lock()         { m <- struct{}{} }
func (m ChanMutex) Unlock()       { <-m }

// 它的优势：可以和超时、取消组合
func (m ChanMutex) LockContext(ctx context.Context) error {
	select {
	case m <- struct{}{}:
		return nil
	case <-ctx.Done():
		return ctx.Err()
	}
}
```

**常见追问**

- channel 是 FIFO 的吗？→ 缓冲区是 FIFO；等待的发送者和接收者也按 FIFO 排队唤醒。
- 为什么说 channel 适合“所有权转移”？→ 发送之后发送方不再使用这个对象，接收方独占它，天然避免了共享和竞争。
- 一个 channel 能被多个 goroutine 同时读吗？→ 能，每个值只会被其中一个接收者拿到，这就是 worker 池的工作方式。

**实战建议**

- 用 channel 编排流程（流水线、扇入扇出、信号通知），用锁保护共享状态，不要反过来。
- 用 channel 传递大对象时传指针，避免每次复制整个对象。

=== conc-17
--- deep
**原理展开**

为什么“由发送方关闭”：关闭是向接收方传递“不会再有数据了”的信号，只有发送方知道这件事。接收方关闭 channel 时，发送方可能正在发送，会 panic。

多个发送方时，任何一个发送方都不知道其他发送方是否还会发送，所以需要一个知道全局情况的**协调者**：它等待所有发送方结束（WaitGroup），然后关闭。

反方向的通知（消费者让生产者停止）用另一个信号：`done` channel 或者取消 ctx。生产者在发送时 select 这个信号，收到后退出，最终由协调者关闭数据 channel。

**代码示例**

```go
// 消费者遇到错误时通知所有生产者停止
func run(ctx context.Context) error {
	ctx, cancel := context.WithCancel(ctx)
	defer cancel()

	data := make(chan int)
	var prod sync.WaitGroup
	for i := range 3 {
		prod.Add(1)
		go func() {
			defer prod.Done()
			for n := i; ; n += 3 {
				select {
				case data <- n:
				case <-ctx.Done():
					return
				}
			}
		}()
	}
	go func() { prod.Wait(); close(data) }()

	for v := range data {
		if v > 100 {
			cancel() // 通知生产者停止；继续 range 把 channel 读完
		}
	}
	return nil
}
```

注意 cancel 之后消费者仍然要把 channel 读到关闭，否则已经在发送中的生产者可能阻塞（这里生产者的 select 也监听了 ctx，不会阻塞）。

**常见追问**

- 可以用 recover 捕获“向已关闭的 channel 发送”的 panic 吗？→ 技术上可以，但这是在掩盖设计问题。
- 怎么判断 channel 是否已经关闭？→ 没有不读取就能判断的方法；需要这个信息说明设计上应该用别的信号。
- `sync.Once` 包装 close 能解决多发送方问题吗？→ 只能防止重复关闭，防不住“关闭后还有人发送”。

**实战建议**

- 画出每个 channel 的所有发送方、接收方和关闭方，确保关闭方唯一且在所有发送结束之后。
- 优先使用 errgroup + ctx 组织多生产者多消费者，取消和等待都更容易写对。

=== conc-18

**原理展开**

ThreadSanitizer 为每个 8 字节的内存单元维护若干“影子单元”，记录最近访问它的线程（goroutine）、访问时的逻辑时钟以及读写类型。每个 goroutine 有一个**向量时钟**，同步操作（channel、锁、原子操作）会合并双方的向量时钟，建立 happens-before 关系。每次内存访问时，检查影子单元里的历史访问：如果有一次来自其他 goroutine、两者之间没有 happens-before 关系、并且至少一次是写，就报告数据竞争。

所以它没有误报（报出来的一定是真正的竞争），但会漏报（只检查实际执行到的访问，而且影子单元数量有限，很久以前的访问可能被覆盖）。

**代码示例**

```bash
go test -race ./...                    # 所有测试开启竞态检测
go build -race -o app-race ./cmd/app   # 构建带检测的二进制
GORACE="halt_on_error=1 log_path=/tmp/race" ./app-race
```

典型报告：

```text
WARNING: DATA RACE
Write at 0x00c0000a4010 by goroutine 8:
  main.(*Stats).Inc()  /app/stats.go:12 +0x3c
Previous read at 0x00c0000a4010 by goroutine 7:
  main.(*Stats).Get()  /app/stats.go:16 +0x2e
```

两个调用栈分别指出了冲突的写和读的位置。

**常见追问**

- 测试通过了就说明没有竞争吗？→ 不是，只说明测试执行到的路径上没有发现；要让测试真正并发地执行代码（多个 goroutine、多次迭代）。
- 有“良性”的数据竞争吗？→ 在 Go 内存模型下没有，任何数据竞争都可能导致不可预测的结果（比如读到撕裂的值），必须修复。
- 竞态检测支持哪些平台？→ 主流的 linux/amd64、linux/arm64、darwin、windows 都支持，需要开启 cgo。

**实战建议**

- CI 必须跑 `-race`；对并发相关的代码写专门的压力测试（多 goroutine + `-count=100`）。
- 预发环境可以部署一两个 race 版本的实例，跑一段真实流量。

**原理展开**

内存模型解决的问题：编译器和 CPU 都会为了性能**重排**内存操作（只要单个线程内看起来结果不变），并且每个核心有自己的缓存和写缓冲区。所以在没有同步的情况下，一个 goroutine 写入的顺序，另一个 goroutine 可能以不同的顺序看到，甚至一直看不到。

双重检查锁的问题：`instance = &Obj{...}` 包含“分配内存、初始化字段、写入指针”几步，没有同步时，另一个 goroutine 可能先看到指针被写入、后看到字段被初始化，于是拿到一个“半初始化”的对象。

Go 1.19 的内存模型明确：没有数据竞争的程序（所有共享访问都有同步）表现得像顺序一致的（DRF-SC）；有数据竞争的程序，结果不可预测，但不会像 C++ 那样整个程序都是未定义行为（不会“凭空产生”值）。

**代码示例**

```go
// 正确：atomic.Pointer 的 Store/Load 建立了 happens-before
var instance atomic.Pointer[Obj]
var mu sync.Mutex

func Get() *Obj {
	if p := instance.Load(); p != nil {
		return p // 能看到完整初始化的对象
	}
	mu.Lock()
	defer mu.Unlock()
	if p := instance.Load(); p != nil {
		return p
	}
	p := &Obj{ /* ... */ }
	instance.Store(p)
	return p
}

// 更简单：
var getObj = sync.OnceValue(func() *Obj { return &Obj{ /* ... */ } })
```

**常见追问**

- 哪些操作建立 happens-before？→ channel 发送先于对应的接收完成；关闭先于收到零值的接收；无缓冲 channel 的接收先于发送完成；Unlock 先于下一次 Lock；Once 的 f 返回先于所有 Do 返回；原子写先于读到它的原子读。
- `go` 语句呢？→ `go` 语句先于新 goroutine 开始执行；但 goroutine 的退出不与任何操作同步，必须用 WaitGroup 等方式等待。
- 用 `time.Sleep` 等待可以吗？→ 不可以，sleep 不建立任何 happens-before 关系。

**实战建议**

- 共享变量的每一次访问（读和写）都要经过同步原语，没有例外。
- 不要自己发明同步机制，用 `sync`、`sync/atomic`、channel 提供的标准方式。

Go 的定时器由运行时管理：每个 P 有一个按到期时间排序的四叉堆，调度器在调度循环和 sysmon 中检查到期的定时器。`time.After(d)` 等价于 `time.NewTimer(d).C`，返回 channel 后定时器对象本身就无法再被访问（不能 Stop）。

	}

	}

CPU 的缓存一致性协议（如 MESI）以缓存行为单位：一个核心写某个缓存行时，其他核心中这一行的副本都会失效，它们下次访问要重新从更低一级的缓存或内存加载。两个核心交替写同一行里的不同变量，这一行就在它们之间不停地来回“搬家”，每次写都变成了一次跨核通信，性能可能下降一个数量级。

**原理展开**

内存的估算：每个连接如果有读写两个 goroutine（各至少 2KB 栈，实际运行中常增长到 8KB）、读缓冲区 4KB、写缓冲区 4KB，再加上 TLS 状态、连接对象本身，每个连接 20～30KB，百万连接就是 20～30GB。

优化的核心思路是“**只为活跃的连接分配资源**”：大多数长连接大部分时间是空闲的，读缓冲区可以在有数据可读时才从池中获取；写 goroutine 可以在有消息要发送时才启动；心跳不需要每个连接一个定时器。

**代码示例**

```go
// 按需获取读缓冲区：空闲连接不持有缓冲区
func (c *Conn) readLoop() {
	for {
		// 先用很小的缓冲区等待数据（或者用 netpoll 的回调），
		// 有数据可读时再从池中拿大缓冲区
		if err := c.waitReadable(); err != nil {
			return
		}
		buf := bufPool.Get().(*[]byte)
		n, err := c.conn.Read(*buf)
		c.handle((*buf)[:n])
		bufPool.Put(buf)
		if err != nil {
			return
		}
	}
}
```

（`waitReadable` 在标准库里没有直接的 API，这正是 gnet、netpoll 这类库要解决的问题：它们暴露“连接可读”的事件。）

**常见追问**

- epoll 模型和 goroutine-per-connection 模型怎么选？→ 连接数在十万级以内，标准库的模型通常足够，代码更简单；百万级的长连接网关才值得引入事件驱动库。
- 内核参数要调哪些？→ `fs.file-max`、`fs.nr_open`、`ulimit -n`，`net.ipv4.tcp_mem` / `tcp_rmem` / `tcp_wmem`，`net.core.somaxconn`，以及端口范围（作为客户端时）。
- 怎么测试百万连接？→ 需要多台压测机（每个源 IP 最多约 6 万个端口），或者给压测机配置多个 IP。

**实战建议**

- 先测量：在目标连接数下观察每个连接的实际内存、GC 耗时、调度延迟，再决定优化方向。
- 连接状态尽量小、尽量放在连续的内存里（比如数组 + 下标），减少 GC 扫描的指针数量。

**原理展开**

运行时只能检测“**所有** goroutine 都阻塞”的全局死锁：调度器发现没有可运行的 goroutine、也没有等待中的网络 IO 和定时器时报错。只要还有一个 goroutine 在运行（比如 HTTP 服务的 accept 循环、一个后台 ticker），部分 goroutine 之间的死锁就不会被检测到，表现为请求挂起、goroutine 数量增长、连接池耗尽。

死锁的四个必要条件：互斥、持有并等待、不可抢占、循环等待。实践中最容易打破的是“循环等待”（固定加锁顺序）和“持有并等待”（一次获取所有需要的锁，或者获取失败时释放已持有的锁）。

// 避免锁内调用外部代码：先复制需要的数据，释放锁后再调用
func (s *Subject) notify() {
	s.mu.Lock()
	observers := slices.Clone(s.observers)
	s.mu.Unlock()
	for _, o := range observers {
		o.OnChange() // 回调里如果再调用 s 的方法，也不会死锁
	}
}

**常见追问**

- channel 也会死锁吗？→ 会，比如两个 goroutine 互相等待对方先发送；或者无缓冲 channel 的发送方和接收方在同一个 goroutine 里。
- 怎么在测试中发现死锁？→ 给测试设置超时（`go test -timeout 30s`），超时时测试框架会打印所有 goroutine 的栈。
- 有没有死锁检测工具？→ 第三方的 `go-deadlock` 可以替换 sync.Mutex，检测加锁顺序的不一致和长时间的等待（只适合测试环境）。

**实战建议**

- 一个锁只保护一组明确的数据，锁的数量越少、关系越简单越好。
- 设计接口时避免“持有锁时调用用户提供的回调”，这是死锁最常见的来源之一。
