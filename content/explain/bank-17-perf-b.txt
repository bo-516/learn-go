**思路**

“优化”必须用数据证明。基准测试测量每次操作的耗时和分配次数，优化前后各跑多次，用 `benchstat` 做统计比较，才能判断差异是真实的还是噪声。

=== perf-18-1
--- explain
**思路**

OOM 常常是突发的：一批大请求同时到达，每个都把大量数据加载进内存。与其等着被 OOM Killer 杀掉（所有请求一起失败、服务重启），不如给“正在处理中的数据量”设一个**内存预算**：超过预算的请求直接拒绝，返回 503 让客户端稍后重试。这是一种**背压**（backpressure）。

**代码讲解**

1. `used`、`limit` 用 Mutex 保护。
2. `TryAcquire(n)`：`b.used+n > b.limit` 时拒绝，否则占用。判断和占用在同一个临界区里，保证不会超额。
3. `Release(n)`：处理完成后释放。调用方通常写成 `if !b.TryAcquire(size) { return 503 }; defer b.Release(size)`。

**易错点**

- 先判断后占用（两次加锁）：并发时多个请求同时通过判断，总量超过预算。
- 单个请求就超过整个预算时它永远无法成功，应该在更早的地方用请求大小限制（`http.MaxBytesReader`）拒绝。
- 排查 OOM：`dmesg` 看 OOM Killer 的记录；对比 heap profile 和 RSS（见「RSS 为什么不下降」）；`GOMEMLIMIT` 设置在容器限制的 80%～90%，让 GC 在接近上限时更积极地回收。

--- explain
**思路**

服务端关闭了空闲连接（发送 FIN），客户端这一侧的连接就进入 **CLOSE_WAIT**，直到客户端程序调用 Close。这里的 bug 是只取了状态码、没有关闭响应体：连接既没有放回连接池复用，也没有被关闭，就一直停留在 CLOSE_WAIT。

**代码讲解**

1. `client.Get(url)` 出错时 `resp` 为 nil，直接返回。
2. `defer resp.Body.Close()`：任何返回路径都会关闭。
3. `io.Copy(io.Discard, io.LimitReader(resp.Body, 64<<10))`：把剩余的响应体读完（最多 64KB）。HTTP/1.1 的连接只有在响应体**被完整读取并关闭**后才能放回连接池；只关闭不读完，Transport 会直接关闭这个连接，下次请求要重新建连。
4. 限制最多读 64KB：如果对方返回了一个巨大的响应体，没必要全部读完，直接关闭连接更划算。

**易错点**

- 测试统计服务端看到的新连接数：正确的实现在 20 次顺序调用中只建立 1 个连接。
- 排查 CLOSE_WAIT：`ss -tanp state close-wait` 找到进程和对端地址，确定是哪个下游的连接，然后检查调用它的代码有没有在所有分支上关闭响应体。

**思路**

- **502 Bad Gateway**：网关没有从上游拿到有效的响应（连接被拒绝、被重置）。
- **504 Gateway Timeout**：网关等上游响应超时了。

偶发 502 的经典原因：负载均衡器和后端之间使用长连接，后端的空闲超时比 LB 的**短**。后端先关闭了空闲连接，LB 不知道，恰好在这个连接上转发请求，收到 RST，返回 502。所以后端的 `IdleTimeout` 必须**大于** LB 的空闲超时，让关闭总是由 LB 发起。

1. `CheckIdle`：`backendIdle <= lbIdle` 时返回错误，错误信息里用 `%v` 打印两个时长。
2. `Classify` 用无条件 switch 按顺序判断：
   - 上游状态为 `-` 表示没有收到上游的响应；耗时达到代理超时就是 504，否则是连接被重置（502）；
   - 上游返回了 5xx：问题在上游服务本身；
   - 其他正常。

**易错点**

- 常见的默认值：AWS ALB 空闲超时 60 秒、Nginx 的 `keepalive_timeout` 75 秒；Go `http.Server` 的 `IdleTimeout` 不设置时使用 `ReadTimeout`（如果设置了的话）。
- 504 的排查方向是上游为什么慢：看上游的慢日志、依赖的数据库和下游、是否有 GC 停顿或 CPU 限流。

=== perf-26-1
--- explain
**思路**

容器的 CPU limit 是通过 CFS 带宽控制实现的：每个周期（默认 100ms）最多使用 `limit × 100ms` 的 CPU 时间，用完了这个周期剩下的时间里**所有线程都会被暂停**（throttle）。Go 程序的 GOMAXPROCS 如果大于 CPU limit（比如在 64 核机器上 limit 是 2 核），多个线程并行运行，可能在周期的前 30ms 就用完了配额，然后被暂停 70ms，表现为平均 CPU 使用率不高、延迟却周期性飙升。

**代码讲解**

1. `ParseCPUStat`：每行两个字段，`ParseInt` 解析值，格式不对返回错误。
2. `Throttle` 用命名返回值 `(ratio float64, avg time.Duration)`。
3. 两次采样的增量：被限流的周期数 / 总周期数 = 限流比例；被限流的总时长 / 被限流的次数 = 每次平均被暂停多久。
4. `time.Duration(usec/throttled) * time.Microsecond`：微秒数转成 Duration。

**易错点**

- 解决方法：让 GOMAXPROCS 与 CPU limit 匹配（Go 1.25 自动处理，之前用 `automaxprocs`）；或者适当提高 limit；有些团队干脆只设置 request 不设置 limit。
- 只看 CPU 使用率的平均值发现不了限流问题，一定要看 `nr_throttled` 和 `throttled_usec`（或者 Prometheus 的 `container_cpu_cfs_throttled_periods_total`）。

=== perf-28-1
--- explain
**思路**

eBPF 可以在内核里安全地运行小程序：在事件发生的地方（磁盘 IO 完成、调度、TCP 重传）直接统计，把延迟按 **2 的幂**分桶计数，只把几十个桶的计数传回用户态，所以开销极低，可以在生产环境长时间运行。bcc 工具集里的 `biolatency`、`runqlat`、`tcpretrans` 都是这样实现的。

**代码讲解**

1. `bits.Len64(v)` 返回表示 v 需要的二进制位数，`Len64(v) - 1` 就是最高位的位置，即 `floor(log2(v))`。0 和 1 都放在第 0 个桶。
2. `for len(counts) <= k { counts = append(counts, 0) }`：按需扩展，中间的空桶也会被创建。
3. 桶的范围：第 k 个桶是 `[2^k, 2^(k+1) − 1]`，`uint64(1) << k`；第 0 个桶特殊处理，下界是 0。`uint64(1)<<(k+1) - 1`：`<<` 优先级高于 `-`。
4. `Render`：先求最大计数；星号数 = `Count × width / maxCount`（整数除法）；`strings.Repeat` 生成星号和补齐用的空格。
5. `fmt.Fprintf(&sb, ...)`：`*strings.Builder` 实现了 `io.Writer`；`%-8d` 左对齐、`%8d` 右对齐。

**易错点**

- 对数分桶的精度有限（每个桶的上下界相差一倍），但足以看出延迟分布的形状：是一个峰还是两个峰（比如缓存命中和未命中）。
- 常用的 eBPF 工具：`execsnoop`（新进程）、`opensnoop`（打开的文件）、`biolatency`（磁盘延迟）、`runqlat`（调度延迟）、`tcpretrans`（重传）、`offcputime`（线程在等什么）。
