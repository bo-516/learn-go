=== db-01-1
--- explain
**思路**

每个 key 一把锁，由一个全局的 map 管理。两个要点：

1. **等待某一行的锁时不能持有全局锁**，否则一行被锁住，所有其他行的加锁请求都会卡在全局锁上，行锁就退化成了表锁；
2. 锁对象要能被回收：用**引用计数**记录“持有 + 等待”这把锁的人数，降到 0 时从 map 中删除。

**代码讲解**

1. `entry` 包含真正的行锁 `mu` 和引用计数 `refs`；`locks map[string]*entry` 存指针，保证大家拿到的是同一把锁。
2. `Lock`：持全局锁找到（或创建）entry 并 `refs++`，然后**释放全局锁**，再去 `e.mu.Lock()` 等待。引用计数在全局锁内增加，保证这个 entry 不会在等待期间被删除。
3. `Unlock`：持全局锁 `refs--`，到 0 时 `delete`，最后 `e.mu.Unlock()`。即使 entry 已经从 map 删除，还在等待它的人数也是 0，所以不会有人用到一把“已删除”的锁。

**易错点**

- 在 `Lock` 里持有全局锁的同时调用 `e.mu.Lock()`：持有行锁的人调用 `Unlock` 时需要全局锁，于是死锁。
- 不做引用计数而是永不删除：key 数量（比如订单号）无限增长，内存泄漏。
- 这就是 MyISAM（表锁）和 InnoDB（行锁）在并发写上差距的直观体现。

=== db-02-1
--- explain
**思路**

B+ 树的非叶子节点只存“键 + 子页指针”，一个 16KB 的页能放一千多个，所以树非常“矮胖”：高度为 h 的树能存 `扇出^(h-1) × 每个叶子的行数` 行。3 层就能存两千多万行，主键查询只需要 2～3 次磁盘 IO（根节点通常常驻内存）。

**代码讲解**

1. `Fanout`：`pageSize / (keySize + ptrSize)`，整数除法自动向下取整。16384 / 14 = 1170。
2. `Capacity`：从叶子的行数开始，每多一层乘一次扇出。用循环而不是 `math.Pow`，避免浮点数误差。
3. `MinHeight`：从 1 层开始不断加层，直到容量够用。

**易错点**

- 为什么不用二叉平衡树或 B 树：二叉树太高，IO 次数多；B 树的非叶子节点也存数据，扇出更小，而且范围查询要在树上来回遍历。B+ 树的数据全在叶子、叶子之间有链表，范围扫描很高效。
- 主键越长，扇出越小，树越高；二级索引的叶子存的是主键值，主键长也会让所有二级索引变大。这是推荐用自增 BIGINT 做主键的原因之一。

=== db-02-2
--- explain
**思路**

范围查询在 B+ 树上分两步：先从上层索引**二分定位**到包含 `lo` 的叶子，然后沿着叶子之间的 `Next` 链表顺序扫描，遇到大于 `hi` 的键就停止。读的叶子页数大约是 “结果条数 / 每页条数 + 1”，和表的总大小无关。

**代码讲解**

1. `Build`：按 `perLeaf` 切分，每个叶子是一段子切片；从第二个叶子开始，把上一个叶子的 `Next` 指向它，并记录它的第一个 key 作为分隔键。
2. `if n := len(ix.Leaves); n > 0`：if 的初始化语句。
3. `sort.Search(len(ix.Seps), func(i int) bool { return ix.Seps[i] > lo })`：找第一个大于 lo 的分隔键，它的下标正好是起始叶子的下标（`Seps[i]` 是第 i+1 个叶子的最小值）。
4. 遍历叶子链表 `for leaf := ...; leaf != nil; leaf = leaf.Next`，命名返回值 `keys, leavesRead` 在遍历过程中直接更新。
5. 遇到 `k > hi` 立即 `return keys, leavesRead`。

**易错点**

- 用 `>= lo` 作为二分条件会在 lo 恰好等于某个分隔键时定位到错误的叶子吗？等于分隔键时，lo 是下一个叶子的第一个元素，用 `> lo` 得到的正是下一个叶子；用 `>= lo` 会定位到前一个叶子，多读一页但结果仍然正确。
- 这也解释了为什么 `LIMIT` 加上合适的索引非常快：扫描在拿够结果后就停止了。

=== db-03-1
--- explain
**思路**

InnoDB 的数据本身就按主键组织成一棵 B+ 树（**聚簇索引**），叶子存整行。**二级索引**的叶子只存索引列和主键。通过二级索引查到主键后，还要回到聚簇索引取其他列，这就是**回表**。如果查询需要的列在二级索引里都有（比如只要 id），就不用回表，这叫**覆盖索引**。

**代码讲解**

1. `rows map[int]Row` 模拟聚簇索引；`byName []secEntry` 模拟二级索引，按 `(name, id)` 排序（InnoDB 的二级索引里相同的索引值也是按主键排序的）。
2. `slices.SortFunc` 的比较函数先比名字，名字相同再比 id。
3. `slices.BinarySearchFunc(t.byName, name, cmp)`：在结构体切片上按某个字段二分，比较函数的第二个参数是要查找的目标类型（这里是 string），返回第一个 ≥ name 的位置。
4. 从那个位置往后读，直到名字不同：这就是二级索引上的一次范围扫描。
5. `FindByName` 对每个 id 回表一次，`t.Lookups++` 计数。

**易错点**

- 回表是**随机 IO**：二级索引上相邻的记录，主键可能分散在聚簇索引的各处。结果很多时，优化器可能认为全表扫描更快而放弃索引。
- 覆盖索引常见用法：`SELECT id, name FROM t WHERE name = ?` 用 `(name)` 索引就够了；`EXPLAIN` 的 Extra 显示 `Using index`。

=== db-04-1
--- explain
**思路**

联合索引 `(a, b, c)` 先按 a 排序，a 相同再按 b，b 相同再按 c。所以：

- a 等值时，b 在这个范围内是有序的，可以继续用 b；
- a 是范围条件时，在这个范围内 b 是**无序的**，b、c 就用不上了（MySQL 8.0 的索引下推和跳跃扫描是另外的优化）；
- 没有 a 的条件，b 在整个索引里都是无序的，一列都用不上。

**代码讲解**

1. 先把条件整理成 `列 → 操作符` 的 map。同一列有多个条件时，等值条件优先（`!seen || c.Op == "=" || c.Op == "in"` 才覆盖）。这一步也体现了“WHERE 里的书写顺序无所谓”。
2. 按索引列顺序遍历：
   - 等值（`=`、`in`）：`n++`，继续；
   - 范围（`>`、`<`、`between`、`like-prefix`）：这一列能用，后面不能用，返回 `n + 1`；
   - 其他（没有条件、`like-suffix`、`func`）：返回 n。
3. `switch ops[col]`：map 里没有的列返回零值 `""`，自然落到 default。

**易错点**

- `LIKE 'abc%'` 是范围扫描，能用索引；`LIKE '%abc'` 不知道从哪里开始找，不能用。
- 对列使用函数（`WHERE DATE(created_at) = ...`）、隐式类型转换（字符串列和数字比较）都会让索引失效，应该改写成对常量计算：`created_at >= '2026-01-01' AND created_at < '2026-01-02'`。

=== db-05-1
--- explain
**思路**

隔离级别从低到高，每升一级多避免一种异常：

| 级别 | 脏读 | 不可重复读 | 幻读 |
| --- | --- | --- | --- |
| READ UNCOMMITTED | 可能 | 可能 | 可能 |
| READ COMMITTED | 不会 | 可能 | 可能 |
| REPEATABLE READ | 不会 | 不会 | 可能（标准） |
| SERIALIZABLE | 不会 | 不会 | 不会 |

把级别和异常都用 `iota` 编号，规律就变成了一个简单的比较：`异常编号 >= 级别编号` 时可能出现。

**代码讲解**

1. `type Level int` + `const ( ReadUncommitted Level = iota ... )`：枚举。
2. `levelNames = [...]string{...}`：`[...]` 让编译器根据元素个数确定数组长度。
3. `String()` 先做越界检查，非法值返回 `Level(5)` 这样的调试信息。实现了 `String()` 后，`fmt.Println(level)` 会自动输出名字。
4. `ParseLevel`：`TrimSpace` → 空格替换成连字符 → 转大写，然后在名字表里查找；找不到返回带 `%q` 的错误。
5. `Allows`：`int(a) >= int(l)`，两个不同的自定义类型比较前要转换成同一类型。

**易错点**

- 用 iota 时，给 0 值一个有意义的含义（这里 0 是最低的隔离级别），或者专门留一个“未知”值。
- InnoDB 默认是 RR，并且通过 MVCC（快照读）和临键锁（当前读）在大多数情况下避免了幻读。

=== db-06-1
--- explain
**思路**

EXPLAIN 最重要的几列：`type`（访问方式）、`key`（实际使用的索引）、`rows`（预估扫描行数）、`filtered`（按条件过滤后剩下的比例）、`Extra`（额外信息）。按固定顺序逐项检查，把常见的危险信号收集起来。

**代码讲解**

1. `switch r.Type` 只处理两种需要报告的类型，其他类型（const、ref、range……）什么都不做。
2. `strings.Contains(r.Extra, "Using filesort")`：Extra 是一个包含多个提示的字符串，用子串判断。
3. 最后判断扫描量大且过滤后剩下很少：说明索引的选择性差或者条件没有用上索引。

**各项含义**

- `ALL` 全表扫描；`index` 全索引扫描（比 ALL 好一点，但仍然扫描全部）；
- `Using filesort`：需要额外排序（ORDER BY 没有用上索引的顺序）；
- `Using temporary`：需要临时表（常见于 GROUP BY、DISTINCT、UNION）；
- `Using index`：覆盖索引，好事；`Using index condition`：索引下推。

**易错点**

- `rows` 是基于统计信息的**估算值**，可能和实际差很多；MySQL 8.0 的 `EXPLAIN ANALYZE` 会真正执行并给出实际行数和耗时。

=== db-07-1
--- explain
**思路**

ReadView 记录了“创建视图那一刻，哪些事务还没提交”。判断某个版本是否可见，就看写入它的事务 ID：

- 自己写的，可见；
- 比所有活跃事务都小，说明视图创建前就已提交，可见；
- 大于等于视图创建时的“下一个事务 ID”，说明是之后才开始的事务，不可见；
- 在两者之间：在活跃列表里就是还没提交，不可见；不在就是已经提交，可见。

**代码讲解**

1. `NewReadView`：`slices.Clone(active)` 复制一份，避免外部修改影响视图；没有活跃事务时 `MinTrxID` 等于 `nextTrxID`。
2. `slices.Min(active)` 求最小值（空切片会 panic，所以先判断长度）。
3. `Visible` 用无条件 switch 按顺序判断四种情况，`slices.Contains` 检查是否在活跃列表中。
4. `Read`：沿着版本链从新到旧找第一个可见的版本，这就是 undo log 版本链的读取过程。

**易错点**

- `MaxTrxID` 不是“活跃事务里最大的 ID”，而是“下一个将要分配的 ID”。
- 判断顺序很重要：先判断“是不是自己”，因为自己的事务 ID 也在活跃列表里。

=== db-07-2
--- explain
**思路**

RC 和 RR 用的是同一套可见性规则，区别只在于 **ReadView 什么时候创建**：

- **RC**：每次 SELECT 都新建 ReadView，所以能看到其他事务**最新提交**的数据（不可重复读）；
- **RR**：事务里第一次 SELECT 时创建，之后一直复用，整个事务看到的是同一个快照（可重复读）。

**代码讲解**

1. `Engine` 维护下一个事务 ID、活跃事务集合、版本链（最新的在前）和每个事务的视图缓存 `views`。
2. `Write`：`append([]Version{{id, v}}, e.chain...)` 把新版本插到链表头部。
3. `newView`：遍历活跃事务集合，收集 ID 并求最小值；`v.min` 的初始值是 `e.nextID`。
4. `Select`：RR 时先查 `e.views[txID]`，没有就创建并保存；RC 时每次新建。
5. 拿到视图后沿版本链找第一个可见版本。

**场景复现**

T1 开始 → T2 开始、修改、提交 → T1 读取：RC 下 T1 的新视图里 T2 已经不在活跃列表中，读到新值；RR 下 T1 用的是第一次读取时的视图，T2 当时还在活跃列表中，读到旧值。

**易错点**

- RR 的视图是在**第一次读**时创建的，而不是在 BEGIN 时；`START TRANSACTION WITH CONSISTENT SNAPSHOT` 才会在开始时立即创建。
- 当前读（`SELECT ... FOR UPDATE`、UPDATE、DELETE）不用快照，读的是最新版本并加锁。

=== db-08-1
--- explain
**思路**

在 RR 隔离级别下，范围查询加 `FOR UPDATE` 时 InnoDB 加的是**临键锁**（next-key lock）= 记录锁 + 记录前面的间隙锁，锁住的是左开右闭区间 `(前一个值, 当前值]`。扫描还会多访问第一条不满足条件的记录，它也会被加临键锁。这样整个范围内（以及边界附近）都插不进新记录，从而防止幻读。

**代码讲解**

1. `prev := math.MinInt` 表示负无穷。
2. 遍历索引上的值：小于 lo 的只更新 prev；
3. 满足条件的和第一个大于 hi 的都加 `Interval{prev, k}`；遇到大于 hi 的加完就返回。
4. 一直没遇到大于 hi 的值，最后锁 `(最后一个值, +∞)`，用 `math.MaxInt` 表示。
5. `Blocked`：`v > l.Lo && v <= l.Hi` 判断是否落在左开右闭区间里。

**例子**

`keys = [10, 20, 30, 40]`，`BETWEEN 15 AND 25`：锁 `(10, 20]` 和 `(20, 30]`。插入 11～30 之间的值都会被阻塞，插入 35 不会。

**易错点**

- 唯一索引上的等值查询会退化成只加记录锁；这道题是非唯一索引，规则更“宽”。
- 间隙锁之间不冲突，但会阻塞插入（插入意向锁），这是很多死锁的来源：两个事务先各自锁了同一个间隙，然后都想插入。

=== db-09-1
--- explain
**思路**

redo log 属于 InnoDB，binlog 属于 MySQL Server 层，两者必须对“这个事务有没有提交”达成一致，否则主库（靠 redo 恢复）和从库（靠 binlog 复制）的数据就会不一样。两阶段提交把 redo 分成 prepare 和 commit 两步，binlog 写在中间。崩溃恢复时，**以 binlog 为准**：redo 处于 prepare 状态的事务，binlog 完整就提交，不完整就回滚。

**代码讲解**

1. `Commit(crashAfter)`：`slices.Clone(allSteps[:crashAfter])` 返回执行了的步骤的副本，不暴露包级切片。
2. `StateAfter`：遍历步骤推出状态，命名返回值 `(redo string, binlogComplete bool)`，先把 redo 初始化成 `"none"`。
3. `Recover`：redo 已提交，或者 prepare + binlog 完整 → 提交；否则回滚。

**各个崩溃点**

- prepare 之前崩溃：什么都没写，回滚，binlog 里也没有，一致；
- prepare 之后、binlog 之前：回滚，binlog 里没有，一致；
- binlog 之后、commit 之前：binlog 已经有了（可能已经同步给从库），所以必须提交，一致。

**易错点**

- 保证数据不丢还需要 `innodb_flush_log_at_trx_commit=1` 和 `sync_binlog=1`（“双 1”配置），否则日志可能还在操作系统缓存里就崩溃了。

=== db-10-1
--- explain
**思路**

慢查询日志是按行组织的文本：每条记录以 `# Time` 等注释行开头，`# Query_time:` 行包含四个指标，后面是 SQL（可能多行）。逐行扫描，用一个“当前记录”的状态机来收集；遇到新记录的开头或文件结束时把当前记录保存下来。

**代码讲解**

1. `flush` 是一个闭包：把收集到的 SQL 行拼起来、保存当前记录、重置状态。用闭包可以在循环里和循环结束后复用同一段逻辑。
2. 遇到 `# Query_time:`：先 flush 上一条，再创建新记录。`strings.Fields` 切分后按“键、值”成对遍历（`i += 2`），用 switch 按键名解析到对应字段。
3. 其他 `#` 开头的行（`# Time`、`# User@Host`）表示新记录的开头，也 flush。
4. `case cur == nil, strings.HasPrefix(...), ...:` 一个 case 里多个条件，任一为真就跳过这一行。
5. `Worst`：`slices.Clone` 后稳定排序（降序），`s[:min(n, len(s))]` 防止 n 超过长度。
6. `Suspicious`：`max(q.RowsSent, 1)` 避免返回 0 行时的特殊情况。

**易错点**

- 扫描行数远大于返回行数是缺索引或索引选择不当的典型信号，下一步用 EXPLAIN 确认。
- 生产环境通常用 `pt-query-digest` 对慢查询日志做聚合分析：把参数不同、结构相同的 SQL 归为一类，按总耗时排序。
