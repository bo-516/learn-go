**思路**

排行榜需要两种查询：按成员查分数（哈希表）和按分数查排名（有序结构）。Redis 的 ZSet 内部同时维护了一个哈希表和一个**跳表**，所以 ZADD、ZRANK 都是 O(log N)。这里用 map 存分数，需要排名时临时排序，逻辑上是等价的。

**思路**

- **缓存穿透**：查询一定不存在的数据（比如恶意请求不存在的 ID），缓存永远不命中，每次都打到数据库。解决：把“不存在”也缓存起来（空值缓存，过期时间短一些）。
- **缓存雪崩**：大量 key 在同一时刻过期，请求同时涌向数据库。解决：过期时间加**随机抖动**，让过期时间分散开。

**代码讲解**

1. `item` 结构体里用 `notFound bool` 标记空值。
2. 命中判断：`ok && c.now().Before(it.expire)`；命中空值时返回 `ErrNotFound`，不查库。
3. 未命中时 `c.load(key)`，用无条件 switch 处理三种结果：
   - 成功：过期时间 `ttl + jitter(ttl/5)`，即在 10 分钟的基础上随机加 0～2 分钟；
   - `errors.Is(err, ErrNotFound)`：缓存空值，过期时间 30 秒；
   - 其他错误（比如数据库超时）：**不缓存**，否则一次临时故障会被缓存下来。

- 空值缓存的过期时间要短：之后这条数据真的被创建了，最多 30 秒就能读到。也可以在创建数据时主动删除空值缓存。
- 缓存击穿（热点 key 过期瞬间的大量并发）要用 singleflight 或互斥锁解决，见「用 singleflight 防止缓存击穿」。

--- explain
**思路**

布隆过滤器是一个 m 位的位数组和 k 个哈希函数。添加时把 k 个位置置 1；查询时 k 个位置**有任何一个是 0，就一定不存在**；都是 1 则“可能存在”（可能是别的 key 恰好把这些位置都置了 1）。用很少的内存（每个元素约 10 位）就能挡住绝大多数不存在的 key。

**代码讲解**

1. `bits: make([]uint64, (m+63)/64)`：向上取整，每个 uint64 存 64 位。
2. **双重哈希**：只计算一次 64 位哈希，拆成高低两个 32 位 `h1`、`h2`，第 i 个位置是 `(h1 + i*h2) % m`。效果接近 k 个独立的哈希函数，但只算一次哈希。
3. 置位：第 p 位在 `bits[p/64]` 的第 `p%64` 位，`|= 1 << (p % 64)`。
4. 检查：`b.bits[p/64]&(1<<(p%64)) == 0`。Go 里 `&` 优先级高于 `==`，不需要额外括号。

**易错点**

- 标准布隆过滤器**不能删除**元素（清掉某一位可能影响其他元素），需要删除时用计数布隆过滤器或布谷鸟过滤器。
- 参数选择：误判率 p 时，m ≈ −n·ln(p) / (ln 2)²，k ≈ (m/n)·ln 2。1000 个元素、误判率 1% 大约需要 9600 位、7 个哈希函数。
- `uint32(i)*h2` 会溢出回绕，这正是期望的行为（相当于模 2³²）。

=== db-24-1
--- explain
**思路**

Redis 的命令由一个线程顺序执行，所以每条命令天然是原子的，数据结构不需要任何锁。在 Go 里可以用“**一个 goroutine 独占数据，其他 goroutine 通过 channel 发送请求**”实现同样的模型，这就是 Go 谚语“通过通信来共享内存”。

**代码讲解**

1. `command` 结构体带一个 `reply chan int`：每个请求自带回复通道，执行 goroutine 把结果发回去。
2. `NewServer` 启动唯一的 `loop` goroutine，它是唯一读写 `data` 的地方。
3. `loop`：`for c := range s.cmds` 依次处理命令，处理完 `c.reply <- s.data[c.key]`。
4. `Incr` / `Get`：创建容量为 1 的 reply channel，发送命令，等待结果。缓冲 1 让执行 goroutine 发送结果时不会阻塞。
5. `Close`：`close(s.cmds)` 让 loop 的 range 结束，`<-s.done` 等它真正退出。

**易错点**

- 在 `Get` 里直接读 `s.data` 会和 loop 的写入产生数据竞争，`-race` 会报告。
- 单线程模型的瓶颈是那一个 goroutine：每个命令必须很快，一条慢命令会阻塞所有请求（Redis 里的 `KEYS *`、大 key 的删除就是这样的问题）。
- Redis 6.0 的“多线程”只用于网络 IO（读取请求、写回响应），命令执行仍然是单线程。

=== db-25-1
--- explain
**思路**

Cache Aside（旁路缓存）是最常用的模式：

- 读：先读缓存，未命中读数据库并写回缓存；
- 写：**先更新数据库，再删除缓存**。

为什么是删除而不是更新缓存：两个并发写可能以不同的顺序更新数据库和缓存，导致缓存里留下旧值；删除是幂等的，下一次读会加载最新的值。为什么先更新数据库：如果先删缓存，在更新数据库之前，一个并发读会把旧值重新写回缓存。

**代码讲解**

1. `Read`：缓存命中直接返回；未命中读数据库，存在才写回缓存。
2. `Update`：`s.db.Set` → `s.cache.Del` → `s.after(500ms, ...)` 安排第二次删除。
3. `after` 是注入的函数（生产环境用 `time.AfterFunc`），测试可以同步执行或者手动触发。

**延迟双删在防什么**：读请求 R 缓存未命中，从数据库读到旧值；此时写请求 W 更新数据库、删除缓存；然后 R 才把旧值写回缓存。缓存里就留下了旧值。延迟一段时间再删一次，可以把这个旧值清掉。

**易错点**

- 删除缓存可能失败（网络问题），可靠的做法是重试，或者订阅数据库的 binlog（如 Canal）异步删除缓存。
- 这些方案只能保证**最终一致**；需要强一致的数据不适合放缓存，或者要加分布式锁。

**思路**

AOF 是一个命令日志：重启时从头执行一遍就能恢复数据。日志会越来越长（同一个 key 被修改了一万次就有一万条），所以需要**重写**：根据当前的数据状态，生成最短的等价命令序列，每个 key 一条 SET。

**代码讲解**

1. `Replay`：`switch c.Op` 处理三种命令。`data[c.Key]++` 对不存在的 key 从 0 开始，正好是 INCR 的语义。
2. `Rewrite`：先 `Replay` 得到最终状态，再按 key 排序生成 SET 命令。
3. `Cmd{"SET", k, data[k]}`：按位置初始化结构体字面量（字段少且固定时可以这样写）。

**易错点**

- Redis 的真实重写不读旧 AOF 文件，而是 fork 子进程，直接根据内存中的数据生成新文件；重写期间的新写入会同时写到一个缓冲区，最后追加到新文件里。
- RDB 是某个时间点的快照，恢复快、文件小，但会丢失最后一次快照之后的数据；AOF 更完整（`appendfsync everysec` 最多丢 1 秒）。Redis 4.0 起的混合持久化：AOF 重写时先写一份 RDB 格式的快照，再追加增量命令。

**思路**

分布式锁的两个基本要求：

1. 加锁要**原子**并且带过期时间：`SET key token NX PX ttl`，防止持有者崩溃后锁永远不释放；
2. 释放时**只能删自己的锁**：value 里存一个唯一的 token，释放时比较 token 一致才删除，并且“比较 + 删除”必须原子执行（用 Lua 脚本）。

**代码讲解**

1. `FakeRedis.get` 实现了惰性过期：读到已过期的 key 时删除并返回不存在。
2. `Acquire`：`SetNX` 成功才返回 `*Lock`，Lock 里保存 key 和自己的 token。
3. `Release`：调用 `CompareAndDelete(l.key, l.token)`，锁已经不是自己的（过期后被别人拿走了）就什么也不做，返回 false。

**经典事故**：A 加锁 → A 执行太久，锁过期 → B 加锁成功 → A 执行完直接 `DEL` → B 的锁被删除 → C 也加锁成功，B 和 C 同时进入临界区。

**易错点**

- 锁过期后 A 和 B 仍然可能同时在执行（A 不知道自己的锁已经过期）。缓解方法：“看门狗”定期续期（如 Redisson）；真正要求正确性的场景要用 **fencing token**（单调递增的令牌号，存储层拒绝旧令牌的写入）。
- `SETNX` + `EXPIRE` 两条命令不是原子的，中间崩溃会留下一把永不过期的锁。

**思路**

找出现次数最多的 k 个元素：先计数，再维护一个大小为 k 的**最小堆**。堆顶是当前 Top K 里“最冷”的那个，新元素比堆顶热才替换。内存只需要 O(k)，适合在海量 key 里找热点。

**代码讲解**

1. `less(a, b)` 定义“a 比 b 更冷”：次数更少，或者次数相同但 key 更大（这样次数相同时字典序小的排在前面）。
2. `minHeap` 实现 `heap.Interface`，`Less` 直接复用 `less`。
3. 堆没满时 `heap.Push`；满了以后，如果堆顶比新元素冷（`less((*h)[0], kv)`），就**直接替换堆顶**然后 `heap.Fix(h, 0)`，比 Pop + Push 少一次调整。
4. `k > 0` 的判断防止 k 为 0 时访问空堆。
5. 最后复制一份并按“从热到冷”排序：`less(a, b)` 为真说明 a 更冷，应该排在后面，返回 1。

**易错点**

- 用最大堆存所有元素再取 k 次，内存是 O(n)。
- 真实系统里发现热 key：Redis 4.0+ 的 `redis-cli --hotkeys`（需要 LFU 淘汰策略）、在客户端或代理层统计、`MONITOR`（开销很大，慎用）。数据量极大时还会用 Count-Min Sketch 这类近似算法计数。
- 热 key 的处理：本地缓存、把 key 拆成多个副本（`key_1`…`key_n`）分散到不同节点。

--- explain
**思路**

Redis 不会在 key 过期的那一刻立刻删除它（那需要给每个 key 一个定时器），而是两种方式结合：

- **惰性删除**：访问时发现过期再删，CPU 友好，但不再被访问的过期 key 会一直占内存；
- **定期删除**：每秒若干次随机抽查一批带过期时间的 key，删除其中过期的，限制每次的检查量，避免阻塞。

**代码讲解**

1. `expire` 用 `time.Time` 的零值表示永不过期，`it.expire.IsZero()` 判断。
2. `expired`：`!s.now().Before(it.expire)` 即“当前时间 ≥ 过期时间”。
3. `Get`：发现过期就 `delete` 并返回不存在。
4. `ActiveExpire`：遍历 map（Go 的 map 遍历顺序是随机的，正好模拟“随机抽样”），只检查带过期时间的 key，达到 `limit` 就停止。在 range 循环中删除当前元素是安全的。
5. `Len` 返回实际存储的数量，可以观察到过期但未删除的 key。

**易错点**

- 内存满了以后靠**淘汰策略**（maxmemory-policy）腾空间：`allkeys-lru`、`volatile-lru`、`allkeys-lfu`、`volatile-ttl`、`noeviction`（默认，写入直接报错）等。Redis 的 LRU 是近似的：随机采样几个 key，淘汰其中最久没访问的。
- 大量 key 同时过期时，定期删除会花更多时间，可能造成延迟抖动，这也是要给过期时间加随机值的原因之一。

--- explain
**思路**

Redis Cluster 把 key 空间分成 16384 个槽，每个节点负责一部分槽。`CRC16(key) % 16384` 决定 key 属于哪个槽。多个 key 的命令（MGET、事务、Lua）要求所有 key 在同一个槽里，所以有了 **hash tag**：只对 `{}` 里的部分计算哈希，`{user:1000}.following` 和 `{user:1000}.followers` 就一定在同一个槽。

**代码讲解**

1. `crc16`：逐字节处理。`crc ^= uint16(data[i]) << 8` 把字节放到高 8 位；然后 8 次移位：最高位是 1 就左移后异或多项式 0x1021，否则只左移。`for range 8` 是 Go 1.22 的写法。
2. `crc<<1 ^ 0x1021`：`<<` 优先级高于 `^`，等价于 `(crc << 1) ^ 0x1021`。uint16 左移溢出的位会被自动丢弃。
3. `HashSlot`：`strings.IndexByte(key, '{')` 找到第一个 `{`；在它后面找第一个 `}`，`end > 0` 保证中间至少有一个字符。
4. `key[start+1 : start+1+end]` 截取花括号中的内容（注意 end 是相对于 `start+1` 的下标）。

**易错点**

- `{}` 中间为空（如 `"{}foo"`）时 hash tag 不生效，对整个 key 计算哈希。
- 滥用 hash tag 会让大量 key 集中到一个槽、一个节点，形成数据倾斜和热点。
- 哨兵模式是“一主多从 + 自动故障转移”，容量受单机限制；Cluster 是多主分片，可以水平扩展，但不支持跨槽的多 key 操作。

**思路**

“先 GET 判断库存，再 DECRBY 扣减”是两次独立的操作，两个客户端可能都读到库存为 1，然后都扣减成功，超卖了。必须把“判断 + 扣减”放在**一个原子操作**里：Redis 里用 Lua 脚本（执行期间不会插入其他命令），这里用 `Store.Eval` 模拟。

**代码讲解**

1. `Eval` 在锁内执行传入的函数，函数直接操作 `data`。
2. `Deduct`：在一次 `Eval` 里完成判断和扣减，返回剩余库存；不够返回 -1。
3. 闭包捕获了 `key` 和 `n`。

**易错点**

- 分别调用 `s.Get` 和 `s.Set`，每个方法内部虽然都加了锁，但两次调用之间不是原子的，测试会出现超卖。“每个操作都线程安全”不等于“操作的组合线程安全”。
- Redis 的几种原子性方案：
  - **Pipeline**：只是把多个命令一次性发送，减少往返，不保证原子；
  - **MULTI/EXEC 事务**：命令排队后一起执行，中间不会插入其他命令，但不能根据中间结果做判断，某条命令失败也不会回滚；
  - **Lua 脚本**：原子执行，可以有条件逻辑，是“检查再修改”类操作的首选。脚本要短，执行期间会阻塞其他所有命令。
