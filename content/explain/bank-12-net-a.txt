=== net-01-1
--- explain
**思路**

状态机最清晰的实现方式是**转移表**：`当前状态 → (事件 → 新状态)`，查表即可，不需要一大串 if-else。表里没有的组合就是非法转移。

**代码讲解**

1. `type State string` + 一组常量：比裸字符串更安全，状态值直接就是可读的名字，打印日志也清楚。
2. `transitions map[State]map[string]State`：嵌套 map 字面量，内层 map 的类型可以省略不写。
3. `transitions[s][event]`：外层 key 不存在时返回 nil map，**读 nil map 是安全的**，第二次查找返回零值和 false，所以一行就能完成两层查找。
4. 非法转移返回原状态和带 `%q` 的错误信息。

**几个关键状态**

- **TIME_WAIT**：主动关闭方最后要等待 2MSL。一是确保最后一个 ACK 丢失时还能重发；二是让这个连接的旧报文在网络中消失，不会被同一四元组的新连接误收。
- **CLOSE_WAIT**：收到了对方的 FIN，但本方程序还没有调用 close。大量 CLOSE_WAIT 几乎一定是程序 bug（忘了关闭连接）。

**易错点**

- 同时关闭（双方同时发 FIN）时还有 CLOSING 状态，这里没有建模。

=== net-02-1
--- explain
**思路**

UDP 不保证顺序和到达，可靠传输需要应用层自己做 TCP 做的事：给数据编号、接收方按序号重组、发现缺口后请求重传。这里实现重组和缺口检测。

**代码讲解**

1. `got := map[int]string{}`：序号 → 数据，`if _, dup := got[p.Seq]; !dup` 重复的包只保留第一个。
2. `maxSeq` 初始为 −1，空输入时后面的循环一次也不执行。
3. 从 0 遍历到最大序号：缺失的记录到 `missing`，并把 `contiguous` 置为 false；只有在第一个缺口之前的数据才拼接到结果里。
4. 命名返回值 `(data string, missing []int)`，`missing` 一开始是 nil，没有缺失时就返回 nil。

**易错点**

- 遇到第一个缺口就 `break`：后面的缺失序号就统计不到了。
- `data += d` 在数据量大时应该换成 `strings.Builder`。
- TCP 的接收窗口、累计确认（ACK 的是“期望的下一个序号”）、SACK（选择性确认，告诉对方收到了哪些不连续的段）都是围绕这个思路设计的。QUIC 就是在 UDP 之上重新实现了这些可靠性机制。

=== net-03-1
--- explain
**思路**

TCP 是**字节流**，没有消息边界：发送方两次 Write 的数据，接收方可能一次读到（粘包），也可能一次 Write 的数据被分成好几次读到（拆包）。解决方法是在应用层定义消息边界，最常用的是**长度前缀**：先写 4 字节的长度，再写消息体。

**代码讲解**

1. `var hdr [4]byte` 和 `binary.BigEndian.PutUint32(hdr[:], ...)`：数组在栈上，`hdr[:]` 转成切片传给需要切片的函数。网络协议惯例使用大端序。
2. `WriteFrame`：两次 Write，任一失败返回错误。
3. `ReadFrame`：`io.ReadFull(r, hdr[:])` **保证读满 4 个字节**，否则返回错误。普通的 `Read` 可能只返回 1 个字节。
4. 长度超过上限返回错误：不校验的话，攻击者发一个长度 `0xFFFFFFFF` 就能让服务端分配 4GB 内存。
5. 再用 `io.ReadFull` 读取消息体。

**易错点**

- 用 `r.Read(buf)` 读取：在拆包场景下（测试用 `iotest.OneByteReader`）只读到一部分。
- 读到一半连接关闭时，`io.ReadFull` 返回 `io.ErrUnexpectedEOF`；在帧开始处就关闭返回 `io.EOF`，可以据此区分“正常结束”和“消息被截断”。
- 其他分帧方式：分隔符（如 HTTP/1.1 的 `\r\n`，Redis 协议）、固定长度。

=== net-03-2
--- explain
**思路**

`bufio.Scanner` 把“从流里读数据”和“怎么切分”分开了：切分逻辑通过一个 `SplitFunc` 提供。Scanner 不断读入数据放进缓冲区，然后调用切分函数：返回一个完整的 token 就交给调用方；返回 `0, nil, nil` 表示“数据还不够，再读一些”。

**代码讲解**

1. 签名 `(data []byte, atEOF bool) (advance int, token []byte, err error)`：命名返回值让三个返回值的含义一目了然。
2. 至少有 4 个字节时解析长度 n；数据够 `4 + n` 个字节就返回一个 token，`advance` 告诉 Scanner 消费了多少字节。
3. `data[4 : 4+n]` 直接切出消息体，不复制（Scanner 的文档规定 token 在下一次 Scan 之前有效）。
4. 已经 EOF 但还剩不完整的数据：返回 `io.ErrUnexpectedEOF`。
5. 其他情况返回 `0, nil, nil`。

**易错点**

- Scanner 默认最大 token 是 64KB，超过会报 `bufio.Scanner: token too long`，需要用 `scanner.Buffer(buf, max)` 调大。
- token 引用的是 Scanner 的内部缓冲区，如果要保存起来，必须复制。
- 标准库自带的切分函数：`bufio.ScanLines`、`ScanWords`、`ScanRunes`、`ScanBytes`。

=== net-04-1
--- explain
**思路**

HTTP/1.1 的一个连接上同一时间只能处理一个请求（管线化几乎没人用），前面的请求慢，后面的只能等，这就是 **HTTP 层的队头阻塞**。浏览器的缓解办法是对每个域名开最多 6 个连接。HTTP/2 在一个连接上多路复用，请求之间互不等待，总耗时取决于最慢的那个。

**代码讲解**

1. `HTTP1Time`：`free` 记录每个连接的空闲时刻。每个请求分配给最早空闲的连接（找最小值的下标），该连接的空闲时刻加上请求耗时，同时记录所有完成时刻中的最大值。
2. `HTTP2Time`：求最大耗时。
3. `time.Duration` 可以直接用内置的 `max`、比较和加法。

**易错点**

- HTTP/2 解决了 HTTP 层的队头阻塞，但所有流共用一个 TCP 连接：一个 TCP 包丢失，后面所有流的数据都要等重传（**TCP 层的队头阻塞**），丢包率高时 HTTP/2 甚至可能比多个 HTTP/1.1 连接更慢。
- HTTP/3 基于 QUIC（UDP），每个流独立处理丢包，彻底解决了这个问题；还把握手和 TLS 合并，首次连接 1-RTT、恢复连接 0-RTT。

=== net-05-1
--- explain
**思路**

TLS 1.3 的核心：

1. **ECDHE 密钥交换**：双方各自生成临时密钥对并交换公钥，各自用“自己的私钥 + 对方的公钥”计算出相同的共享秘密。窃听者只能看到两个公钥，算不出共享秘密。每次连接都用新的临时密钥，所以即使服务器长期私钥将来泄露，以前的通信也无法解密（**前向安全**）。
2. 用共享秘密派生出对称密钥，之后用 **AEAD**（如 AES-GCM）加密数据，同时保证机密性和完整性。

（真实的 TLS 还要用证书对握手签名来防止中间人，这里省略了。）

**代码讲解**

1. `ecdh.X25519().GenerateKey(rand.Reader)`：生成 X25519 私钥，`priv.PublicKey()` 得到公钥。
2. `priv.ECDH(peerPub)` 计算共享秘密；`sha256.Sum256` 返回 `[32]byte`，`sum[:]` 转成切片（简化版的密钥派生，真实 TLS 用 HKDF）。
3. `newGCM`：`aes.NewCipher(key)`（32 字节密钥 = AES-256）+ `cipher.NewGCM`。
4. `Seal`：随机生成 12 字节 nonce；`gcm.Seal(nonce, nonce, plaintext, nil)` 的第一个参数是追加的目标，所以结果是“nonce + 密文 + 认证标签”。
5. `Open`：先检查长度，拆出 nonce 再解密；数据被篡改时认证失败，返回错误。

**易错点**

- 同一个密钥下 **nonce 绝对不能重复**，否则 GCM 的安全性会完全崩溃。随机 nonce 在同一密钥加密的消息数量很大时有碰撞风险，TLS 使用递增的序号作为 nonce。
- 不要自己设计加密协议，生产环境直接用 `crypto/tls`。

=== net-06-1
--- explain
**思路**

- **TIME_WAIT 多**：本机主动关闭了大量连接，通常是短连接太多（没有复用连接，比如 HTTP 客户端连接池太小、每次请求都新建连接）。
- **CLOSE_WAIT 多**：对方已经关闭，本方程序却一直没有 close，**几乎一定是代码 bug**（比如忘了关闭响应体、异常分支没有关闭连接）。

**代码讲解**

1. `strings.Split(output, "\n")` 逐行处理，`strings.Fields` 按任意空白切分。
2. `i == 0` 跳过表头，`len(fields) == 0` 跳过空行；第一列就是状态，`counts[fields[0]]++` 计数。
3. `Diagnose` 按顺序检查两个阈值。

**易错点**

- TIME_WAIT 本身不是问题，它占用的资源很少；真正的影响是**作为客户端时**本地端口可能被耗尽（同一个目标地址最多约 28000 个可用端口）。解决：连接复用（长连接、连接池）、开启 `net.ipv4.tcp_tw_reuse`。不要用早已被移除的 `tcp_tw_recycle`。
- 排查 CLOSE_WAIT：用 `ss -tanp` 找到进程和对端地址，对照代码检查对应的连接在哪些路径上没有关闭；Go 程序可以看 goroutine profile 里阻塞在读写上的 goroutine。

=== net-07-1
--- explain
**思路**

三种“保活”的层次不同：

- **TCP keepalive**：内核在连接空闲很久（Linux 默认 2 小时）后发探测包，只能证明对方的**内核**还在；
- **HTTP keep-alive**：复用连接发送多个请求，和“探活”无关；
- **应用层心跳**：客户端定期发送心跳消息，服务端可以发现“进程卡死”“中间设备（NAT、负载均衡）悄悄清理了连接”等内核层面看不到的问题。

**代码讲解**

1. `last map[string]time.Time`：每个客户端最后一次心跳的时间，用 Mutex 保护（大量读 goroutine 会并发调用 `Beat`）。
2. `Beat`：临界区只有一行赋值，直接 Lock / Unlock。
3. `Expired`：遍历 map，超时的收集起来并从 map 中删除（在 range 中删除当前元素是安全的），最后排序。
4. `now` 作为参数传入，方便测试。

**易错点**

- 定时扫描所有连接的复杂度是 O(连接数)，百万连接时可以用**时间轮**：按过期时间把连接分到不同的槽里，每次只检查当前槽。
- 心跳间隔和超时时间要小于中间设备的空闲超时（很多 NAT 设备几分钟就会清理空闲连接）。
- Go 的 `net.Dialer` 和 `net.ListenConfig` 默认开启了 TCP keepalive（间隔 15 秒），可以通过 `KeepAlive` 字段调整。

=== net-08-1
--- explain
**思路**

Go 的网络读写看起来是阻塞的，底层是非阻塞 IO + netpoller。`SetReadDeadline` 设置的截止时间由运行时的定时器实现：到期时把等待中的 goroutine 唤醒，读操作返回超时错误。这样既能写同步风格的代码，又能控制每次读写的最长等待时间。

**代码讲解**

1. `conn.SetReadDeadline(time.Now().Add(timeout))`：deadline 是**绝对时间**，不是时长。
2. `bufio.NewReader(conn).ReadString('\n')`：读取直到换行符（包含换行符）。
3. 写之前单独设置写截止时间，然后 `conn.Write` 写回。
4. 超时时返回的错误满足 `errors.Is(err, os.ErrDeadlineExceeded)`，也可以用 `err.(net.Error).Timeout()` 判断。

**易错点**

- deadline 是绝对时间，对**之后所有的读写**都生效，长连接要在每次读之前重新设置，否则一次超时后后续所有的读都会立即失败。
- 想取消已设置的 deadline，传零值 `time.Time{}`。
- 测试里的 `net.Pipe()` 返回一对内存中直接相连的连接，没有缓冲：一端写的时候另一端必须在读，否则写会阻塞。

=== net-09-1
--- explain
**思路**

服务端有两个队列：收到 SYN 后进入**半连接队列**（SYN 队列），三次握手完成后进入**全连接队列**（accept 队列），等待应用调用 `accept` 取走。应用处理太慢、全连接队列满了，新完成握手的连接会被丢弃，客户端表现为连接超时或者被重置。

**代码讲解**

1. 每个 tick：`room := backlog - queue` 是剩余空间，`in := min(a, room)` 能进入队列的数量，其余 `a - in` 被丢弃。
2. `maxQueue = max(maxQueue, queue)` 在进入队列之后统计。
3. 应用最多 accept `acceptRate` 个：`n := min(queue, acceptRate)`。
4. 命名返回值 `(accepted, dropped, maxQueue int)` 直接在循环里累加。

**易错点**

- 全连接队列的长度是 `min(listen 的 backlog 参数, net.core.somaxconn)`。Go 的 `net.Listen` 会读取 `somaxconn` 作为 backlog，所以通常要调整的是内核参数。
- 排查：`ss -lnt` 中监听套接字的 `Send-Q` 是队列上限，`Recv-Q` 是当前队列长度；`netstat -s | grep -i overflow` 查看溢出次数。
- 根本解决方法是让应用更快地 accept 并处理连接，而不是无限调大队列。

=== net-10-1
--- explain
**思路**

**Nagle 算法**：有未确认的小包时，后续的小数据先攒着，等收到 ACK 或者攒够一个完整的段再发送，以减少小包数量。它和接收端的**延迟 ACK** 叠加时，会造成几十毫秒的延迟。Go 的 TCP 连接默认设置了 `TCP_NODELAY`（关闭 Nagle），每次 Write 都立即发送。所以大量小消息时，应该在**应用层**用缓冲合并后再写。

**代码讲解**

1. `bw := bufio.NewWriter(w)`：默认 4096 字节的缓冲区。
2. 每条消息写入缓冲区，缓冲区满了才会真正调用一次底层的 Write。
3. 最后 `bw.Flush()` 把剩余的数据写出去，并返回可能的错误。

1000 条 10 字节的消息共 10000 字节，只需要 3 次底层 Write（4096 + 4096 + 1808）。

**易错点**

- **忘记 Flush**：最后不满一个缓冲区的数据永远留在内存里，对方收不到。
- 交互式协议（请求-响应）要在每条消息之后 Flush，否则对方一直等不到请求。
- 需要 Nagle 时可以调用 `tcpConn.SetNoDelay(false)`，但大多数延迟敏感的服务都应该保持关闭。

=== net-11-1
--- explain
**思路**

gRPC 基于 HTTP/2，一个 RPC 就是一个 HTTP/2 流，所以天然支持四种模式：一元调用、服务端流、客户端流、双向流。在 Go 生成的代码里，流就是带 `Send` / `Recv` 方法的对象，`Recv` 返回 `io.EOF` 表示对方发送完毕。这里用函数参数模拟这两个方法。

**代码讲解**

1. **服务端流** `Factorize`：试除法分解质因数，每找到一个因子就 `send` 一次；`send` 出错（客户端已断开、ctx 取消）立即返回，不要继续计算。最后剩下的 `n > 1` 本身也是质因数。
2. **客户端流** `SumStream`：`for { v, err := recv() ... }`，`errors.Is(err, io.EOF)` 是正常结束，返回总和；其他错误返回。
3. **双向流** `Doubler`：收到一个就回复一个，`if err := send(v * 2); err != nil` 在 if 里声明的 err 遮蔽了外层的 err，只在这个 if 里有效。

**易错点**

- 把 `io.EOF` 当成错误返回：客户端会收到一个失败的状态码。
- 流式调用里要关注 `stream.Context().Done()`，客户端取消后及时停止。
- 双向流中发送和接收可以在不同的 goroutine 里并发进行，但同一个方向不能被多个 goroutine 同时调用（`Send` 不是并发安全的）。

=== net-12-1
--- explain
**思路**

**varint**：每个字节用低 7 位存数据，最高位表示“后面还有字节”，低位组在前。小数字只需要 1 个字节（0～127），这让 protobuf 非常紧凑。**zigzag**：负数的补码最高位是 1，直接用 varint 编码总是要 10 个字节；zigzag 把有符号数“交错”映射成无符号数（0, −1, 1, −2, 2 → 0, 1, 2, 3, 4），绝对值小的负数也很短。

**代码讲解**

1. `AppendUvarint`：`v >= 0x80` 时还有不止 7 位，`byte(v)|0x80` 取低 8 位并把最高位置 1（`byte()` 转换会截断，只保留低 8 位），然后 `v >>= 7`；最后一个字节最高位为 0。
2. `Uvarint`：`uint64(c&0x7f) << shift` 取出 7 位放到正确的位置，`|=` 合并；遇到最高位为 0 的字节结束，返回值和消耗的字节数。超过 10 个字节（uint64 最多需要 10 个）或者数据不完整返回 `(0, 0)`。
3. `ZigZag`：`v<<1` 把数值左移一位腾出符号位的位置；`v>>63` 是**算术右移**，正数得到 0、负数得到全 1，异或后负数的所有位被取反。
4. `UnZigZag`：`u>>1` 恢复数值，`-int64(u&1)` 在最低位为 1 时是全 1（−1），异或后恢复负数。

**例子**：300 = 0b1_0010_1100 → 低 7 位 `0101100` 加上续位 → `0xAC`，剩下的 `10` → `0x02`。

**兼容性要点**：protobuf 按**字段编号**识别字段，所以可以随意改字段名、新增字段；不能修改已有字段的编号或类型，删除的字段编号要用 `reserved` 保留，防止以后被重用。
