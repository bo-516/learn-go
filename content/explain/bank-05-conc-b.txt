**思路**

`sync.Map` 适合“key 只写一次、之后大量读”的场景。词频统计里每个词的计数器只创建一次，之后只是原子加一，所以把 value 设计成 `*atomic.Int64`：map 本身几乎只读，计数在计数器上原子完成。

**代码讲解**

1. `chunk := (len(words) + workers - 1) / max(workers, 1)`：向上取整的除法，把切片均分成 workers 份；`max` 防止除以 0。
2. `part := words[start:min(start+chunk, len(words))]`：每个 goroutine 处理一段。
3. 先 `Load`，不存在再 `LoadOrStore(w, new(atomic.Int64))`：大部分词已经存在时，只走无锁的快速路径，也避免每次都分配一个新计数器。
4. `LoadOrStore` 返回的是**最终存在 map 里的那个值**（可能是别的 goroutine 先存进去的），所以并发创建时也只会用同一个计数器。
5. `v.(*atomic.Int64).Add(1)`：`sync.Map` 的值是 `any`，需要类型断言。
6. `Range` 遍历转换成普通 map，回调返回 true 表示继续。

**易错点**

- 用 `Load` + `Store` 代替 `LoadOrStore`：两个 goroutine 可能同时发现不存在、各自 Store 一个新计数器，其中一个的计数会丢失。
- 一般的读写混合场景用 `map + RWMutex` 或分片锁更快，`sync.Map` 不是通用的并发 map。

**思路**

`sync.Pool` 缓存临时对象以减少分配。两条规则：拿出来的对象可能是别人用过的，**必须重置**；不要把特别大的对象放回去，否则偶尔一次大请求会让池子长期占用大量内存。

**代码讲解**

1. `sync.Pool{New: func() any { return new(bytes.Buffer) }}`：池子空的时候调用 New 创建。
2. `Get()`：`p.pool.Get().(*bytes.Buffer)` 类型断言，池里只放这一种类型。
3. `Put(b)`：`b.Cap() > p.maxCap` 时直接丢弃，让 GC 回收；否则 `b.Reset()`（长度清零，保留容量）后放回。

**易错点**

- Put 之后继续使用这个 buffer：它可能已经被另一个 goroutine 拿走并写入数据。

**思路**

**写时复制（copy-on-write）**：配置对象一旦发布就不再修改，更新时创建一个新对象，然后原子地替换指针。读取只需要一次原子 Load，完全无锁。多个写者并发更新时，“读旧值 → 生成新值 → 写回”之间可能被别人抢先，所以用 **CAS 循环**：只有当指针仍然是我读到的那个 old 时才替换，否则重新读取、重新计算。

**代码讲解**

1. `p atomic.Pointer[Config]`：泛型的原子指针（Go 1.19+）。
2. `NewHolder` 先 `Store` 初始配置。
3. `Load()` 直接返回当前指针，调用方只读不改。
4. `Update`：`for { old := Load(); if CompareAndSwap(old, fn(old)) { return } }`。CAS 失败说明别人已经更新过，重试时 `fn` 会基于最新的配置计算。

**易错点**

- `fn` 修改旧对象（比如 `old.Limits["x"] = 1` 然后返回 old）：正在读旧配置的 goroutine 会看到半更新的数据，而且 map 并发读写会崩溃。必须深拷贝需要修改的部分。
- 写入非常频繁时 CAS 会大量失败重试，这时用 Mutex 更合适；这个模式适合读远多于写的场景。

**思路**

防抖（debounce）：频繁触发时，只在“安静下来”一段时间后执行一次。每次触发都取消上一次的定时器，重新开始计时，所以只有最后一次触发后的定时器能活到时间到期。

**思路**

CPU 缓存以 **cache line**（通常 64 字节）为单位。两个不相关的变量如果在同一个 cache line 里，被不同的 CPU 核心频繁写入时，这个 cache line 会在核心之间来回失效、传递，性能大幅下降，这就是**伪共享**。让每个计数器独占一个 cache line 就能避免。

2. `slots []PaddedCounter`：切片里的元素是连续存放的，每个元素正好 64 字节，所以相邻槽位不会共享 cache line（假设起始地址对齐）。
3. `Add`：`c.slots[slot].n.Add(delta)`，直接通过下标访问元素的字段，不会复制。
4. `Sum`：`for i := range c.slots` 用下标访问，避免 `for _, s := range` 复制包含原子变量的结构体（`go vet` 会报 copylocks）。

- 填充会浪费内存，只用在真正高频并发写的热点上，比如分片计数器、每个 P 一个的本地缓存。
- 有的 CPU 的 cache line 是 128 字节（如 Apple M 系列）；`golang.org/x/sys/cpu.CacheLinePad` 会按平台给出合适的大小。

**思路**

Treiber 栈：栈顶是一个原子指针。Push 时让新节点指向当前栈顶，然后 CAS 把栈顶换成新节点；Pop 时 CAS 把栈顶换成 `old.next`。CAS 失败说明别人修改过栈顶，重新读取再试。

**代码讲解**

1. `head atomic.Pointer[node]`：零值是 nil，空栈。
2. `Push`：节点只分配一次，循环里每次重新设置 `n.next = old`，然后 `CompareAndSwap(old, n)`。
3. `Pop`：`old == nil` 返回空；否则 `CompareAndSwap(old, old.next)` 成功就返回 `old.val`。

**为什么 Go 里没有 ABA 问题**：ABA 指的是：线程 1 读到栈顶 A，准备 CAS；期间线程 2 弹出 A、B，又把 A 的内存释放后重新分配成一个新节点压回去，地址又是 A。线程 1 的 CAS 会成功，但 `old.next` 已经是一个无效的 B。Go 有 GC：只要线程 1 还持有 `old` 指针，A 就不会被回收，它的地址也不会被复用，所以这种情况不会发生。

**易错点**

- 高竞争下 CAS 会反复失败、空转，性能可能不如 Mutex。无锁数据结构的价值在于不会因为某个持锁的 goroutine 被挂起而让所有人等待。

**思路**

死锁的必要条件之一是“循环等待”：A 拿着锁 1 等锁 2，B 拿着锁 2 等锁 1。如果所有 goroutine 都**按同一个全局顺序**加锁（比如按账户 ID 从小到大），就不可能形成环，死锁也就不会发生。

3. 先锁 first 再锁 second，各自 defer 解锁（解锁顺序是后进先出，正好相反，没有问题）。
4. 加锁顺序和业务方向（from、to）无关，修改余额时仍然用 from、to。

**易错点**

- 按指针地址排序也可以，但 ID 更稳定、更容易理解。
- 排查死锁：所有 goroutine 都阻塞时运行时会报 `all goroutines are asleep - deadlock!`；只有部分阻塞时，看 `/debug/pprof/goroutine?debug=2` 里卡在 `sync.(*Mutex).Lock` 的 goroutine，比较它们持有和等待的锁。
