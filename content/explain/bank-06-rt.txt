=== rt-01-1
--- explain
**思路**

照着 `runtime.findRunnable` 的优先级写：

1. 每调度 61 次先看一眼全局队列，防止全局队列里的 G 一直得不到运行（饥饿）；
2. `runnext`：刚被当前 G 唤醒的 G（比如刚收到 channel 数据的接收者），优先运行，提高缓存局部性；
3. 本地队列；
4. 全局队列；
5. **工作窃取**：从其他 P 的本地队列偷一半过来。

**代码讲解**

1. `p.SchedTick++` 然后 `p.SchedTick%61 == 0`：61 是个质数，避免和其他周期性行为同步。
2. 取队首的写法统一是 `g := q[0]; q = q[1:]`。
3. 窃取时 `n := len(victim.Local) - len(victim.Local)/2` 是向上取整的一半。
4. `stolen := victim.Local[:n:n]`：**完整切片表达式**把容量限制为 n。下一行把 victim 的队列改成 `victim.Local[n:]`，两者共享底层数组；如果不限制容量，之后对 stolen 的 append 可能覆盖 victim 的数据。这里我们只读 stolen，但这个写法是好习惯。
5. 第一个偷来的 G 直接返回，其余 `append` 到自己的本地队列。

**易错点**

- 真实的调度器里本地队列是一个固定 256 长度的无锁环形队列，窃取用原子操作；全局队列需要加锁，所以访问频率被刻意降低。
- 窃取前还会检查 netpoller（有没有网络 IO 就绪的 G）和定时器。

=== rt-02-1
--- explain
**思路**

时间片轮转调度：队首任务最多运行 `quantum`，没做完放回队尾。这就是抢占的效果：长任务被切成很多段，短任务不会被它长时间阻塞。Go 1.14 起有基于信号的**异步抢占**，运行超过 10ms 的 G 会被强制让出，即使它在一个没有函数调用的紧密循环里。

**代码讲解**

1. `queue := append([]Task(nil), tasks...)`：复制一份，不修改调用方的切片。
2. `t := queue[0]; queue = queue[1:]` 出队。`t` 是结构体的副本，修改 `t.Work` 不影响原数据。
3. `run := min(t.Work, quantum)`：最后一段可能不满一个时间片。
4. `now += run`，做完就记录 `Finish{t.Name, now}`（按位置初始化结构体），没做完 `queue = append(queue, t)` 放回队尾。

**易错点**

- quantum 非常大时，所有任务按顺序一次做完，这就是 Go 1.14 之前协作式调度的问题：`for {}` 这种没有函数调用的循环永远不会让出，甚至会让 GC 的 STW 无限等待。
- 抢占点：函数调用的栈检查（协作式）、sysmon 发送的 SIGURG 信号（异步）、channel / 锁等阻塞操作、`runtime.Gosched()`。

=== rt-03-1
--- explain
**思路**

GOMAXPROCS 默认等于 CPU 核数。在容器里，Go 1.25 之前读到的是**宿主机**的核数（比如 64），但 cgroup 只允许用 2 个核，于是 64 个 P 抢 2 个核的 CPU 配额，频繁被内核限流（throttling），延迟抖动严重。正确的值应该根据 cgroup 的 CPU 限额计算。

**代码讲解**

1. 环境变量优先：`if n, err := strconv.Atoi(env); err == nil && n > 0`，空字符串会解析失败，自然跳过。
2. `strings.Fields(cpuMax)` 按空白切分，必须正好两个字段。
3. 先解析 period 并校验 > 0；quota 为 `"max"` 表示不限制。
4. `limit := (quota + period - 1) / period`：向上取整的整数除法，1.5 核按 2 算。
5. `min(max(limit, 2), numCPU)`：至少 2，但不超过真实核数。

**易错点**

- Go 1.25 之前的通用做法是引入 `go.uber.org/automaxprocs`，在 init 里读取 cgroup 设置 GOMAXPROCS。
- cgroup v1 的配置在 `cpu.cfs_quota_us` 和 `cpu.cfs_period_us` 两个文件里，格式不同。
- Go 1.25 还会定期重新读取限额，限额动态变化时自动调整。

=== rt-04-1
--- explain
**思路**

网络 fd 被设置成非阻塞模式。读不到数据时，goroutine 不会让线程阻塞在 `read` 系统调用上，而是**挂在 netpoller 上**（记录“谁在等这个 fd”），然后让出 P，线程继续运行别的 goroutine。epoll 报告 fd 就绪后，调度器把等待的 goroutine 放回运行队列。这里用 channel 模拟“挂起和唤醒”。

**代码讲解**

1. `waiters map[int][]chan struct{}`：每个 fd 一组等待者，每个等待者一个 channel。
2. `Wait`：创建自己的 channel，加锁登记，**解锁后**再阻塞在 select 上（持锁阻塞会让 Ready 永远拿不到锁）。
3. 被取消时要把自己从列表中移除：`slices.Index` 找到位置，`slices.Delete` 删除。
4. 找不到自己说明在取消的同时 Ready 已经把列表取走并关闭了 channel，这次等待其实成功了，返回 nil。
5. `Ready`：加锁把列表整个取走并删除，**解锁后**逐个 `close(ch)` 唤醒；close 是广播，不会阻塞。

**易错点**

- 不处理“取消和唤醒同时发生”的竞态，会出现 Waiting 计数不准或者重复唤醒。
- 文件 IO 不走 netpoller（普通文件总是“就绪”的），阻塞的文件读写和 cgo 调用会占住线程，见「程序的线程数为什么会暴涨」。

=== rt-05-1
--- explain
**思路**

goroutine 的栈初始很小（几 KB），函数入口的栈检查发现空间不够时，运行时分配一块 **2 倍大小**的新栈，把旧栈的内容整体复制过去并调整栈上的指针。所以 Go 里递归一百万层通常没问题（默认最大 1GB）。但深递归仍然有复制和内存成本，层数不可控时最好改成**显式栈**。

**代码讲解**

1. `SumTo`：标准递归，`n == 0` 是终止条件。每一层都在栈上占一个栈帧。
2. `MaxDepth`：在函数里定义局部类型 `type item struct { n *Node; depth int }`，只在这个函数里使用。
3. `stack := []item{{root, 1}}`：切片字面量里的元素类型可以省略。
4. 弹出栈顶，更新最大深度，把所有孩子带着 `depth + 1` 压栈。

**易错点**

- 栈复制会让栈上变量的地址改变，所以 Go 不允许把指向栈的指针存到不受 GC 管理的地方（比如转成 `uintptr` 保存）。
- 超过 1GB 会 `fatal error: stack overflow`，无法 recover。
- 用显式栈遍历时，节点的访问顺序和递归不同（后进先出），只求深度时没关系。

=== rt-06-1
--- explain
**思路**

三色标记：白色 = 还没访问（最后仍是白色就是垃圾），灰色 = 已发现但它引用的对象还没扫描，黑色 = 自己和它引用的对象都处理完了。从根对象开始，不断把灰色对象变黑、把它引用的白色对象变灰，直到没有灰色对象。

**代码讲解**

1. `black`、`grey` 两个 map 表示颜色，不在任何一个里的就是白色。
2. 根对象标灰入队，`!grey[r]` 防止重复的根被加入两次。
3. 取出灰色对象 x，遍历 `heap[x]`，只有**既不是灰色也不是黑色**的对象才标灰入队，这保证了每个对象只入队一次，遇到环也不会死循环。
4. `delete(grey, x)` 然后 `black[x] = true`。
5. `Sweep`：遍历所有对象，没被标记的就是垃圾；map 遍历无序，最后排序。

**易错点**

- 不可达的环（A → B → A，但没有根指向它们）在标记阶段根本不会被访问到，会被正确回收。引用计数做不到这一点。
- Go 的 GC 不移动对象（非压缩），回收后的空间留给相同 size class 的对象复用。

=== rt-06-2
--- explain
**思路**

并发标记时，用户代码可能“把白色对象藏到黑色对象下面”，同时删除灰色对象到它的引用，导致白色对象再也不会被扫描、被误回收。两种屏障各自破坏一个必要条件：

- **插入屏障**（Dijkstra）：建立新引用时把目标标灰，黑色对象就不会直接指向白色对象；
- **删除屏障**（Yuasa）：删除引用时把旧目标标灰，从灰色对象出发的可达路径不会被切断。

Go 1.8 的**混合写屏障**结合了两者，这样栈上的指针写入不需要屏障，标记结束时也不用重新扫描所有栈。

**代码讲解**

1. `shade(x)`：只有白色才变灰并加入工作队列，重复调用无害。
2. `WritePointer`：`if h.marking { h.shade(dst) }`，然后添加引用。
3. `DeletePointer`：`if h.marking { h.shade(dst) }`，然后用 `slices.Index` + `slices.Delete` 删除这条引用。
4. 标记结束（`marking == false`）后屏障关闭，不再有额外开销。

**易错点**

- 写屏障只在 GC 标记阶段开启，平时写指针只多一次标志位判断。这也是为什么 GC 期间程序会变慢一些。
- 屏障可能让本该回收的对象“活”到下一轮 GC（浮动垃圾），这是为了正确性付出的代价。

=== rt-07-1
--- explain
**思路**

GOGC 控制“堆增长到上次存活堆的多少倍时触发下一次 GC”：GOGC=100 表示新分配的量达到存活量的 100% 时触发。Go 1.18 起栈和全局变量也算进存活量。GOMEMLIMIT 是内存的软上限：快接近上限时，即使没到 GOGC 的比例也会更频繁地 GC。

**代码讲解**

1. `ParseGOGC`：`switch s` 先处理 `""` 和 `"off"`，其他情况用 `strconv.Atoi` 并检查非负。
2. `HeapGoal` 里 `gogc < 0` 表示 off：没有内存上限时返回 `math.MaxUint64`（永远不会触发），有上限时以上限为目标。
3. `goal := live + (live+stacks+globals)*uint64(gogc)/100`：先乘后除，避免整数除法提前截断。
4. 有上限且目标超过上限时截断。

**易错点**

- `GOGC=off` 而又不设 GOMEMLIMIT，堆会无限增长直到 OOM。常见的用法是 `GOGC=off` + `GOMEMLIMIT=容器内存的 80%~90%`：内存充足时几乎不 GC，接近上限时才 GC。
- GOMEMLIMIT 设得太低（小于实际存活量）会导致 GC 不停运行、CPU 被占满（死亡螺旋），运行时对 GC 的 CPU 占用有 50% 的上限保护。
- `uint64` 相乘在数值极大时可能溢出，这里的输入范围不会遇到。

=== rt-08-1
--- explain
**思路**

`strings.Split` 每次调用都要分配一个 `[]string` 来存放结果。高频调用的解析函数里，这些短命的分配会显著增加 GC 压力。`strings.Cut` 返回的是原字符串的**子串**（只是新的指针和长度），完全不分配。

**代码讲解**

1. `for line != ""`：每轮切掉一个字段，直到剩余部分为空。
2. `field, rest, _ := strings.Cut(line, ",")`：找不到逗号时 `field` 是整个剩余字符串，`rest` 是空串，循环自然结束。
3. `strconv.Atoi(field)`：解析失败直接返回错误。
4. `line = rest` 继续处理剩余部分。

**易错点**

- 输入 `"1,2,"` 时最后会得到一个空字段吗？`Cut("2,", ",")` 返回 `"2"` 和 `""`，循环就结束了，所以末尾的逗号被忽略；而 `"1,,2"` 中间的空字段会让 Atoi 报错。需要严格校验时要注意这些边界。
- Go 1.24 的 `strings.SplitSeq` 返回迭代器，也不会分配结果切片。
- 优化前先用 `go test -bench . -benchmem` 或 pprof 的 alloc_space 确认热点。

=== rt-09-1
--- explain
**思路**

Go 的内存分配器把小对象（≤ 32KB）按大小分成约 68 个 **size class**，每个 class 有自己的 span（一组页），分配时向上取整到最近的 class，这样同一个 span 里的对象大小相同，分配和回收都很快。代价是一些内部碎片：申请 40 字节实际得到 48 字节。

**代码讲解**

1. 大于 32768 的是大对象，直接按 8KB 页向上取整：`(size + pageSize - 1) / pageSize * pageSize`。
2. `slices.BinarySearch(sizeClasses, size)` 返回第一个 ≥ size 的位置（找到相等的也是这个位置），正好是需要的 class。
3. `Kind` 用无条件 switch 按顺序判断：小于 16 字节且不含指针的走 **tiny 分配器**（多个小对象合并放在一个 16 字节块里）。

**易错点**

- 这就是为什么 `append` 扩容后的容量有时比“翻倍”还多：容量还要按 size class 取整。`[]int64` 需要 5 个元素 = 40 字节 → 48 字节 → cap 6。
- tiny 分配器合并的对象要等整个 16 字节块里的所有对象都不可达才会被回收。

=== rt-10-1
--- explain
**思路**

RSS 不下降不一定是泄漏，常见原因有三类：

1. Go 的堆空闲了但还没把内存**归还**给操作系统（`HeapIdle - HeapReleased`）；
2. 大量 goroutine 的**栈**（heap profile 看不到栈）；
3. **非 Go 管理的内存**：cgo 分配、mmap 的文件，这部分连 `Sys` 都不包含。

按顺序检查这几项，可以快速判断内存去了哪里。

**代码讲解**

1. `Snapshot()`：`var ms runtime.MemStats; runtime.ReadMemStats(&ms)` 读取真实数据，然后挑出需要的字段构造自己的结构体（方便测试时手工构造输入）。
2. `m.HeapIdle-m.HeapReleased > rss/4`：整数运算避免浮点数。
3. `float64(rss) > float64(m.Sys)*1.1`：比例比较转成浮点数。
4. `len(out) == 0 && ...`：前面都没命中才检查“确实是堆在使用中”。

**易错点**

- 运行时的后台 scavenger 会逐步把空闲内存归还给系统，也可以手动 `debug.FreeOSMemory()`（会触发一次 GC，生产环境慎用）。
- Linux 上 Go 1.12～1.15 用 `MADV_FREE` 归还内存，内核在没有内存压力时不会真正回收，RSS 看起来不降，这在当年引起过很多“泄漏”误报。
- `ReadMemStats` 会短暂 STW，不要在热路径上高频调用；可以用 `runtime/metrics` 包。

=== rt-11-1
--- explain
**思路**

GOMAXPROCS 只限制**同时运行 Go 代码**的线程数。goroutine 进入阻塞的系统调用（文件 IO、某些 DNS 解析）或 cgo 调用时，它所在的线程会被一直占用，调度器会为 P 启动或唤醒另一个线程继续工作。并发阻塞调用多了，线程数就会暴涨，超过 10000（`debug.SetMaxThreads` 的默认值）进程会直接崩溃。所以要**限制阻塞调用的并发数**。

**代码讲解**

1. `sem chan struct{}`：容量为 n 的信号量。
2. 获取名额放在 select 里，同时监听 `ctx.Done()`：排队期间被取消就直接返回，不执行 fn。
3. 拿到名额后 `defer func() { <-p.sem }()` 释放，然后执行 fn。

**易错点**

- 线程一旦创建，即使空闲了也不会被销毁（Go 运行时不回收 M），所以线程数“只涨不降”。
- 典型场景：大量并发读写磁盘文件、大量 cgo 调用（比如 SQLite 驱动）、`net` 包使用 cgo DNS 解析器时的大量并发 DNS 查询。

**思路**

sysmon 是一个不绑定 P 的后台线程，循环做几件事：抢占运行太久的 G、从阻塞太久的系统调用手里抢回 P、检查 netpoller、必要时触发 GC。它的休眠时间是自适应的：一直有事做就保持 20µs；连续空闲很久就逐步加倍，最长 10ms，减少空转的 CPU 开销。

=== rt-14-1
--- explain
**思路**

用最小堆按触发时间组织定时器，堆顶就是最早到期的那个。要支持任意删除和修改，需要知道每个定时器**当前在堆里的下标**：`heap.Remove(h, i)` 和 `heap.Fix(h, i)` 都需要下标。所以在 `Swap` 和 `Push` 里同步维护元素的 `index` 字段。

- `heap.Push(&q.h, t)` 要传**指针**，因为 Push / Pop 要修改切片本身。

--- explain
**思路**

GC 标记期间，如果业务代码分配内存的速度比后台标记快，堆会在标记完成前超出目标。所以运行时要求分配内存的 goroutine “还债”：分配越多，要帮忙做的标记工作越多（**辅助标记**）。这会让正在处理请求的 goroutine 突然多出一段额外的工作，表现为延迟抖动。

**代码讲解**

1. `debt := int64(math.Ceil(float64(n) * ratio))`：先转成浮点数相乘，向上取整，再转回 int64。
2. `use := min(debt, credit)`：先用自己的信用抵扣。
3. `steal := min(debt, bg)`：再从后台积累的全局信用里偷。
4. 仍有欠债时 `work = max(debt, overAssist)`：至少做 overAssist 那么多，多做的部分 `work - debt` 存成自己的信用，避免每次小分配都要停下来做一点点工作。
5. 命名返回值 `(work, newCredit, newBg int64)`，最后显式返回。

**易错点**

- 减少辅助标记的根本办法是**减少分配**（复用对象、预分配），或者适当调大 GOGC / 设置 GOMEMLIMIT，让 GC 不那么频繁。
- `gctrace` 里 cpu 段的第二项就是辅助标记的 CPU 时间。

=== rt-16-1
--- explain
**思路**

传统的标记按对象被发现的顺序扫描，相邻扫描的对象可能分散在很多不同的内存页上，CPU 缓存和 TLB 命中率很低。Green Tea GC（Go 1.25 实验、1.26 默认开启）以 **span（同一 size class 的一组页）为单位**积累待扫描的对象，一次扫描同一个 span 里的多个对象，内存访问更连续。

**代码讲解**

1. `SpanOrder`：`spans` 切片记录 span **第一次出现的顺序**（map 遍历无序，不能用 map 的顺序），`groups` map 收集每个 span 的对象。
2. `if _, ok := groups[o.Span]; !ok` 判断是否第一次出现。
3. 按 `spans` 的顺序把各组展开拼接：`append(out, groups[s]...)`。
4. `SpanSwitches`：相邻元素 span 不同就计数一次。

**易错点**

- 只用 map 分组而不记录顺序，结果每次运行都不一样，测试会时好时坏。
- 分组后的换页次数 = 不同 span 数 − 1，这是理论最小值。

=== rt-17-1
--- explain
**思路**

GC 什么时候回收一个对象是**不确定的**，甚至可能永远不回收，所以不能依赖 GC 来释放文件、连接这些稀缺资源：必须显式 `Close`。`runtime.AddCleanup`（Go 1.24+）只用来兜底和**发现泄漏**：对象被回收时如果还没关闭，就记录一次泄漏。

**代码讲解**

1. `runtime.AddCleanup(r, func(fd int) {...}, fd)`：第一个参数是被监视的对象，第三个参数会作为清理函数的参数传入。
2. 清理函数**只能引用 fd，不能引用 r**：如果闭包捕获了 r，r 就永远可达，清理函数永远不会执行。这正是它比旧的 `runtime.SetFinalizer` 更好用的地方：后者把对象本身传给 finalizer，很容易写出复活对象的代码。
3. `Close` 里 `r.cleanup.Stop()`：已经正常关闭，取消兜底。
4. 重复关闭返回 `ErrClosed`。
5. 结构体里的 `name *string` 字段让对象包含指针、大小超过 16 字节，不会被 **tiny 分配器**和其他小对象合并到同一块内存（合并后要整块不可达才回收），测试里的清理才能可靠地触发。

**易错点**

- `SetFinalizer` 的问题：一个对象只能有一个 finalizer、遇到循环引用永远不执行、对象会被“复活”多活一轮 GC。新代码优先用 `AddCleanup`。
- 清理函数在单独的 goroutine 里执行，要保证它是并发安全的，而且执行得很快。

=== rt-18-1
--- explain
**思路**

`schedtrace` 每隔一段时间输出一次调度器状态：P 的数量和空闲数、线程数、全局队列长度和每个 P 的本地队列长度。用通用的 `key=value` 解析，就不依赖字段顺序，不同 Go 版本新增或删除字段也不会出错。

**代码讲解**

1. `strings.Cut(line, ": ")` 分成头部 `SCHED 2003ms` 和剩余部分。
2. `strings.TrimPrefix` / `TrimSuffix` 去掉 `SCHED ` 和 `ms`，得到毫秒数。
3. `strings.Cut(rest, "[")` 把键值对部分和方括号里的本地队列分开。
4. 键值对：`strings.Fields` 按空白切分，每个再 `strings.Cut(f, "=")`；没有 `=` 的字段跳过。
5. 本地队列：去掉 `]` 后按空白切分，逐个转成整数。
6. `Runnable` 和 `Diagnose` 用**值接收者**：只读，`SchedTrace` 很小。

**易错点**

- `idleprocs=0` 且可运行的 G 远多于 P：CPU 饱和，需要扩容或者优化 CPU 热点。
- 线程数远大于 P：大量阻塞的系统调用或 cgo（见「程序的线程数为什么会暴涨」）。
- 加上 `GODEBUG=schedtrace=1000,scheddetail=1` 能看到每个 P、M、G 的详细状态，输出非常多，只在排查时短时间使用。
