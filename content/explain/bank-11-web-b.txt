--- explain
**思路**

所有错误从一个出口返回给客户端，格式统一。内部错误（数据库报错、文件路径）**不能**直接暴露给用户：既不友好，也可能泄露系统信息。所以只有“明确知道可以展示”的 `*AppError` 才把它的信息返回，其他错误一律返回通用信息，详细原因记日志。

**代码讲解**

1. `AppError` 有对外的 `Status`、`Code`、`Message`，以及不导出的 `cause`；`Unwrap()` 返回 cause，日志里可以看到完整的错误链。
2. `WriteError` 先设好默认值（500 / 50000），再用无条件 switch 依次判断：
   - `errors.As(err, &ae)`：错误链上有 AppError（即使被 `fmt.Errorf("%w")` 包了几层也能找到）；
   - `errors.Is(err, context.DeadlineExceeded)`：超时返回 504。
3. `status, b = ae.Status, body{ae.Code, ae.Message}`：多重赋值同时更新两个变量。
4. 写响应：先设 Content-Type，再 `WriteHeader`，最后编码 JSON。

**易错点**

- `w.WriteHeader` 必须在 `Header().Set` 之后、写响应体之前。
- 用 `err.Error()` 作为 message 返回给用户，会把 SQL 语句、内部地址等暴露出去。
- 错误码的设计常见做法是“HTTP 状态码 + 业务码”，业务码前几位表示模块，方便定位问题。

**思路**

参数校验要**收集所有错误**一次性返回，而不是遇到第一个就返回，前端可以一次标出所有有问题的字段。错误类型 `ValidationErrors` 是切片，实现了 `error` 接口。最关键的陷阱：没有错误时必须 `return nil`，而不是 `return errs`。

**代码讲解**

1. `type ValidationErrors []FieldError`：基于切片定义新类型并实现 `Error()`，用 `strings.Join` 拼接每个字段的错误。
2. `var errs ValidationErrors`：nil 切片，可以直接 append。
3. name：先 `TrimSpace`，无条件 switch 判断“为空”和“太长”两种情况（互斥，只报一个）。`utf8.RuneCountInString` 按字符而不是字节计数，中文名不会被误判为太长。
4. email：`strings.Cut(r.Email, "@")` 拆成两部分，再检查两边不为空、域名里没有第二个 `@`。
5. `if len(errs) == 0 { return nil }`。

**易错点**

- 用 `len(s)` 统计中文名的长度，一个汉字算 3 个。
- 生产项目常用 `go-playground/validator` 通过 struct tag 声明校验规则，Gin 的 `binding` 标签就是基于它。

**思路**

上传文件不能 `io.ReadAll`：100 个并发的 1GB 上传就是 100GB 内存。应该**流式处理**：边读边写到目标位置，内存占用只有一个固定大小的缓冲区。同时用 `io.MultiWriter` 把同一份数据写给哈希计算器，不需要读两遍。

**代码讲解**

1. `h := sha256.New()`：哈希也是一个 `io.Writer`。
2. `io.MultiWriter(w, h)`：写入的数据会同时写到 w 和 h。
3. `io.LimitReader(r, max+1)`：最多读 `max+1` 个字节。如果真的读到了 `max+1` 个，说明文件超过了限制，而且只多读了一个字节就停止了。
4. `io.Copy` 返回复制的字节数，`n > max` 时返回 `ErrTooLarge`。
5. `hex.EncodeToString(h.Sum(nil))` 得到十六进制哈希。

**易错点**

- 用 `io.LimitReader(r, max)`：正好 max 字节和超过 max 字节的文件都只会读到 max 个字节，无法区分。
- 超限时 w 里已经写入了 max+1 字节，调用方需要删除这个不完整的文件。
- HTTP 服务里先用 `http.MaxBytesReader(w, r.Body, max)` 限制请求体，`r.ParseMultipartForm` 超过内存限制的部分会写到临时文件，或者用 `r.MultipartReader()` 完全流式地处理。

--- explain
**思路**

请求结束后连接被放回空闲池，下次复用，省去 TCP 握手（和 TLS 握手）。但 `MaxIdleConnsPerHost` 默认只有 2：10 个并发请求结束时，只有 2 个连接能放回池子，其他 8 个被关闭；下一轮又要新建 8 个连接。高并发调用同一个服务时，这会导致大量的新建连接和 TIME_WAIT。

**代码讲解**

1. `idle map[string][]int`：每个 host 一个空闲连接栈。
2. `Get`：有空闲就从末尾取（后放回的先用，这样最近使用过的连接更可能还是活的）；没有就新建，`Dialed++`。
3. `Put`：空闲数达到上限就关闭，`Closed++`；否则放回。

**测试结论**：上限为 2 时，每轮 10 个并发请求，第一轮新建 10 个，之后每轮关闭 8 个、新建 8 个；上限为 10 时总共只建立 10 个连接。

**易错点**

- 调用内部服务时，`MaxIdleConnsPerHost` 应该调到和并发度相当；`MaxIdleConns`（所有 host 的总数，默认 100）也要相应调大。
- 不读完、不关闭响应体，连接不会被放回池子，再大的池也没用（见「正确使用 http.Client」）。
- 还有 `MaxConnsPerHost` 限制每个 host 的总连接数（默认不限制）、`IdleConnTimeout` 控制空闲连接存活多久（默认 90 秒）。

**思路**

Webhook 接口是公开的，任何人都可以伪造请求。双方共享一个密钥，发送方对“时间戳 + 请求体”计算 HMAC 签名放在请求头里；接收方用同样的密钥重新计算并比较。把时间戳放进签名并检查它和当前时间的差距，可以防止攻击者截获一个合法请求后**重放**。

4. `d := now.Sub(time.Unix(sec, 0))`：时间差，`d > tolerance || d < -tolerance` 同时拒绝太旧和来自未来的时间戳。
5. 任意一个签名通过 `hmac.Equal` 常量时间比较即通过。

**易错点**

- 对**原始请求体字节**计算签名，不能先解析 JSON 再重新序列化（字段顺序、空格会变）。
- 用 `==` 或 `bytes.Equal` 比较签名有时序攻击风险。
- 时间窗口只能缩小重放的机会；要彻底防止重放，还要记录处理过的事件 ID（幂等）。

**思路**

API 的两种版本标识方式：放在 URL 路径里（`/v2/users`，直观、方便调试和缓存），或者通过 `Accept` 头协商（URL 保持不变）。服务端根据版本号决定响应的结构。判断是否需要升级版本的原则：**新增可选字段是兼容的**，删除字段、改名、改类型、改语义都是不兼容的。

**代码讲解**

1. `Version`：无条件 switch 按优先级判断：路径前缀 → Accept 头 → 默认 1。
2. `RenderUser` 用**匿名结构体**定义不同版本的响应格式：`struct { ... }{值}` 声明和初始化写在一起，只在这里使用，不需要单独命名类型。
3. 匿名结构体的字段同样可以带 json tag。
4. v1 把名和姓拼接起来，`strings.TrimSpace` 处理其中一个为空的情况。

**易错点**

- 在 v1 里直接把 name 改成两个字段，老客户端会读不到 name。
- 兼容性的另一面：客户端要**忽略不认识的字段**，服务端才能放心地新增字段（Go 的 `encoding/json` 默认就是这样）。
- 旧版本要有明确的下线计划：通过响应头（如 `Deprecation`、`Sunset`）提前通知调用方。
