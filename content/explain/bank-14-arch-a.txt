=== arch-01-1
--- explain
**思路**

服务依赖构成一张有向图，发布顺序就是**拓扑排序**：被依赖的先发布。用 Kahn 算法：统计每个服务还有几个依赖没发布，为 0 的就可以发布；发布一个服务后，依赖它的服务的计数减一。最后如果还有服务没发布，说明存在循环依赖。

**代码讲解**

1. `pending`：服务 → 尚未发布的依赖数；`dependents`：服务 → 依赖它的服务。依赖里出现、但自己不在 `deps` 的 key 里的服务（叶子服务），也要放进 `pending`，计数为 0。
2. 收集初始计数为 0 的服务到 `ready`。
3. 每轮 `slices.Sort(ready)` 后取第一个：保证同时可以发布的服务按字典序，结果确定（map 的遍历顺序是随机的）。
4. 发布后遍历 `dependents[svc]`，计数减到 0 就加入 ready。
5. `len(order) != len(pending)`：有服务一直没被发布，存在环。

**易错点**

- 依赖的方向写反：`deps[a]` 是 a 依赖的服务，边应该是“依赖 → a”。
- 每轮都排序 ready 的复杂度不是最优的，用最小堆可以优化，服务数量不多时没有必要。
- 循环依赖在微服务里意味着拆分边界有问题：两个服务互相调用，发布、回滚、故障都会互相牵连。

=== arch-02-1
--- explain
**思路**

N 个副本，写入 W 个成功才算成功，读取时读 R 个副本取版本最新的。只要 `W + R > N`，任意一个读集合和任意一个写集合**至少有一个公共副本**，所以一定能读到最新写入的值。调整 W 和 R 可以在读写性能和可用性之间取舍：W = N、R = 1 写慢读快；W = 1、R = N 写快读慢；常见的是 N=3、W=2、R=2。

**代码讲解**

1. `Overlaps`：`w+r > n`。
2. `Write`：写所有存活的副本，`r.Version, r.Value = version, value` 多重赋值；成功数少于 w 返回 `ErrNoQuorum`。
3. `Read`：跳过不存活的副本，读满 r 个就停止；`best` 记录版本最大的副本指针。存活数不足 r 时返回错误。
4. 函数参数是 `[]*Replica`：通过指针修改副本的状态。

**易错点**

- 读到的版本不同说明有副本落后了，真实系统会顺便把新值写回落后的副本（**读修复**）。
- Quorum 只保证能读到最新的“已成功写入”的值，并发写入时的冲突还需要版本向量或最后写入者胜出（LWW）等策略来解决。
- 这是 Dynamo、Cassandra 这类 AP 系统的核心机制；CP 系统（etcd、ZooKeeper）通过共识算法保证线性一致。

=== arch-03-1
--- explain
**思路**

服务注册与发现的基本模型：实例启动时注册自己的地址，之后定期发送**心跳**续约；注册中心发现某个实例超过 TTL 没有心跳，就认为它已经下线，不再返回给调用方。正常关闭时实例应该主动注销，不要等 TTL 过期。

**代码讲解**

1. `instances map[string]map[string]time.Time`：服务名 → (地址 → 最后心跳时间)。
2. `Register`：内层 map 不存在时先创建；写入当前时间。注册和心跳是同一个操作。
3. `Deregister`：`delete(r.instances[service], addr)`，外层 key 不存在时得到 nil map，**对 nil map 调用 delete 是安全的**（什么也不做）。
4. `Instances`：遍历时顺便删除过期的实例（range 中删除当前元素是安全的），最后排序。
5. `now` 通过函数注入，测试可以模拟时间流逝。

**易错点**

- TTL 太短，网络抖动会让健康的实例被误摘；太长，故障实例要很久才被摘除。通常心跳间隔是 TTL 的 1/3。
- 客户端应该缓存实例列表并监听变化（etcd watch、Nacos 推送），而不是每次请求都查询注册中心；注册中心挂掉时，客户端还能用缓存继续工作。
- 在 Kubernetes 里通常直接使用 Service + Endpoints，由 kubelet 的探针决定实例是否可用。

=== arch-04-1
--- explain
**思路**

平滑加权轮询：每个节点维护一个 `current`。每次选择时，所有节点的 current 先加上自己的权重，选 current 最大的节点，然后把被选中节点的 current 减去总权重。效果是：权重大的节点被选中的次数符合比例，但不会连续出现，而是被均匀地穿插在其他节点之间。

**代码讲解**

1. `node` 存指针到切片里，修改 `n.current` 才能保存下来。
2. `Next`：一次遍历同时完成三件事：所有节点 `current += weight`、计算总权重、找 current 最大的节点。`n.current > best.current` 用严格大于，相同时保留靠前的。
3. 选中的节点 `current -= total`。
4. 没有节点时返回空字符串。

**推演**（a:5, b:1, c:1，total = 7）：

| 轮 | 加权后 | 选中 | 减去 7 后 |
| --- | --- | --- | --- |
| 1 | 5, 1, 1 | a | −2, 1, 1 |
| 2 | 3, 2, 2 | a | −4, 2, 2 |
| 3 | 1, 3, 3 | b | 1, −4, 3 |
| 4 | 6, −3, 4 | a | −1, −3, 4 |
| 5 | 4, −2, 5 | c | 4, −2, −2 |

**易错点**

- 每一轮所有 current 的总和始终为 0，所以这个过程是周期性的，周期等于总权重。
- 并发使用时需要加锁。

=== arch-04-2
--- explain
**思路**

“最少连接”需要扫描所有节点，节点多时开销大，而且所有客户端会同时涌向同一个最空闲的节点（羊群效应）。**P2C**：随机选两个，挑负载低的那个。理论和实践都表明，只比较两个就能得到接近全局最优的负载分布，又避免了羊群效应。

**代码讲解**

1. 只有一个节点时直接返回。
2. `i := randIntn(len(nodes))`；`j := randIntn(len(nodes) - 1)`，如果 `j >= i` 就加一。这个技巧保证 j 在“除 i 之外的其他下标”里均匀分布，而且 j 一定不等于 i，不需要循环重试。
3. 比较 `Inflight`，b 严格更小才选 b，相同时选 a。
4. 随机函数通过参数注入，测试可以控制选中哪两个节点。

**易错点**

- 两次独立随机可能选到同一个节点，等于没有比较。
- 真实实现（如 gRPC、Kratos 的 P2C）的负载指标通常结合了在途请求数、EWMA 平滑的响应时间和成功率。
- `Inflight` 要在请求开始时加一、结束时减一，用原子操作。

=== arch-05-1
--- explain
**思路**

降级：下游超时或出错时，返回一个兜底结果（缓存的旧数据、默认值、简化版的结果），保证主流程可用。关键是**不能被下游卡住**：即使下游完全不响应 ctx，我们也要在超时后立即返回。所以把下游调用放在单独的 goroutine 里，主 goroutine 用 select 同时等待“结果”和“超时”。

**代码讲解**

1. `ctx, cancel := context.WithTimeout(ctx, timeout)` + `defer cancel()`：返回时取消，通知下游可以停止了。
2. 在函数内定义局部类型 `type result struct { v string; err error }`，把两个返回值打包成一个值通过 channel 传递。
3. `ch := make(chan result, 1)`：**缓冲为 1**，超时返回后没人接收，goroutine 也能把结果放进缓冲然后退出，不会泄漏。
4. `select`：先拿到结果且没有错误，返回 `(r.v, false)`；有错误或超时，都落到最后的 `return fallback(), true`。

**易错点**

- 无缓冲 channel：超时返回后，下游的 goroutine 最终完成时会永远阻塞在发送上。
- 直接调用 `primary(ctx)` 而不放进 goroutine：下游不响应 ctx 时，超时完全不起作用。
- 区分限流、熔断、降级：**限流**保护自己（拒绝超出能力的请求），**熔断**保护下游并快速失败（下游错误率高时直接不调用），**降级**是失败后的兜底策略，三者通常组合使用。

=== arch-06-1
--- explain
**思路**

Saga 把一个分布式事务拆成多个本地事务（扣库存 → 扣余额 → 创建订单），每一步都有一个**补偿操作**（加回库存、退回余额）。某一步失败时，按**相反的顺序**对已经成功的步骤执行补偿，让系统回到一致的状态。它不需要全局锁，适合长流程、跨服务的业务，代价是中间状态对外可见（没有隔离性）。

**代码讲解**

1. 依次执行 `Action`，失败时记录 `fmt.Errorf("step %s: %w", ...)`。
2. `for j := i - 1; j >= 0; j--`：只补偿**已经成功**的步骤，失败的那一步本身不需要补偿。
3. 补偿失败时不中断，记录错误后继续补偿其他步骤。
4. `errors.Join(errs...)`（Go 1.20+）把多个错误合成一个，`errors.Is` / `errors.As` 能匹配其中任意一个。

**易错点**

- 补偿操作必须**幂等**：网络超时后重试补偿，不能退两次款。
- 补偿也失败时，真实系统需要持久化 Saga 的状态，由后台任务重试，最终还不行就告警人工处理。
- 其他方案：2PC（强一致但阻塞，性能差）、TCC（Try-Confirm-Cancel，业务侵入大）、本地消息表 / 事务消息（最终一致，见下一题）。

=== arch-06-2
--- explain
**思路**

“写数据库”和“发消息”是两个系统，无法在一个事务里完成：先写库后发消息，发送失败消息就丢了；先发消息后写库，写库失败下游却收到了消息。**本地消息表**：把待发送的消息和业务数据写在**同一个本地事务**里（一定同时成功或同时失败），然后由后台任务把消息表里未发送的消息投递到 MQ，失败就重试。

**代码讲解**

1. `Msgs []*Message`：存指针，修改 `Sent`、`Attempts` 才能保存。
2. `Relay` 按顺序遍历：已发送的跳过；`publish(*m)` 传值（解引用后复制一份）；失败 `Attempts++` 然后 `continue`，下次再试；成功标记 `Sent = true` 并计数。

**易错点**

- 投递成功但标记 `Sent` 之前崩溃，重启后会再发一次，所以这是**至少一次**投递，下游必须幂等。
- `Attempts` 超过阈值应该告警或转入死信，避免一条坏消息无限重试。
- 用数据库的 binlog（Debezium、Canal）代替轮询消息表，延迟更低（CDC 模式）。

=== arch-07-1
--- explain
**思路**

雪花 ID 是 64 位整数：`0 | 41 位时间戳 | 10 位机器 ID | 12 位序列号`。时间戳在高位，所以 ID **大体按时间递增**（对数据库索引友好）；机器 ID 保证不同机器不冲突；同一毫秒内用序列号区分，每台机器每毫秒最多 4096 个。

**代码讲解**

1. 常量：`maxSeq = 1<<seqBits - 1`，`<<` 优先级高于 `-`，即 4095。
2. `New` 校验机器 ID 范围：`worker >= 1<<workerBits`（1024）。
3. `Next` 加锁，保证并发安全。
4. **时钟回拨**：小于 5ms 就自旋等待时间追上；超过 5ms 直接返回错误（等太久不如报错）。
5. 同一毫秒：`s.seq++`，用完了就自旋等到下一毫秒，序列号归零。不同毫秒：序列号归零。
6. 拼装：`(ts-epoch)<<22 | worker<<12 | seq`。
7. `Decompose`：`id>>22 + epoch` 得到时间戳；`id >> seqBits & (1<<workerBits - 1)`，Go 里 `>>` 和 `&` 优先级相同、从左到右结合，等于 `(id >> 12) & 1023`；`id & maxSeq` 得到序列号。

**易错点**

- 时钟回拨会导致重复 ID，这是雪花算法最大的风险（NTP 校时、虚拟机迁移都可能发生）。
- 41 位毫秒时间戳大约能用 69 年，从自定义纪元开始算，所以纪元要选得近一些。
- 机器 ID 的分配需要协调（配置、ZooKeeper / etcd 分配、K8s StatefulSet 的序号）。其他方案：数据库号段模式（美团 Leaf）、UUIDv7（时间有序的 UUID）。

=== arch-08-1
--- explain
**思路**

- **串联**：所有组件都可用系统才可用，可用性相乘。依赖越多，整体可用性越低：5 个 99.9% 的服务串联只有约 99.5%。
- **并联**（冗余）：任一副本可用就可用，不可用的概率相乘。两个 99% 的副本冗余，不可用概率是 1% × 1% = 0.01%，可用性 99.99%。

这就是高可用设计的两条主线：**减少关键路径上的依赖**，以及**对关键组件做冗余**。

**代码讲解**

1. `Series(avail ...float64)`：可变参数，从 1.0 开始连乘。
2. `Parallel`：先求所有副本都失败的概率 `∏(1 − aᵢ)`，再用 1 减去它。
3. `Downtime`：`365 * 24 * time.Hour` 是一年的时长；`(1 - avail) * float64(year)` 在浮点数上计算，最后转回 `time.Duration`。

**参考值**：99.9% 每年约 8.76 小时，99.99% 约 52.6 分钟，99.999% 约 5.26 分钟。

**易错点**

- 并联公式假设各副本**独立失效**，同一个机房、同一个依赖、同一个配置错误会让它们同时失效，所以冗余要跨机房、跨可用区，变更要灰度。
- 除了冗余，还有：超时与重试、限流熔断降级、异步化、快速发现与恢复（缩短故障时间同样提高可用性）。

=== arch-09-1
--- explain
**思路**

多级缓存：本地缓存（L1，进程内，最快）→ 分布式缓存（L2，Redis）→ 数据库。读的时候逐级查找，查到后**逐级回填**。最大的问题是 L1 的一致性：数据更新后，每个实例的本地缓存里还是旧值。所以更新时除了删 L2，还要通过消息总线**广播**失效消息，所有实例收到后删除自己的 L1。

**代码讲解**

1. `NewNode` 里 `bus.Subscribe(func(key string) { n.l1.Del(key) })`：每个实例订阅失效消息，闭包捕获了 n。
2. `Get`：L1 命中直接返回；L2 命中回填 L1；都没有就查数据库，然后回填 L2 和 L1。
3. `Update`：写数据库 → 删 L2 → 广播。
4. 已有的 `Bus.Publish` 先在锁内复制订阅者列表，再在锁外逐个调用：回调里如果再调用 `Subscribe` 也不会死锁。

**易错点**

- 广播消息可能丢失或延迟，所以本地缓存一定要设置**较短的过期时间**作为兜底。
- 本地缓存要限制容量（LRU），否则内存会无限增长。
- 适合放本地缓存的是读多写少、能容忍短暂不一致的数据，比如配置、商品信息；库存、余额不适合。

=== arch-10-1
--- explain
**思路**

Prometheus 的 Histogram 不保存原始数据，只记录每个**桶**里有多少个样本（`le` 标签就是桶的上界）。查询分位数时，`histogram_quantile` 先找到目标排名落在哪个桶里，再假设样本在桶内**均匀分布**，线性插值出一个估计值。所以估算的精度完全取决于桶的划分。

**代码讲解**

1. `Counts` 比 `Bounds` 多一个，最后一个是 `+Inf` 桶。
2. `Observe`：从前往后找第一个 `v <= Bounds[i]` 的桶（循环条件是 `v > h.Bounds[i]` 时继续），都不满足就停在最后的 +Inf 桶。
3. `Quantile`：
   - `rank = q × 总数`；
   - 累加计数，`prev` 是本桶之前的累计数，累计数第一次 `>= rank`（并且本桶非空）时就是目标桶；
   - 落在 +Inf 桶无法插值，返回最大的有限上界；
   - 线性插值：`lower + (upper − lower) × (rank − prev) / c`。
4. 没有数据时返回 `math.NaN()`。

**例子**：桶 `[0.1, 0.5, 1]`，计数 `[50, 40, 10]`，p90 的 rank = 90，落在第二个桶（累计 90），估计值 = 0.1 + 0.4 × (90 − 50) / 40 = 0.5。

**易错点**

- 桶的边界要根据实际的延迟分布和 SLO 设计（比如 SLO 是 300ms，就要有 0.3 这个边界），桶太粗时 p99 可能偏差很大。
- Prometheus 2.40+ 的 Native Histogram 使用指数分布的桶，精度更好且不用手工设计边界。

=== arch-11-1
--- explain
**思路**

Raft 的选举规则保证两件事：

1. **每个任期最多一个 Leader**：每个节点在一个任期内只能投一票；
2. **Leader 一定包含所有已提交的日志**：只把票投给日志“至少和自己一样新”的候选者。已提交的日志一定存在于多数节点上，候选者要赢得多数票，必然要得到至少一个拥有该日志的节点的认可。

**代码讲解**

1. 任期更小的请求直接拒绝，响应里带上自己的任期，让候选者知道自己落后了。
2. 任期更大：更新任期并重置投票（新任期还没投过票）。
3. 计算自己最后一条日志的下标和任期，`lastIndex, lastTerm := len(n.LogTerms), 0`，有日志时再取最后一个任期。
4. `upToDate`：先比任期（大的更新），任期相同再比长度。
5. 本任期没投过票（或者已经投给了同一个候选者，处理重复请求）并且日志足够新，才投票。

**易错点**

- 只比较日志长度而不比较最后的任期：一个日志很长但都是旧任期的节点可能当选，覆盖掉已提交的日志。
- 真实实现中，`CurrentTerm` 和 `VotedFor` 必须在回复之前**持久化**，否则重启后可能在同一任期投出第二票。
- 投票后还要重置选举超时计时器。

=== arch-11-2
--- explain
**思路**

Leader 知道每个节点复制到了哪里（`matchIndex`），一条日志被复制到**多数节点**上就可以提交。求“多数节点都已达到的最大下标”：把 matchIndex 排序，取中间偏左的那个值。还要满足一个关键限制：**只能通过计数提交当前任期的日志**。

**代码讲解**

1. `slices.Clone` 后排序，不修改调用方的数据。
2. `sorted[(len(sorted)-1)/2]`：升序排序后，这个位置及其右边的节点（共 `n - (n-1)/2` 个，即多数）都至少达到了这个值。
3. 从这个值往下找，第一个任期等于当前任期的下标就是新的 commitIndex；`logTerms[n-1]` 是因为日志下标从 1 开始。
4. 找不到（多数节点上的日志都是旧任期的）就保持原来的 commitIndex。

**为什么不能提交旧任期的日志**（Raft 论文 Figure 8）：旧任期的日志即使已经复制到多数节点，也可能被一个拥有更新任期日志的新 Leader 覆盖。如果此时已经提交并应用了，就会出现已提交的日志被覆盖的情况。等当前任期的一条日志被复制到多数节点后，它之前的所有日志就随之**间接提交**了。

**易错点**

- 新 Leader 上任后通常会立即提交一条空日志（no-op），尽快把之前任期的日志间接提交。
- 偶数个节点时 `(n-1)/2` 取的是中间偏左的位置，仍然满足“多数”（例如 4 个节点需要 3 个）。

=== arch-12-1
--- explain
**思路**

普通的取模哈希 `hash(key) % N`，节点数变化时几乎所有 key 都要迁移。一致性哈希把节点和 key 都映射到一个 0～2³² 的**环**上，key 顺时针找到的第一个节点就是它的归属。增加一个节点只影响它和前一个节点之间的那一段 key。**虚拟节点**：每个物理节点在环上放很多个点，让分布更均匀，节点下线时它的负载也会分散到多个节点上。

**代码讲解**

1. `hashes []uint32` 是排序后的环，`owner` 记录每个哈希点属于哪个物理节点。
2. `Add`：每个节点生成 `replicas` 个虚拟节点 `node#i`，`strconv.Itoa` 转数字；哈希冲突（极少）时不重复加入切片。最后整体排序。
3. `Remove`：`slices.DeleteFunc` 删除所有属于这个节点的哈希点，回调里顺便从 map 中删除。
4. `Get`：`slices.BinarySearch` 找第一个 ≥ key 哈希的位置，越过末尾回到 0（环形）。

**易错点**

- 虚拟节点太少时分布很不均匀，通常每个节点 100～200 个。
- 增加节点后，迁移的 key 只会从**其他节点迁到新节点**，不会在老节点之间互相迁移，这是测试验证的性质。
- 其他方案：Redis Cluster 的固定槽位（16384 个槽，迁移以槽为单位）、Jump Consistent Hash（无需存储环，但只支持在末尾增删节点）。
