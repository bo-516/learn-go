=== net-12-2
--- explain
**思路**

protobuf 的消息就是一串“字段”，每个字段 = **tag**（字段编号和类型）+ **值**。`tag = 字段编号 << 3 | wire type`，低 3 位是 wire type，告诉解码器值的格式：0 是 varint，2 是“长度 + 内容”。所以即使不认识某个字段编号，解码器也知道怎么跳过它，这就是 protobuf 向前兼容的基础。

**代码讲解**

1. `binary.AppendUvarint(dst, uint64(num)<<3|0)`：先写 tag，再写值。`<<` 优先级高于 `|`。
2. `AppendBytesField`：tag → varint 长度 → `append(dst, b...)` 内容。
3. `Decode`：循环直到数据用完：
   - `binary.Uvarint(b)` 返回值和消耗的字节数，`n <= 0` 表示数据不完整或溢出；
   - `tag >> 3` 是字段编号，`tag & 7` 是 wire type；
   - wire type 0：再读一个 varint；
   - wire type 2：读长度，检查剩余数据够不够（`uint64(len(b)-n) < l`），然后切出内容。
4. `f.Varint, b = v, b[n:]`：多重赋值同时保存值和推进切片。

**易错点**

- 不检查长度就切片：恶意数据里的长度字段可能远超实际数据，`b[n:n+int(l)]` 直接 panic。
- 切出来的 `f.Bytes` 和输入共享底层数组，调用方修改输入会影响解析结果，需要时要复制。
- 例子 `08 96 01`：`08` = 字段 1 << 3 | 0；`96 01` 是 150 的 varint 编码。

**思路**

拦截器就是 gRPC 版的中间件：接收请求和“下一个处理者”，可以在调用前后加逻辑（日志、鉴权、超时、指标、恢复 panic）。把多个拦截器组合成一个 Handler，和 HTTP 中间件的 `Chain` 是同一个思路：从最后一个开始包装。

=== net-15-1
--- explain
**思路**

重试是把双刃剑：下游真的出问题时，每个请求重试 3 次就是 3 倍流量，下游更加起不来（**重试风暴**）。几条原则：

1. 只重试**幂等**的请求（重复执行没有副作用）；
2. 只重试**暂时性**错误（超时、服务不可用），参数错误重试多少次都没用；
3. 用**重试预算**限制重试流量占总流量的比例。

**代码讲解**

1. `Retryable`：`idempotent && (errors.Is(...) || errors.Is(...))`，括号不能省，`&&` 优先级高于 `||`。
2. `Budget.AllowRetry`：`(b.retries+1)*100 > b.percent*b.requests` 就拒绝，把“重试次数 ≤ 请求数 × 百分比”转成整数比较，避免浮点数。
3. `Call`：`for attempt := 1; ; attempt++` 条件留空，在循环体里判断退出：成功、达到最大次数、不可重试、预算不允许，任一成立就返回最后的错误。
4. 条件的顺序很重要：`b.AllowRetry()` 放在最后，只有前面的条件都允许重试时才会消耗预算。

**易错点**

- 把 `AllowRetry` 放在前面：即使错误不可重试也会消耗预算。
- 实际的重试还要加**指数退避 + 随机抖动**，避免所有客户端在同一时刻重试；以及传递“剩余超时时间”，不要在调用方已经放弃后还在重试。
- 只在一层做重试：调用链上每一层都重试 3 次，5 层就是 3⁵ = 243 倍。

**思路**

广播时如果对每个客户端都**阻塞地**发送，一个网络很慢的客户端就会让所有人都收不到消息。每个客户端有一个带缓冲的发送 channel，广播时用 `select + default` **非阻塞**发送：缓冲满了说明这个客户端跟不上，直接把它踢掉。

**代码讲解**

1. `Unregister`：从 map 删除，并 `close(c.Send)`，该客户端的写 goroutine 用 `for msg := range c.Send` 读取，channel 关闭后它会退出并关闭连接。`if c, ok := ...; ok` 保证不会重复关闭。
2. `Broadcast` 持**读锁**遍历：`select { case c.Send <- msg: ... default: ... }` 非阻塞发送；发不出去的记到 `slow` 里。
3. **释放读锁之后**再逐个 `Unregister`：Unregister 需要写锁，持有读锁时再去获取写锁会死锁（Go 的 RWMutex 不支持锁升级）。

**易错点**

- 在读锁里直接调用 `Unregister`：死锁。
- 两个 goroutine 同时 Unregister 同一个客户端：第二次检查 `ok` 为 false，不会重复 close。
- 踢掉慢客户端是一种策略；另一种是丢弃消息但保留连接（适合行情推送这类只关心最新值的场景）。

**思路**

为每个连接创建一个定时器，百万连接就是百万个定时器，插入、删除都要操作运行时的定时器堆。**时间轮**把时间分成固定数量的槽，像钟表一样转：连接按过期时间放进对应的槽，指针每 tick 前进一格，只处理当前格里的连接。添加、删除、续期都是 O(1)。

**代码讲解**

1. `slots []map[string]struct{}`：每个槽是一个集合；`where map[string]int` 记录每个 id 在哪个槽，删除时直接定位。
2. `NewWheel` 里逐个初始化每个槽的 map（`make([]map...)` 只创建了 nil map 的切片，nil map 不能写）。
3. `Add`：先 `Remove`（续期），然后放进 `(pos + delay) % size` 号槽。
4. `Tick`：指针前进一格，收集这一格里的所有 id，同时从 `where` 删除，然后给这一格换一个新的空 map，最后排序。

**易错点**

- delay 必须小于槽数，否则会和当前位置冲突（绕了一圈）。需要更长的延迟时可以用**多层时间轮**（像时、分、秒），或者在槽里记录“剩余圈数”。
- Kafka、Netty 都使用了时间轮。真实的网关里，每次收到心跳就调用一次 `Add` 续期，`Tick` 返回的就是超时需要关闭的连接。

=== net-21-2
--- explain
**思路**

分区内并发处理时，消息会**乱序完成**：offset 10 处理完了，offset 8 还在处理中。如果直接提交 11，进程崩溃后 8 和 9 就丢了。所以只能提交**连续完成**的最高位点：记录哪些 offset 已完成，从当前的提交位点开始，只要下一个已完成就往前推进。

**代码讲解**

1. `next`：可以提交的位点（它之前的消息都已完成）；`done`：已完成但还不连续的 offset 集合。
2. `MarkDone`：`offset < t.next` 说明已经推进过了（重复标记），直接忽略。
3. 标记完成后 `for t.done[t.next] { delete(...); t.next++ }`：不断推进，同时清理已经连续的部分，`done` 只保存“空洞”之后的 offset，不会无限增长。
4. 所有方法加锁：`MarkDone` 会被多个 worker 并发调用。

**例子**：起始 5。完成 7 → 不能推进（5、6 没完成），仍为 5；完成 5 → 推进到 6；完成 6 → 6、7 都完成，推进到 8。

**易错点**

- 某条消息一直处理不完（卡死），位点就永远无法推进，积压越来越大；要给处理设置超时，失败的消息转入重试队列或死信队列后标记为完成。
- 崩溃重启后会重新消费“已完成但未提交”的消息，所以仍然需要幂等处理。
