=== arch-13-1
--- explain
**思路**

秒杀的两个核心约束：**不超卖**（库存不能变成负数）和**一人一单**。两个判断都要在并发下原子完成：

- 一人一单：`sync.Map.LoadOrStore` 原子地“查询并占位”，只有第一个请求能占到；
- 扣库存：CAS 循环，只有在读到的库存还没被别人改过时才扣减，库存为 0 时停止。

**代码讲解**

1. `stock atomic.Int64`：`NewSeckill` 里用 `Store` 初始化。
2. `LoadOrStore(user, true)` 返回 `loaded = true` 说明之前已经有记录，返回 `ErrDuplicate`。
3. CAS 循环：读当前库存，≤ 0 就**删除刚才的占位**（这个用户没买到，不应该被记为已购买）并返回 `ErrSoldOut`；`CompareAndSwap(cur, cur-1)` 成功就返回，失败说明被别人抢先修改了，重新读取再试。

**易错点**

- 用 `stock.Add(-1)` 再判断是否小于 0：库存会短暂变成负数，而且需要再加回来，并发时判断容易出错。CAS 循环保证库存永远不会小于 0。
- 卖完时忘记删除占位，用户在补货后就再也买不了了。
- 真实系统的完整链路：前端限流（按钮置灰、验证码）→ 网关限流 → Redis 预扣库存（Lua 脚本保证原子）→ 消息队列异步创建订单 → 数据库最终扣减（带 `WHERE stock > 0` 条件）。

=== arch-13-2
--- explain
**思路**

**削峰**：秒杀时瞬间的请求量远超下单服务的处理能力。把请求先放进一个**有界**队列，后台固定数量的 worker 按自己的节奏处理。队列满了就立即拒绝，让用户稍后重试，而不是让请求堆积、所有人都超时。

**代码讲解**

1. `Submit`：`select { case q.ch <- o: ... default: return ErrBusy }`，非阻塞入队。
2. `Start(n, handle)`：启动 n 个 worker，每个 `for o := range q.ch` 消费。返回值是一个**闭包** `stop`：调用者不需要知道内部的 WaitGroup。
3. `stop`：`close(q.ch)` 后 worker 会把缓冲里剩余的订单处理完再退出，`wg.Wait()` 等它们全部退出。

**易错点**

- 用阻塞的 `q.ch <- o`：队列满时请求会一直挂着，大量 goroutine 堆积，最终耗尽内存。
- `stop` 之后再调用 `Submit` 会向已关闭的 channel 发送，panic。生产代码应该先停止接收新请求（比如网关摘流），再调用 stop。
- 内存队列在进程崩溃时会丢数据，真实系统使用 Kafka、RocketMQ 等持久化的消息队列，用户通过轮询或推送得知下单结果。

**思路**

Base62 就是“62 进制”：用 `0-9a-zA-Z` 共 62 个字符表示数字。编码：反复除以 62 取余数，余数就是从低到高的各位；解码：从高位开始 `n = n × 62 + 当前位`。

**代码讲解**

1. `Encode`：uint64 最大约 1.8 × 10¹⁹，62¹¹ > 2⁶⁴，所以最多 11 位，用固定大小的数组 `var buf [11]byte` 从**后往前**填，避免最后再反转，也不需要动态分配。
2. `alphabet[id%62]`：字符串可以按下标取字节。
3. `string(buf[i:])`：数组切片后转字符串。
4. `Decode`：`strings.IndexByte(alphabet, s[i])` 得到字符对应的数值，-1 表示非法字符。
5. **溢出检查**：在计算 `n*62 + d` 之前判断 `n > (MaxUint64 - d) / 62`，如果成立，计算结果一定会超出 uint64。

**易错点**

- 先算再判断是否溢出：溢出后的值已经回绕，无法判断。
- 用自增 ID 生成短码可以被**遍历**（猜到别人的链接），而且暴露了业务量。可以把 ID 和一个密钥做可逆的混淆（比如用 Feistel 网络打乱）后再编码。

**思路**

二进制浮点数无法精确表示 0.1，`0.1 + 0.2` 的结果是 `0.30000000000000004`。金额计算一律用**整数（分）**。解析字符串时也不能先转 float64 再乘 100（`ParseFloat("0.29") * 100` 得到 28.999999999999996），而是把整数部分和小数部分分开解析。

**代码讲解**

1. `allDigits`：非空且每个字节都是数字。
2. `ParseYuan`：
   - 先处理负号；
   - `strings.Cut(s, ".")` 拆成整数部分和小数部分；
   - 校验：整数部分必须是数字（所以 `".5"` 不合法）；有小数点时小数部分必须是 1～2 位数字（所以 `"1."`、`"1.234"` 不合法）；`"1e3"` 也会因为 e 不是数字被拒绝；

4. `Split`：先平均分，余数从前往后每份多分 1 分，保证总和不变。

**易错点**

- `FormatCents(-5)` 如果直接 `c/100` 和 `c%100`，Go 的除法向零截断，会得到 `0` 和 `-5`，格式化成 `0.-5`，所以要先处理符号。
- 分账（比如优惠券分摊到多个商品）时，必须保证各部分之和等于总额，否则对账会出现一分钱的差异。

--- explain
**思路**

流量超过系统处理能力时，如果所有请求都放进来，大家都会变慢、超时，最后谁都没有成功。**负载保护**（load shedding）：限制同时处理的请求数，超出的直接拒绝。再加上**优先级**：低优先级的请求只能使用一部分容量，即使它们很多，也会给核心链路（下单、支付）留出余量。

**代码讲解**

1. `inflight` 是当前在途请求数，加锁保护。
2. `Acquire(high)`：高优先级的上限是 `limit`，低优先级是 `limit * 80 / 100`（先乘后除，避免整数除法提前截断）。
3. 达到上限返回 false，调用方应立即返回“系统繁忙”（比如 HTTP 503 或 429）。
4. `Release` 在请求结束时调用，通常写成 `if s.Acquire(high) { defer s.Release(); ... }`。

**易错点**

- 局部变量叫 `max` 会**遮蔽**内置函数 max，在这个函数里就不能再调用 `max(...)` 了。这里没有用到内置的 max 所以能编译，但最好换个名字（如 `ceiling`）。
- 固定的 limit 需要通过压测确定；更高级的做法是**自适应限流**，根据 CPU 使用率、排队时间或延迟动态调整（如 Sentinel 的系统自适应保护、Netflix 的 concurrency-limits）。
- 应对流量突增的完整手段：提前扩容和预热、多级缓存、静态化、限流、降级非核心功能、异步化、熔断。

异地多活的常见做法是**单元化**：按用户 ID 把用户划分到不同的单元（每个单元是一个完整的、能独立服务的部署），一个用户的所有读写都在自己的单元内完成，避免跨地域的延迟和数据冲突。某个单元故障时，把它的用户切换到备份单元。

=== arch-20-2
--- explain
**思路**

多个地域异步复制时，同一条记录可能在两边几乎同时被修改，同步过来后需要决定保留哪一个。**LWW（Last Write Wins）**：时间戳大的胜出，时间戳相同时用地域名打破平局。只要比较规则是一个**全序**，`Merge` 就满足交换律、结合律和幂等性，无论消息以什么顺序到达、到达几次，所有地域最终都会收敛到同一个值。

**代码讲解**

1. 时间戳不同：大的胜出。
2. 时间戳相同：`a.Unit >= b.Unit` 时选 a，否则选 b。字符串可以直接比较大小（按字典序）。
3. 函数是纯函数，只返回结果、不修改参数。

**易错点**

- 时间戳相同时只按 `a` 优先（不比较地域）：`Merge(a, b)` 和 `Merge(b, a)` 的结果不同，违反交换律，两个地域会收敛到不同的值。
- LWW 的代价：被覆盖的写入会**悄悄丢失**，不同机器的时钟偏差还会让“后写”的反而输掉。
- 不能丢失更新的场景（比如计数器、购物车）可以用 **CRDT**（无冲突复制数据类型，比如 G-Counter 每个地域各自计数再求和），或者保证同一条记录只在一个单元写入（单元化）。
