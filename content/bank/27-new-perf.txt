=== perf-29-1
title: 实现磁盘满故障智能诊断器与安全日志原地截断（Truncate vs Remove）
race: true
--- desc
线上排查 `No space left on device` 时，需快速区分“Inode 耗尽”与“已 `rm` 但未关闭句柄的大文件未释放”，并在清理活跃日志时使用 `Truncate(0)` 而非 `os.Remove`。请实现：

1. `DiagnoseDiskFull(usedBytes, totalBytes, usedInodes, totalInodes, visibleDuBytes int64) string`：
   - 若 `usedInodes >= totalInodes`（且 `totalInodes > 0`），返回 `"inode_exhausted"`；
   - 若磁盘使用率 `usedBytes * 100 >= totalBytes * 90` **且** `usedBytes - visibleDuBytes > totalBytes / 5`（即 `df` 已用空间比 `du` 可见文件总和大了超过总容量的 20%），返回 `"deleted_open_files"`；
   - 否则返回 `"normal_disk_full"`；
2. `TruncateActiveLog(f *os.File) error`：
   - 严禁调用 `os.Remove`！请调用 `f.Truncate(0)` 将正在写入的日志文件长度原地截断为 0，并调用 `f.Seek(0, 0)` 将文件偏移量重置回开头。
--- solution
package main

import "os"

func DiagnoseDiskFull(usedBytes, totalBytes, usedInodes, totalInodes, visibleDuBytes int64) string {
	// @solution
	if totalInodes > 0 && usedInodes >= totalInodes {
		return "inode_exhausted"
	}
	if totalBytes > 0 && usedBytes*100 >= totalBytes*90 && (usedBytes-visibleDuBytes) > totalBytes/5 {
		return "deleted_open_files"
	}
	return "normal_disk_full"
	// @starter
	// return "" // TODO: 区分 inode_exhausted、deleted_open_files 和 normal_disk_full
	// @end
}

func TruncateActiveLog(f *os.File) error {
	// @solution
	if err := f.Truncate(0); err != nil {
		return err
	}
	_, err := f.Seek(0, 0)
	return err
	// @starter
	// return nil // TODO: 原地截断文件为 0 字节并将读写偏移量归零
	// @end
}

**思路**

1. **诊断模型**：先看 `df -i`（`usedInodes >= totalInodes` 则是小文件把 Inode 耗尽）；再对比 `df`（`usedBytes`）与 `du`（`visibleDuBytes`）的差值，若差值悬殊则必然存在已被 `rm` 但仍被进程打开的幽灵大文件（`lsof +L1`）。
2. **原地截断与偏移重置**：对一个未以 `O_APPEND` 打开的普通文件描述符调用 `f.Truncate(0)` 后，文件大小虽然变成了 0，但句柄当前的写入偏移量（offset）仍然停留在原来的高水位处！如果不调用 `f.Seek(0, 0)`，下一次 `Write` 会在原偏移量之前补齐一串 `\x00` 空洞（稀疏文件）。

**代码讲解**

- `f.Truncate(0)` 立即通知内核回收数据块，同时保持原 Inode 不变；紧接着 `f.Seek(0, 0)` 将游标拉回文件首部。

**易错点**

- 切记 `Truncate(0)` 不会自动修改文件描述符的 `offset`，必须配合 `Seek(0, 0)`。

=== perf-30-1
title: 实现 Linux nf_conntrack 连接跟踪表容量淘汰与 Early-Drop 驱逐模拟器
race: true
--- desc
为模拟并诊断 Linux 内核 `nf_conntrack: table full, dropping packet` 故障与内核表满自救机制，请实现连接跟踪表模拟器 `ConntrackTable` 的 `Track(tuple string, state string, ttlSec int64, nowSec int64) (accepted bool, reason string)`：

1. **已存在未过期表项刷新**：若 `tuple` 在表中且未过期（`nowSec < entry.expireAt`），更新其 `state` 和 `expireAt = nowSec + ttlSec`，返回 `(true, "updated")`；
2. **表满时的两级自救驱逐（当表中当前条目数 `>= maxEntries` 且本次为新五元组或已过期五元组时）**：
   - **第一级：清理所有已过期条目（Expired Eviction）**：遍历删除所有 `nowSec >= entry.expireAt` 的条目（例如已到期的 `TIME_WAIT` 连接）；
   - **第二级：Early-Drop 驱逐半连接（Unreplied Eviction）**：若清理过期条目后表依然满（`len >= maxEntries`），仿照 Linux 内核 `early_drop` 机制，寻找表中任意一条状态为 `"UNREPLIED"` 且 `expireAt` 最小（最早过期）的条目将其强制删除，并将 `t.EarlyDrops` 计数 `+1`；
3. **最终判定**：
   - 若经过上述两级驱逐后仍有空位（`len < maxEntries`），插入新条目 `{state: state, expireAt: nowSec + ttlSec}`，返回 `(true, "inserted")`；
   - 若表中全是未过期的 `"ESTABLISHED"` / `"TIME_WAIT"` 活跃连接导致无法腾出空位，将 `t.Drops` 计数 `+1`，返回 `(false, "table_full")`。
--- solution
package main

import "sync"

type conntrackEntry struct {
	state    string
	expireAt int64
}

type ConntrackTable struct {
	mu         sync.Mutex
	maxEntries int
	entries    map[string]*conntrackEntry
	EarlyDrops int64
	Drops      int64
}

func NewConntrackTable(maxEntries int) *ConntrackTable {
	return &ConntrackTable{
		maxEntries: maxEntries,
		entries:    make(map[string]*conntrackEntry),
	}
}

func (t *ConntrackTable) Track(tuple string, state string, ttlSec int64, nowSec int64) (bool, string) {
	// @solution
	t.mu.Lock()
	defer t.mu.Unlock()

	if ent, ok := t.entries[tuple]; ok {
		if nowSec < ent.expireAt {
			ent.state = state
			ent.expireAt = nowSec + ttlSec
			return true, "updated"
		}
		delete(t.entries, tuple)
	}

	if len(t.entries) >= t.maxEntries {
		for k, ent := range t.entries {
			if nowSec >= ent.expireAt {
				delete(t.entries, k)
			}
		}
	}

	if len(t.entries) >= t.maxEntries {
		var victimKey string
		var victimExpire int64
		for k, ent := range t.entries {
			if ent.state == "UNREPLIED" {
				if victimKey == "" || ent.expireAt < victimExpire || (ent.expireAt == victimExpire && k < victimKey) {
					victimKey = k
					victimExpire = ent.expireAt
				}
			}
		}
		if victimKey != "" {
			delete(t.entries, victimKey)
			t.EarlyDrops++
		}
	}

	if len(t.entries) >= t.maxEntries {
		t.Drops++
		return false, "table_full"
	}

	t.entries[tuple] = &conntrackEntry{
		state:    state,
		expireAt: nowSec + ttlSec,
	}
	return true, "inserted"
	// @starter
	// return false, "table_full" // TODO: 实现五元组更新、过期回收、UNREPLIED Early-Drop 与 table_full 丢包统计
	// @end
}

**思路**

这道题还原了 Linux 内核 `nf_conntrack` 表满时的真实防线与局限性：
1. **为什么调小 `nf_conntrack_tcp_timeout_time_wait` 能救命？** 因为只有当 `nowSec >= ent.expireAt` 时，大量的短连接 `TIME_WAIT` 表项才能被及时回收腾出槽位。
2. **为什么内核的 `early_drop` 救不了短连接风暴？** 因为内核 `early_drop` 只敢驱逐尚未收到回包的 `"UNREPLIED"` 半连接；如果表里塞满的全是已经完成握手的 `"ESTABLISHED"`（默认存活 5 天）或未到期的 `"TIME_WAIT"`（默认 120s），`early_drop` 找不到可驱逐目标，只能直接触发 `nf_conntrack: table full, dropping packet`（`Drops++`）！

**代码讲解**

- 按顺序执行：已存在未过期五元组原地续期 → 表满时先扫一遍回收 `nowSec >= ent.expireAt` 的过期表项 → 仍满则找最早到期的 `"UNREPLIED"` 表项执行 `EarlyDrops` → 依然满则记入 `Drops` 并返回 `"table_full"`。

**易错点**

- 如果 `tuple` 本身已经在表中但**已过期**（`nowSec >= ent.expireAt`），应当先将其旧记录删除，再作为新连接走后续容量判定与插入逻辑，返回值应为 `"inserted"` 而非 `"updated"`。

=== perf-31-1
title: 实现容器内存水位拆解与隐藏内存（Cgo / Mmap / PageCache）诊断器
race: true
--- desc
当容器发生 OOMKilled 或内存告警，但 `pprof/heap`（`HeapAlloc`）看起来很低时，需要通过运行时的完整内存账本定位真正的内存去向。请实现 `AnalyzeContainerMemory(s MemorySnapshot) string`：

给定快照 `MemorySnapshot`：
- `ContainerUsage`：容器 cgroup 统计的总内存用量
- `ProcessRSS`：Go 进程的物理内存占用（`VmRSS`）
- `GoHeapAlloc`：Go 存活堆对象大小
- `GoHeapIdleUnrel`：`HeapIdle - HeapReleased`（Go 未归还给操作系统的空闲堆页）
- `GoStackInuse`：所有 Goroutine 栈占用的内存

请按以下优先级返回占比最高（超过 30% `ContainerUsage`）的隐形内存元凶：
1. 若 `ContainerUsage - ProcessRSS > ContainerUsage * 30 / 100`（容器总用量远大于 Go 进程 RSS），说明是容器内 **PageCache 或其他子进程** 占用，返回 `"page_cache_or_subprocesses"`；
2. 若 `GoRunTimeKnown := GoHeapAlloc + GoHeapIdleUnrel + GoStackInuse`，且 `ProcessRSS - GoRunTimeKnown > ContainerUsage * 30 / 100`（进程 RSS 远大于 Go 运行时已知内存总和），说明存在 **Cgo / Mmap 堆外内存**，返回 `"off_heap_cgo_or_mmap"`；
3. 若 `GoStackInuse > ContainerUsage * 30 / 100`，说明是 **Goroutine 栈膨胀/泄漏**，返回 `"goroutine_stack_bloat"`；
4. 若 `GoHeapIdleUnrel > ContainerUsage * 30 / 100`，说明是 **Go 空闲堆未归还 OS（需配置 GOMEMLIMIT）**，返回 `"unreleased_heap_idle"`；
5. 否则返回 `"go_heap_alloc"`。
--- solution
package main

type MemorySnapshot struct {
	ContainerUsage  int64
	ProcessRSS      int64
	GoHeapAlloc     int64
	GoHeapIdleUnrel int64
	GoStackInuse    int64
}

func AnalyzeContainerMemory(s MemorySnapshot) string {
	// @solution
	threshold := s.ContainerUsage * 30 / 100
	if s.ContainerUsage-s.ProcessRSS > threshold {
		return "page_cache_or_subprocesses"
	}
	goRuntimeKnown := s.GoHeapAlloc + s.GoHeapIdleUnrel + s.GoStackInuse
	if s.ProcessRSS-goRuntimeKnown > threshold {
		return "off_heap_cgo_or_mmap"
	}
	if s.GoStackInuse > threshold {
		return "goroutine_stack_bloat"
	}
	if s.GoHeapIdleUnrel > threshold {
		return "unreleased_heap_idle"
	}
	return "go_heap_alloc"
	// @starter
	// return "" // TODO: 逐层比对 cgroup、ProcessRSS 与 Go Runtime 内部账本，定位隐形内存去向

=== perf-32-1
title: 实现火焰图折叠调用栈（Collapsed Stacks）的 Flat 与 Cum 热点统计器
race: true
--- desc
火焰图的底层标准输入格式是 Brendan Gregg 定义的折叠调用栈文本（每行格式为 `funcA;funcB;funcC 采样次数`，分号分隔从根到叶子的调用链）。请实现解析与统计函数 `ComputeFlameStats(lines []string) map[string]FlameStat`：

1. 输入每行形如 `"main;Handler;MarshalJSON 90"`（忽略空行或格式非法行）；
2. 对每个出现的函数名统计两个核心指标 `FlameStat{Flat int64, Cum int64}`：
   - **`Flat`（自身耗时/大平顶宽度）**：该函数作为调用栈**最末端叶子节点**（即分号切分后的最后一个函数）时的采样次数之和；
   - **`Cum`（累计耗时/底座总宽度）**：该函数出现在调用栈任意位置时的采样次数之和（注意：**若同一行调用栈中存在递归调用如 `A;B;A 10`，`A` 在该行的 `Cum` 只加一次 `10`，不能重复累加**！）。
--- solution
package main

import (
	"strconv"
	"strings"
)

type FlameStat struct {
	Flat int64
	Cum  int64
}

func ComputeFlameStats(lines []string) map[string]FlameStat {
	// @solution
	stats := make(map[string]FlameStat)
	for _, line := range lines {
		line = strings.TrimSpace(line)
		if line == "" {
			continue
		}
		spaceIdx := strings.LastIndexByte(line, ' ')
		if spaceIdx <= 0 {
			continue
		}
		stackStr := line[:spaceIdx]
		samples, err := strconv.ParseInt(strings.TrimSpace(line[spaceIdx+1:]), 10, 64)
		if err != nil {
			continue
		}
		frames := strings.Split(stackStr, ";")
		if len(frames) == 0 {
			continue
		}

		// 栈顶（最右侧叶子函数）计入 Flat
		leaf := frames[len(frames)-1]
		st := stats[leaf]
		st.Flat += samples
		stats[leaf] = st

		// 调用链上所有去重后的函数计入 Cum
		seen := make(map[string]struct{}, len(frames))
		for _, fn := range frames {
			if _, dup := seen[fn]; dup {
				continue
			}
			seen[fn] = struct{}{}
			s := stats[fn]
			s.Cum += samples
			stats[fn] = s
		}
	}
	return stats
	// @starter
	// return nil // TODO: 解析折叠调用栈，计算每个函数的 Flat（栈顶自身耗时）与 Cum（去重累计耗时）
	// @end
}

**思路**

这道题直接揭示了火焰图与 `pprof top` 中 `flat` 和 `cum` 的数学定义：
- **`Flat`（大平顶）**：采样中断发生时，CPU 的程序计数器（PC）正停在该函数内部执行指令（即它位于调用栈的最末端 `frames[len(frames)-1]`），这是优化代码的唯一直接目标。
- **`Cum`（底座宽）**：只要调用栈里包含该函数，就计入它的累计开销。

**代码讲解**

1. `leaf := frames[len(frames)-1]`：将样本数加到叶子函数的 `Flat` 上。
2. 遍历 `frames` 时用 `seen` 集合去重，防止递归函数 `Walk;Walk` 把单次 10ms 的采样重复累加变成 20ms（超过总采样数 100%）。

**易错点**

- 递归调用去重是 `pprof` 和火焰图工具链计算 `Cum` 时的经典边界条件。

=== perf-33-1
title: 实现消除滚动发布冷启动毛刺的线性慢启动（Slow-Start）权重计算器

--- desc
新节点刚上线的前几十秒内，由于连接池和本地缓存尚未预热，负载均衡器应采用**线性慢启动（Slow-Start Warmup）**逐步放大其流量权重。请实现：

1. `SlowStartWeight(uptime, warmupWindow time.Duration, minWeight float64) float64`：
   - 若 `warmupWindow <= 0` 或 `uptime >= warmupWindow`，说明预热已完成，返回满额权重 `1.0`；
   - 若 `uptime <= 0`，返回起步最小权重 `minWeight`；
   - 当 `0 < uptime < warmupWindow` 时，按时间进度比例 `ratio := float64(uptime) / float64(warmupWindow)` 计算，若 `ratio < minWeight` 则返回 `minWeight`，否则返回 `ratio`（即 `max(minWeight, min(1.0, uptime/warmupWindow))`）。
--- solution
package main

import "time"

func SlowStartWeight(uptime, warmupWindow time.Duration, minWeight float64) float64 {
	// @solution
	if warmupWindow <= 0 || uptime >= warmupWindow {
		return 1.0
	}
	if uptime <= 0 {
		return minWeight
	}
	ratio := float64(uptime) / float64(warmupWindow)
	if ratio < minWeight {
		return minWeight
	}
	return ratio
	// @starter
	// return 1.0 // TODO: 计算慢启动期间的动态流量权重
	// @end
}

package main

	return math.Abs(a-b) < 1e-6
}

func TestSlowStartWeight(t *testing.T) {
	window := 30 * time.Second
	minW := 0.1

	// 刚上线 0s 或 1s（1/30 = 0.033 < 0.1）时，使用保底权重 0.1
	if w := SlowStartWeight(0, window, minW); !almostEqual(w, 0.1) {
		t.Fatalf("uptime 0s weight = %v, want 0.1", w)

	if w := SlowStartWeight(time.Second, window, minW); !almostEqual(w, 0.1) {
		t.Fatalf("uptime 1s weight = %v, want 0.1", w)
	}

	// 上线 15s（半程）时，权重线性升至 0.5
	if w := SlowStartWeight(15*time.Second, window, minW); !almostEqual(w, 0.5) {
		t.Fatalf("uptime 15s weight = %v, want 0.5", w)
	}

	// 满 30s 及以后，恢复 1.0 全量权重
	if w := SlowStartWeight(30*time.Second, window, minW); !almostEqual(w, 1.0) {
		t.Fatalf("uptime 30s weight = %v, want 1.0", w)
	}
	if w := SlowStartWeight(2*time.Minute, window, minW); !almostEqual(w, 1.0) {
		t.Fatalf("uptime 2m weight = %v, want 1.0", w)
	}
}

**思路**

Envoy 的 `slow_start_config` 与 gRPC 慢启动负载均衡器的核心思想是：新实例通过 Readiness 探针上线后，不要第 1 秒就给它 100% 的流量，而是从 `minWeight`（如 10%）开始，在 `warmupWindow`（如 30 秒）内随时间线性增加到 100%，给足连接池建连和本地缓存预热的缓冲期。

**代码讲解**

- 先处理 `warmupWindow <= 0 || uptime >= warmupWindow` 的短路分支（返回 `1.0`），这也是节点稳定运行 99.9% 时间所走的快路径。

**易错点**

- 必须设置保底权重 `minWeight`（如 `0.1`），否则在刚上线 `uptime == 0` 的一瞬间权重为 `0`，新节点永远分不到第一批触发预热的请求。

=== perf-34-1
title: 实现防磁盘 I/O 雪崩的窗口日志采样器（zap Sampler 核心算法）
race: true
--- desc
当下游故障导致每秒爆发数万条相同报错日志时，全量刷盘会打满磁盘 I/O 并锁死业务协程。请仿照 `uber-go/zap` 的 `zapcore.sampler` 实现按时间窗口与消息模板采样的 `LogSampler`：

1. `NewLogSampler(window time.Duration, first, thereafter int) *LogSampler`：
   - 在每个固定时间窗口 `window`（按 `now.UnixNano() / int64(window)` 划分窗口槽位 `tick`）内，按日志消息键 `msgKey` 独立计数（从 `1` 开始）；
2. `ShouldLog(msgKey string, now time.Time) bool`：
   - 若该 `msgKey` 进入了新的时间窗口 `tick`，将其计数重置为 `1`；否则计数 `+1`；
   - 若当前窗口内计数 `n <= first`：返回 `true`（每个窗口的前 `first` 条日志 100% 放行，保留完整故障第一现场）；
   - 若 `n > first`：仅当 `thereafter > 0 && (n - first) % thereafter == 0` 时返回 `true`（之后每 `thereafter` 条只采样打印 1 条），其余返回 `false`。
--- solution
package main

import (
	"sync"
	"time"
)

type sampleCounter struct {
	tick  int64
	count int
}

type LogSampler struct {
	mu         sync.Mutex
	window     time.Duration
	first      int
	thereafter int
	counters   map[string]*sampleCounter
}

func NewLogSampler(window time.Duration, first, thereafter int) *LogSampler {
	return &LogSampler{
		window:     window,
		first:      first,
		thereafter: thereafter,
		counters:   make(map[string]*sampleCounter),
	}
}

func (s *LogSampler) ShouldLog(msgKey string, now time.Time) bool {
	// @solution
	tick := now.UnixNano() / int64(s.window)
	s.mu.Lock()
	c, ok := s.counters[msgKey]
	if !ok || c.tick != tick {
		c = &sampleCounter{tick: tick, count: 1}
		s.counters[msgKey] = c
	} else {
		c.count++
	}
	n := c.count
	s.mu.Unlock()

	if n <= s.first {
		return true
	}
	if s.thereafter <= 0 {
		return false
	}
	return (n-s.first)%s.thereafter == 0
	// @starter
	// return true // TODO: 每个时间窗口前 first 条全放行，超出后每 thereafter 条采样 1 条
	// @end
}
--- test
package main

import (
	"testing"
	"time"
)

func TestLogSamplerBurstProtection(t *testing.T) {
	// 每秒窗口内：前 5 条全打，之后每 100 条打 1 条
	sampler := NewLogSampler(time.Second, 5, 100)
	t0 := time.Unix(1700000000, 0)

	allowed := 0
	for range 1005 {
		if sampler.ShouldLog("redis_conn_timeout", t0) {
			allowed++
		}
	}
	// 1005 条相同报错日志：前 5 条 + 后续 1000 条采样 10 条 = 仅写入 15 条！削减 98.5% I/O
	if allowed != 15 {
		t.Fatalf("allowed logs in 1005 burst = %d, want 15 (5 + 1000/100)", allowed)
	}

	// 同一秒内另一种全新的报错类型不受影响，依然能打出前 5 条
	if !sampler.ShouldLog("mysql_deadlock", t0) {
		t.Fatal("different error key must have its own quota")
	}

	// 进入下一秒窗口（t0 + 1s），配额自动恢复
	if !sampler.ShouldLog("redis_conn_timeout", t0.Add(time.Second)) {
		t.Fatal("new time window should reset counter")
	}
}
--- explain
**思路**

这是 `uber-go/zap` 生产环境默认开启的 `NewSamplerWithOptions` 算法：
- 为什么不能用固定概率随机采样（如 1% 随机打印）？因为如果某类偶发关键报错一秒只出现了 3 次，1% 随机采样大概率会把这 3 条全丢掉，导致死无对证！
- **`first + thereafter` 策略**：保证任何错误在每秒钟的前 `first`（如 10）次**100% 必打**，只有当同一秒内爆发第 11~100000 次刷屏时，才开启每 `thereafter`（如 100）次抽 1 次的降频保护。

**代码讲解**

1. `tick := now.UnixNano() / int64(s.window)`：将时间戳映射到离散的时间窗口编号。
2. 当 `c.tick != tick` 时原地重置 `count = 1`，无需后台启动清理定时器。

**易错点**

- 注意当 `s.thereafter == 0`（含义是超过 `first` 后彻底静默丢弃）时，不能执行 `% s.thereafter`，必须先判断 `if s.thereafter <= 0 { return false }` 防止除以 0 panic。

=== perf-35-1
title: 实现多可用区容灾的同机房亲和路由（Zone-Aware Routing）选择器
race: true
--- desc
为消除跨可用区（Cross-AZ）网络抖动毛刺并节省跨机房带宽费，微服务客户端应优先路由到**同可用区（Same Zone）**的健康节点，但当本可用区健康节点占比过低时需自动降级到全集群路由。请实现 `SelectZoneEndpoints(clientZone string, all []Endpoint, minLocalHealthyRatio float64) []Endpoint`：

1. 每个 `Endpoint` 包含 `Addr string`、`Zone string`、`Healthy bool`；
2. 统计所有 `Healthy == true` 的全局健康节点列表 `globalHealthy`，以及位于 `clientZone` 的总节点数 `localTotal` 和健康节点列表 `localHealthy`；
3. **亲和判定**：只有当 `localTotal > 0`、`len(localHealthy) > 0`，且本可用区健康率 `float64(len(localHealthy)) / float64(localTotal) >= minLocalHealthyRatio` 时，返回 `localHealthy`（仅在同机房内部转发）；
4. **故障溢出降级（Fallback）**：否则返回全集群健康节点 `globalHealthy`（避免本机房仅存的 1 台机器被全量流量压垮）。
--- solution
package main

type Endpoint struct {
	Addr    string
	Zone    string
	Healthy bool
}

func SelectZoneEndpoints(clientZone string, all []Endpoint, minLocalHealthyRatio float64) []Endpoint {
	// @solution
	var globalHealthy []Endpoint
	var localHealthy []Endpoint
	localTotal := 0

	for _, ep := range all {
		if ep.Zone == clientZone {
			localTotal++
			if ep.Healthy {
				localHealthy = append(localHealthy, ep)
			}
		}
		if ep.Healthy {
			globalHealthy = append(globalHealthy, ep)
		}
	}

	if localTotal > 0 && len(localHealthy) > 0 {
		ratio := float64(len(localHealthy)) / float64(localTotal)
		if ratio >= minLocalHealthyRatio {
			return localHealthy
		}
	}
	return globalHealthy
	// @starter
	// return nil // TODO: 本机房健康率达标时只返回 localHealthy，否则降级返回 globalHealthy
	// @end
}
--- test
package main

import "testing"

func TestSelectZoneEndpoints(t *testing.T) {
	cluster := []Endpoint{
		{Addr: "10.1.0.1", Zone: "az-a", Healthy: true},
		{Addr: "10.1.0.2", Zone: "az-a", Healthy: true},
		{Addr: "10.1.0.3", Zone: "az-a", Healthy: false}, // az-a 2/3 健康 (66.7%)
		{Addr: "10.2.0.1", Zone: "az-b", Healthy: true},
		{Addr: "10.2.0.2", Zone: "az-b", Healthy: true},
	}

	// 1. 阈值设为 0.5（50%）：az-a 健康率 66.7% >= 50%，100% 走同机房 az-a 的 2 台节点
	got1 := SelectZoneEndpoints("az-a", cluster, 0.5)
	if len(got1) != 2 || got1[0].Zone != "az-a" || got1[1].Zone != "az-a" {
		t.Fatalf("expected 2 local az-a endpoints, got %+v", got1)
	}

	// 2. az-a 又挂了 1 台，只剩 1/3 (33.3% < 50%) 健康 -> 触发安全水位保护，降级到全集群 3 台健康节点！
	cluster[1].Healthy = false
	got2 := SelectZoneEndpoints("az-a", cluster, 0.5)
	if len(got2) != 3 {
		t.Fatalf("expected fallback to all 3 global healthy endpoints when local ratio < 0.5, got %+v", got2)
	}
}
--- explain
**思路**

同可用区亲和路由（如 Envoy `zone_aware_routing` / K8s Topology Aware Hints）为什么必须设一个 **`minLocalHealthyRatio`（通常 50%~60%）安全水位线**？
假设 `az-a` 原本有 10 台下游机器，突然挂了 9 台只剩 1 台存活。如果不判断健康占比，仍然死板地遵守“本机房有存活节点就只调本机房”，那么 `az-a` 10 台上游机器的 100% 流量会全部砸向那仅存的 1 台下游机器，瞬间将其压爆引发连环雪崩！因此当本机房健康率低于阈值时，必须立即打破机房隔离，将流量打散到全集群所有健康节点。

**代码讲解**

- 一次遍历同时收集 `localTotal`、`localHealthy` 和 `globalHealthy`，当 `float64(len(localHealthy))/float64(localTotal) >= minLocalHealthyRatio` 时返回 `localHealthy`，否则兜底返回 `globalHealthy`。

**易错点**

- 注意计算比例前先判断 `localTotal > 0`，防止客户端所在可用区原本就没有部署任何下游实例时发生 `0.0 / 0.0 = NaN`。
