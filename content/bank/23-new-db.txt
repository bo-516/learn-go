=== db-32-1
title: 模拟索引下推（ICP）与 MRR 顺序回表优化
--- desc
模拟 InnoDB 的二级索引查询加上 **ICP（索引下推）** 与 **MRR（Multi-Range Read）**：

二级索引条目 `IndexEntry` 包含 `(Category, Price, Status, PrimaryKey)`，并且输入的 `entries` 已经按 `(Category, Price)` 排序。
实现 `QueryByICPAndMRR(entries []IndexEntry, category string, minPrice, maxPrice int, targetStatus int) (rows []string, tableLookups int)`：

1. 只挑选满足 `Category == category` 且 `minPrice <= Price <= maxPrice` 的二级索引项；
2. **索引下推（ICP）**：在回表前，直接利用二级索引中的 `Status == targetStatus` 过滤掉不匹配的条目；
3. **多范围读（MRR）**：对需要回表的 `PrimaryKey` 先**去重并按升序排序**，然后依次从聚簇索引表 `clusteredTable map[int64]string`（这里通过传入的 `fetchRow func(pk int64) string` 模拟）读取行数据，统计实际回表次数 `tableLookups`。
--- solution
package main

import "slices"

type IndexEntry struct {
	Category   string
	Price      int
	Status     int
	PrimaryKey int64
}

func QueryByICPAndMRR(
	entries []IndexEntry,
	category string,
	minPrice, maxPrice int,
	targetStatus int,
	fetchRow func(pk int64) string,
) (rows []string, tableLookups int) {
	// @solution
	var pks []int64
	for _, e := range entries {
		if e.Category != category || e.Price < minPrice || e.Price > maxPrice {
			continue
		}
		// ICP：在二级索引层直接过滤 Status，避免无效回表
		if e.Status != targetStatus {
			continue
		}
		pks = append(pks, e.PrimaryKey)
	}
	// MRR：按主键升序排序并去重后再顺序回表
	slices.Sort(pks)
	pks = slices.Compact(pks)
	rows = make([]string, 0, len(pks))
	for _, pk := range pks {
		tableLookups++
		rows = append(rows, fetchRow(pk))
	}
	return rows, tableLookups
	// @starter
	// // TODO: 先用 ICP 过滤出满足条件的 PrimaryKey，再用 slices.Sort 升序排序后调用 fetchRow
	// return nil, 0
	// @end
}
--- test
package main

import (
	"fmt"
	"slices"
	"testing"
)

func TestQueryByICPAndMRR(t *testing.T) {
	entries := []IndexEntry{
		{Category: "book", Price: 30, Status: 1, PrimaryKey: 90},
		{Category: "book", Price: 40, Status: 0, PrimaryKey: 20}, // Status 不匹配，应被 ICP 过滤不回表
		{Category: "book", Price: 50, Status: 1, PrimaryKey: 10},
		{Category: "book", Price: 60, Status: 0, PrimaryKey: 5},  // Status 不匹配
		{Category: "book", Price: 70, Status: 1, PrimaryKey: 50},
		{Category: "game", Price: 40, Status: 1, PrimaryKey: 1},
	}
	var visitedPKs []int64
	rows, lookups := QueryByICPAndMRR(entries, "book", 25, 75, 1, func(pk int64) string {
		visitedPKs = append(visitedPKs, pk)
		return fmt.Sprintf("row-%d", pk)
	})
	if lookups != 3 {
		t.Fatalf("tableLookups = %d, want 3 (ICP should skip status!=1)", lookups)
	}
	// 验证 MRR：回表顺序必须按主键升序 10 -> 50 -> 90，而不是原二级索引里的乱序 90 -> 10 -> 50
	if !slices.Equal(visitedPKs, []int64{10, 50, 90}) {
		t.Fatalf("visitedPKs = %v, want [10 50 90]", visitedPKs)
	}
	if !slices.Equal(rows, []string{"row-10", "row-50", "row-90"}) {
		t.Fatalf("rows = %v", rows)
	}
}
--- explain
**思路**

没有 ICP 时，范围条件 `25 <= Price <= 75` 命中的 5 条 `"book"` 记录都要先调用 `fetchRow(pk)` 回表，再过滤 `Status == 1`；有了 ICP 后，直接在扫描 `IndexEntry` 时检查 `e.Status == targetStatus`，将回表次数从 5 次降为 3 次。接着通过 `slices.Sort(pks)`（MRR）把原本乱序的主键 `[90, 10, 50]` 排成升序 `[10, 50, 90]`，实现聚簇索引的顺序页读取。

**代码讲解**

1. `if e.Status != targetStatus { continue }`：在二级索引扫描阶段直接完成过滤（ICP）。
2. `slices.Sort(pks)` 和 `slices.Compact(pks)`：排序并去重主键值（MRR）。
3. 按排好序的 `pks` 依次调用 `fetchRow(pk)` 并统计回表次数。

**易错点**

- 如果边扫二级索引边立刻调用 `fetchRow(e.PrimaryKey)`，回表顺序就是 `[90, 10, 50]`，失去了 MRR 顺序访问聚簇索引的效果。

=== db-33-1
title: 生成时间有序的 UUIDv7（RFC 9562）并提取毫秒时间戳
--- desc
InnoDB 使用随机 UUIDv4 作为主键会导致严重的 B+ 树页分裂，而 **UUIDv7（RFC 9562）** 将 48 位毫秒级 Unix 时间戳放在最前面的高 6 字节，使其天然按时间单调递增。

请实现两个函数：

1. `MakeUUIDv7(ms int64, randBytes [10]byte) [16]byte`：
   - 前 6 个字节（`b[0..5]`）按**大端序（Big-Endian）**写入 `ms` 的低 48 位（毫秒时间戳）；
   - 后 10 个字节（`b[6..15]`）先填入 `randBytes`；
   - 将 `b[6]` 的高 4 位设为版本号 `7`（即 `0111xxxx`，`b[6] = (b[6] & 0x0f) | 0x70`）；
   - 将 `b[8]` 的高 2 位设为 RFC 4122 变体 `10xxxxxx`（即 `b[8] = (b[8] & 0x3f) | 0x80`）。
2. `ExtractUUIDv7Millis(u [16]byte) int64`：从 UUIDv7 的前 6 个字节还原出 48 位毫秒时间戳。
--- solution
package main

func MakeUUIDv7(ms int64, randBytes [10]byte) [16]byte {
	var b [16]byte
	// @solution
	ts := uint64(ms)
	b[0] = byte(ts >> 40)
	b[1] = byte(ts >> 32)
	b[2] = byte(ts >> 24)
	b[3] = byte(ts >> 16)
	b[4] = byte(ts >> 8)
	b[5] = byte(ts)
	copy(b[6:], randBytes[:])
	b[6] = (b[6] & 0x0f) | 0x70
	b[8] = (b[8] & 0x3f) | 0x80
	// @starter
	// // TODO: 按大端序写入 48 位时间戳并设置 version(7) 和 variant 位
	// @end
	return b
}

func ExtractUUIDv7Millis(u [16]byte) int64 {
	// @solution
	ts := uint64(u[0])<<40 |
		uint64(u[1])<<32 |
		uint64(u[2])<<24 |
		uint64(u[3])<<16 |
		uint64(u[4])<<8 |
		uint64(u[5])
	return int64(ts)
	// @starter
	// return 0 // TODO: 从 u[0:6] 还原大端序毫秒时间戳
	// @end
}
--- test
package main

import (
	"bytes"
	"testing"
)

func TestUUIDv7OrderAndTimestamp(t *testing.T) {
	r := [10]byte{0xff, 0xff, 0xff, 0xff, 0xff, 0xff, 0xff, 0xff, 0xff, 0xff}
	u1 := MakeUUIDv7(1730000000000, r)
	u2 := MakeUUIDv7(1730000000001, r)

	// 验证版本号与变体位
	if u1[6]>>4 != 7 {
		t.Fatalf("version nibble = %d, want 7", u1[6]>>4)
	}
	if u1[8]>>6 != 0b10 {
		t.Fatalf("variant bits = %02b, want 10", u1[8]>>6)
	}
	// 验证时间戳提取
	if got := ExtractUUIDv7Millis(u1); got != 1730000000000 {
		t.Fatalf("ExtractUUIDv7Millis = %d, want 1730000000000", got)
	}
	// 验证字节序单调递增（可直接用于 InnoDB BINARY(16) 主键顺序比较）
	if bytes.Compare(u1[:], u2[:]) >= 0 {
		t.Fatalf("expected u1 < u2 in lexicographical byte order")
	}
}
--- explain
**思路**

为了让生成的 16 字节二进制主键在按字节序（`bytes.Compare` 或 MySQL `BINARY(16)`）比较时与时间先后顺序完全一致，前 6 个字节必须采用**大端序（Big-Endian，高位字节在前）**存储 48 位毫秒时间戳；随后按位掩码清除并写入 4 位版本号 `0x70` 和 2 位变体号 `0x80`。

**代码讲解**

1. `b[0] = byte(ts >> 40)` ～ `b[5] = byte(ts)`：将 48 位整数从最高字节到最低字节依次放入 `b[0..5]`。
2. `b[6] = (b[6] & 0x0f) | 0x70`：`& 0x0f` 清零高 4 位，`| 0x70` 将高 4 位设为 `0111`（即十进制 7）。
3. `b[8] = (b[8] & 0x3f) | 0x80`：`& 0x3f` 清零高 2 位，`| 0x80` 将高 2 位设为 `10`。

**易错点**

- 提取时间戳移位拼接时，必须先将 `u[i]` 转为 `uint64(u[i])` 再左移 `<< 40`，否则 `byte` 类型直接左移会溢出归零（编译报错）。

=== db-34-1
title: 根据 ROW 格式 Binlog 事件生成逆向闪回（Flashback）数据
--- desc
当 `binlog_format = ROW` 且 `binlog_row_image = FULL` 时，误操作可以通过反转 Binlog 事件来恢复（Flashback）：

- `INSERT` 事件变为 `DELETE`（保留 `After` 作为 `Before`）；
- `DELETE` 事件变为 `INSERT`（将原 `Before` 作为新 `After`）；
- `UPDATE` 事件仍为 `UPDATE`，但将修改前镜像 `Before` 和修改后镜像 `After` **互换**；
- 最终生成的回滚事件列表必须按原事件顺序**倒序排列**（后发生的修改先回滚）！

请实现 `BuildFlashbackEvents(events []BinlogEvent) []BinlogEvent`。
--- solution
package main

type OpType string

const (
	OpInsert OpType = "INSERT"
	OpUpdate OpType = "UPDATE"
	OpDelete OpType = "DELETE"
)

type BinlogEvent struct {
	Op     OpType
	Before map[string] string
	After  map[string]string
}

func BuildFlashbackEvents(events []BinlogEvent) []BinlogEvent {
	out := make([]BinlogEvent, 0, len(events))
	// @solution
	for i := len(events) - 1; i >= 0; i-- {
		ev := events[i]
		switch ev.Op {
		case OpInsert:
			out = append(out, BinlogEvent{Op: OpDelete, Before: ev.After})
		case OpDelete:
			out = append(out, BinlogEvent{Op: OpInsert, After: ev.Before})
		case OpUpdate:
			out = append(out, BinlogEvent{Op: OpUpdate, Before: ev.After, After: ev.Before})
		}
	}
	// @starter
	// // TODO: 从后往前遍历 events，反转操作类型与 Before/After 镜像
	// @end
	return out
}
--- test
package main

import (
	"reflect"
	"testing"
)

func TestBuildFlashbackEvents(t *testing.T) {
	events := []BinlogEvent{
		{Op: OpInsert, After: map[string]string{"id": "1", "val": "a"}},
		{Op: OpUpdate, Before: map[string]string{"id": "1", "val": "a"}, After: map[string]string{"id": "1", "val": "b"}},
		{Op: OpDelete, Before: map[string]string{"id": "1", "val": "b"}},
	}
	got := BuildFlashbackEvents(events)
	want := []BinlogEvent{
		{Op: OpInsert, After: map[string]string{"id": "1", "val": "b"}},
		{Op: OpUpdate, Before: map[string]string{"id": "1", "val": "b"}, After: map[string]string{"id": "1", "val": "a"}},
		{Op: OpDelete, Before: map[string]string{"id": "1", "val": "a"}},
	}
	if !reflect.DeepEqual(got, want) {
		t.Fatalf("got %+v, want %+v", got, want)
	}
}
--- explain
**思路**

如果同一行数据先后经历了 `INSERT (a) -> UPDATE (a->b) -> DELETE (b)`，回滚时必须**从后往前倒序执行**：先恢复最后被删掉的 `INSERT (b)`，再把 `b` 改回 `a`（`UPDATE b->a`），最后删掉最初插入的 `DELETE (a)`。

**代码讲解**

1. `for i := len(events) - 1; i >= 0; i--`：倒序遍历所有误操作事件。
2. `OpInsert` 变 `OpDelete`（删除刚插入的 `ev.After`），`OpDelete` 变 `OpInsert`（重新插入被删掉的 `ev.Before`），`OpUpdate` 交换 `Before` 和 `After`。

**易错点**

- 如果不倒序而是正序回放逆向事件，当同一主键在同一个事务里被连续修改多次时，回滚结果会停留在错误的中间状态。

=== db-35-1
title: 使用泛型 sql.Null[T] 处理数据库可空列与动态 IN 查询占位符构造
--- desc
实现两个日常编写 Go SQL 访问层最常用的辅助函数：

1. `NullOrValue[T any](n sql.Null[T], fallback T) T`：如果 Go 1.22+ 的 `sql.Null[T]` 有效（`n.Valid == true`），返回 `n.V`；否则（数据库列为 `NULL`）返回默认值 `fallback`；
2. `BuildInQuery[T any](baseSQL string, items []T) (query string, args []any, err error)`：将包含单个 `"(?)"` 占位符的 `baseSQL`（例如 `"SELECT id FROM users WHERE id IN (?)"`）按 `len(items)` 展开为 `"SELECT id FROM users WHERE id IN (?, ?, ?)"`，并返回转换后的 `[]any` 参数切片；若 `len(items) == 0`，返回错误（防止生成非法的 `IN ()` 语法）。
--- solution
package main

import (
	"database/sql"
	"errors"
	"strings"
)

func NullOrValue[T any](n sql.Null[T], fallback T) T {
	// @solution
	if n.Valid {
		return n.V
	}
	return fallback
	// @starter
	// return fallback // TODO: 检查 n.Valid
	// @end
}

func BuildInQuery[T any](baseSQL string, items []T) (string, []any, error) {
	// @solution
	if len(items) == 0 {
		return "", nil, errors.New("empty slice for IN clause")
	}
	placeholders := strings.Repeat("?, ", len(items)-1) + "?"
	query := strings.Replace(baseSQL, "(?)", "("+placeholders+")", 1)
	args := make([]any, len(items))
	for i, v := range items {
		args[i] = v
	}
	return query, args, nil
	// @starter
	// return "", nil, nil // TODO: 校验空切片、替换 (?) 并构造 []any 参数
	// @end
}
--- test
package main

import (
	"database/sql"
	"slices"
	"testing"
)

func TestNullOrValueAndBuildInQuery(t *testing.T) {
	v1 := sql.Null[string]{V: "alice", Valid: true}
	v2 := sql.Null[string]{Valid: false}
	if got := NullOrValue(v1, "anon"); got != "alice" {
		t.Fatalf("got %q, want alice", got)
	}
	if got := NullOrValue(v2, "anon"); got != "anon" {
		t.Fatalf("got %q, want anon", got)
	}

	q, args, err := BuildInQuery("SELECT * FROM orders WHERE id IN (?)", []int{10, 20, 30})
	if err != nil {
		t.Fatalf("unexpected err: %v", err)
	}
	wantQ := "SELECT * FROM orders WHERE id IN (?, ?, ?)"
	if q != wantQ {
		t.Fatalf("query = %q, want %q", q, wantQ)
	}
	if len(args) != 3 || !slices.Equal([]int{args[0].(int), args[1].(int), args[2].(int)}, []int{10, 20, 30}) {
		t.Fatalf("args = %v", args)
	}

	if _, _, err := BuildInQuery("SELECT * FROM orders WHERE id IN (?)", []int{}); err == nil {
		t.Fatal("expected error for empty items slice")
	}
}
--- explain
**思路**

1. Go 1.22 引入了泛型 `sql.Null[T]`，统一了以往繁琐的 `sql.NullString`、`sql.NullInt64` 等类型，通过 `n.Valid` 判断是否为非 `NULL`。
2. `database/sql` 不支持直接把 `[]int` 传给单个 `?` 展开成 `IN (1, 2, 3)`，必须根据切片长度动态生成对应数量的 `?, ?, ?` 占位符并将元素转为 `[]any`（参数化查询，绝对不能直接把用户字符串拼进 SQL 以防注入！）。

**代码讲解**

1. `if len(items) == 0`：SQL 中 `WHERE id IN ()` 是语法错误，必须在构造阶段拦截报错。
2. `strings.Repeat("?, ", len(items)-1) + "?"`：生成精确数量的问号占位符。
3. 将 `[]T` 逐个放入 `[]any` 供 `db.QueryContext(ctx, query, args...)` 安全绑定参数。

**易错点**

- 传入空切片 `[]int{}` 时如果不提前拦截，拼出来的 `WHERE id IN ()` 发到 MySQL 会直接报 1064 语法错误。

=== db-36-1
title: 实现支持 Context 路由标记、事务感知与从库延迟水位熔断的读写分离路由器
race: true
--- desc
实现生产级读写分离路由器 `DBRouter`，综合处理**显式主库标记、事务上下文、SQL 读写/加锁识别、以及从库复制延迟（Replication Lag）超阈值自动熔断与轮询负载均衡**：

1. **Context 路由标记**：
   - `WithPrimary(ctx context.Context) context.Context`：显式标记本次查询强制走主库；
   - `WithTx(ctx context.Context) context.Context`：标记当前操作处于数据库事务内；
2. **动态更新从库延迟水位**：
   - `UpdateReplicaLag(replica string, lag time.Duration)`：并发安全地记录某个从库当前的复制延迟（未上报过的从库默认延迟为 `0`）；
3. **综合路由决策 `RouteSQL(ctx context.Context, sqlStr string) string`**：
   - 若 `ctx` 被 `WithPrimary(ctx)` 或 `WithTx(ctx)` 标记过，必须返回 `primary`（事务内的任何查询都必须走主库连接）；
   - 将 `sqlStr` 去除首尾空格并转为大写后：若**不是**以 `"SELECT "` 开头（如 `INSERT`、`UPDATE`、`DELETE`），或者包含悲观锁子句 `"FOR UPDATE"` 或 `"LOCK IN SHARE MODE"`，必须返回 `primary`；
   - 否则，从 `replicas` 中按原顺序筛选出当前延迟 **`lag <= maxLag`** 的健康从库列表 `healthy`：
     - 若 `healthy` 为空（未配置从库，或所有从库延迟均超过 `maxLag` 触发熔断），自动降级回退返回 `primary`；
     - 否则使用原子计数器 `seq := r.rr.Add(1)`，按 `(seq - 1) % uint64(len(healthy))` 在健康从库间轮询返回 `healthy[idx]`。

func WithPrimary(ctx context.Context) context.Context {

	// @starter

	// @end

	// @solution

	// @starter

type DBRouter struct {
	primary  string
	replicas []string
	maxLag   time.Duration
	rr       atomic.Uint64
	mu       sync.RWMutex
	lags     map[string]time.Duration
}

func NewDBRouter(primary string, replicas []string, maxLag time.Duration) *DBRouter {
	return &DBRouter{
		primary:  primary,
		replicas: replicas,
		maxLag:   maxLag,
		lags:     make(map[string]time.Duration),
	}
}

func (r *DBRouter) UpdateReplicaLag(replica string, lag time.Duration) {
	// @solution
	r.mu.Lock()
	r.lags[replica] = lag
	r.mu.Unlock()
	// @starter
	// // TODO: 并发安全地更新从库复制延迟水位
	// @end
}

func (r *DBRouter) RouteSQL(ctx context.Context, sqlStr string) string {
	// @solution
	if force, _ := ctx.Value(ctxPrimaryKey{}).(bool); force {
		return r.primary
	}
	if inTx, _ := ctx.Value(ctxTxKey{}).(bool); inTx {
		return r.primary
	}
	upper := strings.ToUpper(strings.TrimSpace(sqlStr))
	if !strings.HasPrefix(upper, "SELECT ") ||
		strings.Contains(upper, "FOR UPDATE") ||
		strings.Contains(upper, "LOCK IN SHARE MODE") {
		return r.primary
	}

	r.mu.RLock()
	healthy := make([]string, 0, len(r.replicas))
	for _, rep := range r.replicas {
		if r.lags[rep] <= r.maxLag {
			healthy = append(healthy, rep)
		}
	}
	r.mu.RUnlock()

	if len(healthy) == 0 {
		return r.primary
	}
	idx := (r.rr.Add(1) - 1) % uint64(len(healthy))
	return healthy[idx]
	// @starter
	// return "" // TODO: 检查 WithPrimary/WithTx、写语句与加锁读，筛选延迟 <= maxLag 的健康从库轮询或熔断回退主库
	// @end
}

func TestDBRouterComprehensive(t *testing.T) {
	r := NewDBRouter("master", []string{"rep-1", "rep-2", "rep-3"}, 3*time.Second)

		t.Fatalf("SELECT with WithPrimary routed to %q, want master", node)

		r.RouteSQL(bg, "SELECT * FROM products"),

	if !slices.Equal(healthyGot, []string{"rep-1", "rep-3"}) {
		t.Fatalf("after rep-2 lag spike, got %v, want [rep-1 rep-3]", healthyGot)
	}

	// 5. 所有从库延迟均超阈值时，自动熔断回退到主库 master
	r.UpdateReplicaLag("rep-1", 5*time.Second)
	r.UpdateReplicaLag("rep-3", 6*time.Second)
	if node := r.RouteSQL(bg, "SELECT * FROM products"); node != "master" {
		t.Fatalf("when all replicas lag, got %q, want master", node)
	}

	// 6. rep-2 追平延迟后自动恢复挂载
	r.UpdateReplicaLag("rep-2", 200*time.Millisecond)
	if node := r.RouteSQL(bg, "SELECT * FROM products"); node != "rep-2" {
		t.Fatalf("when rep-2 recovers, got %q, want rep-2", node)
	}

		wg.Add(1)
		go func(id int) {
			defer wg.Done()
			for j := range 50 {
				r.UpdateReplicaLag("rep-1", time.Duration(j%5)*time.Second)
				_ = r.RouteSQL(bg, "SELECT id FROM users")
			}
		}(i)
	}
	wg.Wait()

**思路**

读写分离路由器不能简单地按“是不是 `SELECT`”一刀切，必须依次守住四道防线：
1. **Context 显式路由与事务感知**：通过 `WithPrimary`（关键写后即读）或 `WithTx`（事务内的读必须复用主库事务连接）直接路由到 `primary`；
2. **加锁读拦截**：`SELECT ... FOR UPDATE` 和 `LOCK IN SHARE MODE` 需要加行锁，从库是只读的，必须发往 `primary`；
3. **从库延迟水位健康过滤**：读锁检查 `r.lags[rep] <= r.maxLag`，动态剔除复制延迟超标的慢从库；
4. **原子轮询与全熔断兜底**：在健康从库列表上用 `(r.rr.Add(1) - 1) % uint64(len(healthy))` 轮询；若全部从库延迟超标则降级回退到 `primary`。

**代码讲解**

1. `ctxPrimaryKey{}` 与 `ctxTxKey{}`：使用独立的私有空结构体类型作为 `context.WithValue` 的 key，零内存分配且绝不与外部包 key 冲突。
2. `strings.Contains(upper, "FOR UPDATE")`：拦截伪装成普通 `SELECT` 的当前读（加锁读）。
3. `healthy` 切片过滤与 `r.rr.Add(1)`：仅对健康从库消耗轮询序号，写请求与主库直连请求不干扰从库负载均衡节奏。

**易错点**

- 忘记拦截 `SELECT ... FOR UPDATE`，会导致加锁读落到只读从库（`read_only=ON`）直接报错失败。
- 所有从库延迟超标导致 `len(healthy) == 0` 时，必须在取模前提前返回 `r.primary`，否则会发生除以 `0` 的 panic。

模拟 Redis Stream 消费者组的核心状态机 `ConsumerGroup`：

- `Deliver(id string, consumer string, now time.Time)`：将消息 `id` 派发给 `consumer`，放入 PEL（Pending Entries List），记录所属消费者、派发时间 `DeliveredAt = now` 和投递次数 `Count = 1`；

title: 实现 Redis 小 Hash 分桶键映射器（Listpack 内存优化）
--- desc
为了将一千万个独立的 `String` 键值（如 `user:status:100001 -> "1"`）合并成紧凑的 `listpack` 编码小 Hash，我们按固定桶大小 `bucketSize`（例如 256）对 `id` 进行分桶：

- 外层 Hash Key 为 `fmt.Sprintf("%s:%d", prefix, id / bucketSize)`；
- 内层 Hash Field 为 `strconv.FormatInt(id % bucketSize, 10)`。

请实现 `ShardedHashStore` 的 `Set(id int64, val string)`、`Get(id int64) (string, bool)` 和 `OuterKeyCount() int`（返回外层 Hash Key 的总数）。
--- solution
package main

import (
	"fmt"
	"strconv"
)

type ShardedHashStore struct {
	prefix     string
	bucketSize int64
	hashes     map[string]map[string]string
}

func NewShardedHashStore(prefix string, bucketSize int64) *ShardedHashStore {
	return &ShardedHashStore{
		prefix:     prefix,
		bucketSize: bucketSize,
		hashes:     make(map[string]map[string]string),
	}
}

func (s *ShardedHashStore) keyAndField(id int64) (string, string) {
	// @solution
	key := fmt.Sprintf("%s:%d", s.prefix, id/s.bucketSize)
	field := strconv.FormatInt(id%s.bucketSize, 10)
	return key, field
	// @starter
	// return "", "" // TODO: 计算外层桶 key 和桶内偏移 field
	// @end
}

func (s *ShardedHashStore) Set(id int64, val string) {
	key, field := s.keyAndField(id)
	if s.hashes[key] == nil {
		s.hashes[key] = make(map[string]string)
	}
	s.hashes[key][field] = val
}

func (s *ShardedHashStore) Get(id int64) (string, bool) {
	key, field := s.keyAndField(id)
	h, ok := s.hashes[key]
	if !ok {
		return "", false
	}
	v, ok := h[field]
	return v, ok
}

func (s *ShardedHashStore) OuterKeyCount() int {
	return len(s.hashes)
}

通过整数除法 `id / bucketSize` 将相邻的 `bucketSize` 个 ID 聚合到同一个外层 Hash Key 下，并用取模 `id % bucketSize` 作为 Hash 内部的短字段名，使每个 Hash 的元素个数严格不超过 `bucketSize`（`<= 512`），从而让 Redis 始终保持零指针开销的 `listpack` 紧凑内存编码。

**代码讲解**

**易错点**

title: 实现支持 MOVED 与 ASK 重定向的 Redis Cluster 客户端请求路由器
--- desc
在 Redis Cluster 在线扩缩容迁移哈希槽（`MIGRATING` / `IMPORTING`）期间，客户端请求可能收到两种不同的重定向响应：

- **`MOVED <slot> <targetNode>`**（例如 `"MOVED 8888 node-b:6379"`）：表示槽 `slot` 已经**永久迁移**到 `targetNode`。客户端必须**更新本地槽位路由表缓存**（`c.slots[slot] = targetNode`），然后直接向 `targetNode` 重新发送原命令 `cmd`；
- **`ASK <slot> <targetNode>`**（例如 `"ASK 8888 node-b:6379"`）：表示槽 `slot` 正在迁移中途，当前请求的 key 已在 `targetNode` 上。客户端**绝不能更新本地槽位路由表缓存**（后续该槽的其他 key 默认仍先访问原节点），并且必须**先向 `targetNode` 发送一条 `"ASKING"` 命令**开启一次性临时许可，紧接着再向 `targetNode` 发送原命令 `cmd`。

请实现 `ClusterClient` 的 `Exec(slot int, cmd string, send func(node, cmd string) string) string` 与 `SlotNode(slot int) string`。
--- solution

	// @solution
	"strings"
	// @end

type ClusterClient struct {
	slots map[int]string
}

func NewClusterClient(initialSlots map[int]string) *ClusterClient {
	cp := make(map[int]string, len(initialSlots))
	for k, v := range initialSlots {
		cp[k] = v
	}
	return &ClusterClient{slots: cp}
}

func (c *ClusterClient) SlotNode(slot int) string {
	// @solution
	return c.slots[slot]
	// @starter
	// return "" // TODO: 返回本地路由表缓存中 slot 对应的节点地址
	// @end

func (c *ClusterClient) Exec(slot int, cmd string, send func(node, cmd string) string) string {
	// @solution
	node := c.slots[slot]
	resp := send(node, cmd)
	parts := strings.Fields(resp)
	if len(parts) == 3 {
		switch strings.TrimPrefix(parts[0], "-") {
		case "MOVED":
			target := parts[2]
			c.slots[slot] = target
			return send(target, cmd)

			return send(target, cmd)
		}
	}
	return resp

func TestClusterClientMovedAndAsk(t *testing.T) {

	// 1. 槽 8888 处于 MIGRATING -> IMPORTING 迁移中途：
	// k1 仍在 node-a 上正常返回；k2 已迁往 node-b，node-a 返回 ASK 临时重定向
	var callLog []string
	askingGranted := false
	sendDuringMigration := func(node, cmd string) string {
		callLog = append(callLog, node+"|"+cmd)
		if node == "node-a:6379" {
			if cmd == "GET k1" {
				return "val-1"
			}
			if cmd == "GET k2" {
				return "ASK 8888 node-b:6379"
			}
		}
		if node == "node-b:6379" {
			if cmd == "ASKING" {
				askingGranted = true
				return "OK"
			}
			if cmd == "GET k2" {
				if !askingGranted {
					// 若客户端未先发 ASKING 直接查 IMPORTING 槽，目标节点会拒绝并返回 MOVED
					return "MOVED 8888 node-a:6379"
				}

				return "val-2"
			}
		}
		return "ERR"
	}

	if got := c.Exec(8888, "GET k1", sendDuringMigration); got != "val-1" {
		t.Fatalf("GET k1 = %q, want val-1", got)
	}
	callLog = nil
	if got := c.Exec(8888, "GET k2", sendDuringMigration); got != "val-2" {
		t.Fatalf("GET k2 via ASK = %q, want val-2", got)
	}
	// 验证 ASK 必须先向目标节点发 ASKING，再发原命令
	wantAskLog := []string{
		"node-a:6379|GET k2",
		"node-b:6379|ASKING",
		"node-b:6379|GET k2",
	}
	if !slices.Equal(callLog, wantAskLog) {
		t.Fatalf("ASK call log = %v, want %v", callLog, wantAskLog)
	}
	// 验证 ASK 绝不能修改本地路由表缓存！
	if gotNode := c.SlotNode(8888); gotNode != "node-a:6379" {
		t.Fatalf("after ASK, SlotNode(8888) = %q, want node-a:6379 (must not update local table)", gotNode)

	// 2. 槽 8888 迁移彻底完成：node-a 返回 MOVED 永久重定向

		callLog = append(callLog, node+"|"+cmd)
		if node == "node-a:6379" {

			return "val-1-from-b"
		}

		t.Fatalf("GET k1 via MOVED = %q, want val-1-from-b", got)

	// 验证 MOVED 已刷新本地路由表缓存，后续请求直接发往 node-b
	if gotNode := c.SlotNode(8888); gotNode != "node-b:6379" {
		t.Fatalf("after MOVED, SlotNode(8888) = %q, want node-b:6379", gotNode)
	}
	callLog = nil
	_ = c.Exec(8888, "GET k1", sendAfterMigration)
	if !slices.Equal(callLog, []string{"node-b:6379|GET k1"}) {
		t.Fatalf("subsequent request should go directly to node-b, got %v", callLog)
	}

--- explain
**思路**

这道题把 Redis Cluster 槽迁移期间客户端路由的黄金法则落到了代码中：
- 收到 `MOVED <slot> <target>`：说明槽已经彻底归属新节点，**更新本地 `c.slots[slot] = target`** 并重发原命令；
- 收到 `ASK <slot> <target>`：说明槽仍在迁移中，**保持本地 `c.slots[slot]` 不变**，先向 `target` 发 `"ASKING"` 亮明临时通行证，再向 `target` 重发原命令。

**代码讲解**

1. `parts := strings.Fields(resp)`：按空白字符切分响应字符串，提取指令头 `parts[0]` 和目标节点地址 `parts[2]`。
2. `case "MOVED"`：执行 `c.slots[slot] = target` 永久更新本地槽缓存后重发。
3. `case "ASK"`：不改 `c.slots`，先调 `send(target, "ASKING")` 再调 `send(target, cmd)`。

**易错点**

- 处理 `ASK` 时误更新了 `c.slots[slot] = target`：会导致后续属于该槽但尚未迁移到 `target` 的存量 key 全部直接打到处于 `IMPORTING` 状态的 `target` 节点上，被 `target` 用 `MOVED` 踢回源节点，造成多余的乒乓重定向。
- 处理 `ASK` 时漏发 `"ASKING"` 命令：处于 `IMPORTING` 状态的目标节点默认拒绝不带 `ASKING` 前置标记的请求，直接返回 `-MOVED` 指回源节点，引发客户端死循环。
